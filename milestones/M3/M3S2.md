## Objective

Embed "The Mechanism" into the OMP AEF canonical architecture by codifying five mechanical discipline rules (uncertainty markers, zero-trust review, evidence-based debugging, raw evidence mandates, mechanical tooling stack) and creating a read-only ground-truth check utility. This specification targets scope items 1-6 of M3 that were not addressed in M3S1 (which focused on a separate Ladybug graph pipeline).

### Milestone Complexity & Multi-Spec Plan

This specification covers all five remaining process/culture scope items from M3 plus one small utility script. They form a coherent single delivery because:

- **All six items are additive and non-conflicting** — each modifies a disjoint set of files (different SKILL.md files, different templates, plus one new script).
- **No sequencing dependency** — the uncertainty marker, review mandate, debugging mandate, evidence mandate, ground-truth tool, and tooling stack can be implemented independently and in parallel.
- **Single delivery boundary** — each item is a targeted documentation edit or small script creation; none requires iteration or partial rollout.

The specification is structured as a single specification (M3S2) rather than multiple sub-specifications because the work is entirely additive documentation updates with no complex integration concerns.

## Functional Requirements

### FR-1: Uncertainty Marker (`#NEEDS-CLARIFICATION`)

**Target files:** `docs/FRAMEWORK.md`, `AGENTS.md`, `skills/implement-specification/SKILL.md`

Mandate the literal grep-able marker `#NEEDS-CLARIFICATION: <specific missing fact>` in the following locations:

- **`FRAMEWORK.md`** — Add a new section "The Uncertainty Marker" under Architectural Patterns (between Spec-Driven Development and Agent-Tool Separation). Define the rule: _If an agent's confidence in a fact is below "I could paste the command that proves this," it MUST either run the command immediately to prove it, or emit `#NEEDS-CLARIFICATION: <specific missing fact>` and HALT. Guessing is strictly forbidden._
- **`AGENTS.md`** — Add the Uncertainty Marker rule as a standing directive in the "When ambiguous" / core concepts section.
- **`skills/implement-specification/SKILL.md`** — Add the Uncertainty Marker rule to the "When uncertain" section of the Implementation Principles. The marker must be defined as the literal, grep-able string `#NEEDS-CLARIFICATION: <specific missing fact>`.

### FR-2: Zero-Trust Review Pass

**Target files:** `skills/review-implementation/SKILL.md`, `templates/review_template.md`

- **`skills/review-implementation/SKILL.md`** — Add a standing rule to the beginning of the process (before step 1) and as a header in the Review Analysis Rules section: _"Assume the prior report is wrong until proven otherwise. Verify every claim against the live state using bash or read commands."_ The reviewer agent MUST operate from a separate context (or at minimum, verify every claim independently rather than reading the completion report's self-assessment).
- **`templates/review_template.md`** — Add a new mandatory section "Live State Verification" that requires the reviewer to list which claims were verified, what commands were used, and what actual state was observed. This must appear after the Compliance Matrix and before Architecture Assessment.

### FR-3: Evidence-Based Debugging Mandate

**Target files:** `skills/investigate-issue/SKILL.md`, `skills/evaluate-implementation/SKILL.md`

- **`skills/investigate-issue/SKILL.md`** — Add a standing rule at the top of the process (before step 1) and in the Investigation Strategy section: _"Debug from evidence, never from memory. The first action on any unfamiliar error is to read the literal message and use the tool's --help or introspection command. Never pattern-match from similar tools."_
- **`skills/evaluate-implementation/SKILL.md`** — Add the same standing rule at the top of Your Process (before step 1).

### FR-4: Raw Evidence Mandate

**Target files:** `templates/completion_template.md`, `templates/evaluation_template.md`

- **`templates/completion_template.md`** — Add a mandatory "## Raw Evidence" section after the existing "Technical Debt incurred" section. The section must contain: _"Every 'done' claim must ship with the exact terminal command and raw output that proves it succeeded."_ Followed by a bullet list template: `- [ ] <requirement>: \`<command>\` → <raw output>`.
- **`templates/evaluation_template.md`** — Add the same mandatory "## Raw Evidence" section in the same position.

### FR-5: Ground-Truth Helper Utility

**Target files:** `bin/ground-truth-check.sh` (new file)

Create a single-file, strictly read-only shell script at `~/devcode/aef/agent/bin/ground-truth-check.sh` that provides low-friction live-state verification without writing complex bash one-liners. The script MUST:

- Accept a command argument: `file-exists <path>`, `git-status [path]`, `command-exists <name>`, `dir-exists <path>`, `file-contains <path> <pattern>`.
- Execute the check and output: `PASS: <description>` or `FAIL: <description>` with exit code 0 or 1 respectively.
- Be strictly read-only — never write, create, modify, or delete any file or state.
- Use only POSIX shell and standard Unix utilities (`test`, `grep`, `git`, `which`, `ls`) — no dependencies beyond stdlib.
- Be self-documenting: running with no arguments or `--help` prints a usage synopsis.
- Be explicitly documented for agent use in its header comments.

### FR-6: Mechanical Tooling Stack Mandate

**Target files:** `skills/bootstrap-project/SKILL.md`, `AGENTS.md`

- **`skills/bootstrap-project/SKILL.md`** — Add a new step between existing step 7 (Create missing documents) and step 8 (Create root-level entry points): _"Define and document the Mechanical Tooling Stack. During bootstrapping, advise the project to establish the following categories (project- and language-agnostic): — **Environment Manager** (to prevent version ambiguity and auto-activate toolchains); — **Fast Linter/Formatter** (to provide a deterministic gate an agent can auto-fix against); — **Pre-commit Framework** (to run local gates automatically on every commit without cloud CI); — **Type Checker** (to catch silent property/type mismatches before runtime)."_
- **`AGENTS.md`** — Add a new section in Core Concepts (after Agent Handoffs): **Mechanical Tooling Stack** describing the four tooling categories and the mandate that every bootstrapped project document its chosen stack.

## Non-Functional Requirements

- **NFR-1** — All changes are documentation-only except `bin/ground-truth-check.sh` which is a read-only utility. No code with side effects, enforcement logic, or state mutation is permitted.
- **NFR-2** — The `#NEEDS-CLARIFICATION` marker must be literally grep-able as a single string. No quoting, no abbreviation, no optional parts. The `<specific missing fact>` placeholder is part of the marker.
- **NFR-3** — The ground-truth utility MUST use only POSIX shell and standard Unix utilities. No Python, Node.js, or external dependencies.
- **NFR-4** — No specific tooling brands may be hardcoded (e.g., `mise`, `ruff`, `pre-commit`, `mypy`). Only the category/function must be specified.

## Data Flow

This specification has no data flow between components — all changes are documentation updates and a standalone utility script. The ground-truth utility reads local filesystem state but produces no persistent data; its output is printed to stdout with exit code signaling.

```
Agent/Reviewer
  ↓ (bash invocation)
bin/ground-truth-check.sh <command> <args>
  ↓ (reads filesystem state)
stdout: PASS:/FAIL: <description>
  ↓ (exit code 0/1)
Caller interprets result
```
