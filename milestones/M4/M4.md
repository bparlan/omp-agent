## Goal

Stabilise the OMP/AEF development orchestration so that the pre-implementation Software Development lifecycle is deterministic, resumable, auditable, and strictly gated.

## Motivation

A recent orchestration failure demonstrated that `implement-specification` began before `generate-tests` had successfully completed. This is a critical framework integrity problem.

The intended lifecycle is:

```
Specification → Verification → Tests → Human approval → Implementation
```

The framework must not rely on an agent remembering this sequence from prose instructions. The orchestration layer must enforce the sequence through explicit state, artifact validation, and preconditions.

The recent failure must be investigated before making any changes to the framework.

## Scope

1. **Investigate the Existing Failure**

   Inspect the current implementation of orchestration and state-management:
   - `manage-development`
   - `manage-roadmap`
   - `generate-spec`
   - `generate-verification`
   - `generate-tests`
   - `approve-spec`
   - `implement-specification`
   - Existing OMP state-management conventions
   - Milestone/task artifact conventions

   Determine exactly how `implement-specification` was reached before `generate-tests`.

2. **Define the Pre-Implementation State Machine**

   Establish explicit lifecycle states:
   - `PLANNING_READY`
   - `SPEC_GENERATED`
   - `VERIFICATION_GENERATED`
   - `TESTS_GENERATED`
   - `PRE_IMPLEMENTATION_READY`
   - `AWAITING_HUMAN_APPROVAL`
   - `APPROVED_FOR_IMPLEMENTATION`

   Define the invariant:
   ```
   IMPLEMENTATION_ALLOWED only if:
       SPECIFICATION_VALID
       AND
       VERIFICATION_VALID
       AND
       TESTS_VALID
       AND
       PRE_IMPLEMENTATION_READINESS_PASS
       AND
       EXPLICIT_HUMAN_APPROVAL
   ```

3. **Mandatory Pre-Implementation Chain**

   `manage-development` must enforce:
   ```
   generate-spec
       ↓
   generate-verification
       ↓
   generate-tests
       ↓
   readiness validation
       ↓
   approval gate
       ↓
   implementation allowed
   ```

   Do not skip stages based on appearance of artifacts. Treat missing or invalid artifacts as stage failures.

4. **Generate Tests Before Implementation**

   The framework must explicitly enforce test-first readiness. Tests may initially fail because production implementation does not yet exist.

   Preserve the change in `generate-tests` that removed the implementation-code-read requirement. Do not reintroduce dependencies on implementation code.

5. **Test Readiness Validation**

   After `generate-tests`, validate:
   - Specification exists and is valid
   - Verification exists and is valid
   - Tests exist and are valid
   - Consistency across all three artifacts

   Produce `READY_FOR_APPROVAL` or `NOT_READY_FOR_APPROVAL`.

   If `NOT_READY_FOR_APPROVAL`, STOP and report exact blockers.

6. **Human Approval Gate**

   Only after readiness passes may the workflow enter the approval gate. Generate a consolidated report including:
   - Specification summary
   - Verification summary
   - Test summary
   - Consistency summary

   The report must clearly state `READY FOR IMPLEMENTATION APPROVAL` or `NOT READY FOR IMPLEMENTATION APPROVAL`.

   No implicit approval.

7. **Preserve `approve-spec`**

   Do not remove, deprecate, or redesign `approve-spec`. The responsibility separation should be:
   - `manage-development` determines WHEN approval is required
   - `approve-spec` presents/handles the approval decision

8. **Resume and Recovery**

   Support safe resumption at the earliest incomplete valid stage. Invalidate and rebuild downstream artifacts when upstream artifacts change.

9. **Artifact Integrity**

   Validate artifacts rather than relying on filenames or completion reports. Distinguish:
   - MISSING
   - GENERATED
   - VALIDATED
   - STALE
   - APPROVED

10. **`manage-roadmap` Refinement**

    Keep `manage-roadmap` focused on planning and documentation. Hand off execution-ready work to `manage-development` with explicit handoff information.

11. **Negative Guardrails**

    Do NOT:
    - Allow `implement-specification` before `generate-tests`
    - Allow implementation without verification
    - Allow implementation without specification
    - Allow implementation without readiness validation
    - Allow implementation without explicit human approval
    - Treat completion reports as sufficient evidence
    - Silently bypass missing artifacts
    - Silently regenerate implementation when tests are missing
    - Reintroduce implementation-code dependencies into `generate-tests`
    - Remove the approval gate
    - Remove `approve-spec`
    - Implement autonomous hotfix loops
    - Implement automatic issue routing
    - Implement post-implementation review orchestration

12. **Permitted Changes to Individual Skills**

    Do not redesign domain logic of `generate-spec`, `generate-verification`, `generate-tests`, `implement-specification`, or `approve-spec`. Only lightweight interface improvements are permitted.

13. **Required Validation**

    Create tests demonstrating:
    - Test A — Correct ordering
    - Test B — Missing tests block implementation
    - Test C — Missing verification blocks implementation
    - Test D — Readiness failure blocks approval
    - Test E — Explicit approval required
    - Test F — Explicit approval granted
    - Test G — Resume functionality

## Risks

- Risk: Over-engineering the state machine adds complexity and maintenance burden.
  Mitigation: Use existing OMP conventions where possible. Keep state machine lightweight.

- Risk: Modifying `manage-development` may break existing workflows that depend on its current behaviour.
  Mitigation: Carefully test changes with existing milestones. Verify backwards compatibility.

- Risk: Tests generated before implementation may appear to be failures that the user misinterprets as generation failures.
  Mitigation: Document clearly that initial test failures are expected, not errors.

- Risk: Removing orchestration flexibility may slow down development in some scenarios.
  Mitigation: Provide clear documentation and examples of proper usage.

## Notes

- The investigation of the existing failure is a prerequisite for any changes.
- Preserve existing `approve-spec` functionality and architecture.
- Do not implement autonomous repair/review loops in this milestone.
- Do not redesign domain logic of individual SDD skills unnecessarily.
- The definition of done requires independent verification of the integrity guarantees.
