## Objective

Establish a deterministic, resumable, auditable, and strictly gated pre-implementation Software Development lifecycle by defining a pre-implementation state machine, enforcing mandatory stage ordering, implementing artifact integrity validation, and creating explicit approval gates that prevent implementation until all prerequisites are satisfied.

### Milestone Complexity & Multi-Spec Plan

This milestone is a single, cohesive specification. The pre-implementation integrity concerns are tightly coupled and cannot be separated into independent specifications without breaking the integrity guarantees.

## Functional Requirements

- **FR-1**: Investigate the existing orchestration failure where `implement-specification` began before `generate-tests`.
  - Identify how the violation occurred
  - Document the exact point where the invariant was broken
  - Determine root cause (orchestration logic, state detection, missing validation, etc.)

- **FR-2**: Define the pre-implementation state machine with 7 explicit states:
  - `PLANNING_READY`
  - `SPEC_GENERATED`
  - `VERIFICATION_GENERATED`
  - `TESTS_GENERATED`
  - `PRE_IMPLEMENTATION_READY`
  - `AWAITING_HUMAN_APPROVAL`
  - `APPROVED_FOR_IMPLEMENTATION`

- **FR-3**: Define the invariant that allows implementation:
  ```
  IMPLEMENTATION_ALLOWED only if:
      SPECIFICATION_VALID
      AND
      VERIFICATION_VALID
      AND
      TESTS_VALID
      AND
      PRE_IMPLEMENTATION_READINESS_PASS
      AND
      EXPLICIT_HUMAN_APPROVAL
  ```

- **FR-4**: Enforce the mandatory pre-implementation chain in `manage-development`:
  ```
  generate-spec
      ↓
  generate-verification
      ↓
  generate-tests
      ↓
  readiness validation
      ↓
  approval gate
      ↓
  implementation allowed
  ```

- **FR-5**: Enforce test-first readiness by blocking implementation if tests do not exist or are invalid.

- **FR-6**: Implement test readiness validation after `generate-tests` that confirms:
  - Specification exists and is valid
  - Verification exists and is valid
  - Tests exist and are valid
  - Consistency across all three artifacts

- **FR-7**: Implement the readiness validation check that produces `READY_FOR_APPROVAL` or `NOT_READY_FOR_APPROVAL`.

- **FR-8**: Implement the human approval gate that:
  - Only allows entry after readiness validation passes
  - Generates a consolidated report with specification, verification, and test summaries
  - Clearly states `READY FOR IMPLEMENTATION APPROVAL` or `NOT READY FOR IMPLEMENTATION APPROVAL`

- **FR-9**: Preserve `approve-spec` without modification and maintain its existing responsibility to present/handle approval decisions.

- **FR-10**: Support safe resumption at the earliest incomplete valid stage:
  - Resume from `generate-verification` after `generate-spec`
  - Resume from `generate-tests` after `generate-verification`
  - Resume from readiness validation after `generate-tests`
  - Resume from approval gate after readiness
  - Resume from implementation after approval

- **FR-11**: Implement artifact integrity validation that distinguishes:
  - `MISSING`
  - `GENERATED`
  - `VALIDATED`
  - `STALE`
  - `APPROVED`

- **FR-12**: Implement resume and recovery that invalidates and rebuilds downstream artifacts when upstream artifacts change.

- **FR-13**: Refine `manage-roadmap` to focus on planning/documentation and hand off execution-ready work to `manage-development` with explicit handoff information (milestone ID, task ID, current state, available artifacts, next expected stage).

- **FR-14**: Implement all negative guardrails to prevent invalid workflows:
  - Do not allow `implement-specification` before `generate-tests`
  - Do not allow implementation without verification
  - Do not allow implementation without specification
  - Do not allow implementation without readiness validation
  - Do not allow implementation without explicit human approval
  - Do not treat completion reports as sufficient evidence
  - Do not silently bypass missing artifacts
  - Do not silently regenerate implementation when tests are missing
  - Do not reintroduce implementation-code dependencies into `generate-tests`
  - Do not remove the approval gate
  - Do not remove `approve-spec`
  - Do not implement autonomous hotfix loops
  - Do not implement automatic issue routing
  - Do not implement post-implementation review orchestration

- **FR-15**: Create validation tests demonstrating:
  - Test A — Correct ordering: Verify that the sequence `generate-spec → generate-verification → generate-tests → readiness → approval → implementation` is enforced
  - Test B — Missing tests: Given spec+verification exist, tests missing, implementation is blocked
  - Test C — Missing verification: Given spec+tests exist, verification missing, implementation is blocked
  - Test D — Readiness failure: Given spec/verification/tests inconsistent, approval is blocked
  - Test E — Explicit approval required: Given all artifacts valid and readiness passes, no approval, implementation is blocked
  - Test F — Explicit approval granted: Given all artifacts valid and readiness passes, explicit approval, implementation may begin
  - Test G — Resume: Verify an interrupted workflow resumes at the earliest incomplete valid stage

## Non-Functional Requirements

- **NFR-1**: The pre-implementation workflow must be deterministic (same input always produces same output).
- **NFR-2**: The workflow must be resumable (can continue from any incomplete stage without restarting completed stages).
- **NFR-3**: All state changes and gate decisions must be auditable (traceable to source, timestamped, reason documented).
- **NFR-4**: The system must fail closed (no invalid state transitions allowed).
- **NFR-5**: The state machine must be lightweight (avoid over-engineering; use existing OMP conventions where possible).
- **NFR-6**: Changes to `manage-development` must maintain backwards compatibility with existing milestones.

## Data Flow

The pre-implementation workflow flows as follows:

1. **Specification Generation** (`generate-spec`):
   - Input: Milestone/task context
   - Output: `specification` artifact (M{X}S{Y}.md)
   - State transition: `PLANNING_READY` → `SPEC_GENERATED`
   - Validation: Artifact existence and basic coherence

2. **Verification Generation** (`generate-verification`):
   - Input: Specification artifact
   - Output: `verification` artifact (M{X}S{Y}V.md)
   - State transition: `SPEC_GENERATED` → `VERIFICATION_GENERATED`
   - Validation: Verification exists and corresponds to specification

3. **Test Generation** (`generate-tests`):
   - Input: Specification and verification artifacts
   - Output: `tests` artifact (tests/M{X}/*.md, *.py, *.js, etc.)
   - State transition: `VERIFICATION_GENERATED` → `TESTS_GENERATED`
   - Validation: Tests exist and correspond to verification criteria

4. **Readiness Validation** (`manage-development`):
   - Input: Specification, verification, and tests artifacts
   - Output: `READY_FOR_APPROVAL` or `NOT_READY_FOR_APPROVAL`
   - State transition: `TESTS_GENERATED` → `PRE_IMPLEMENTATION_READY`
   - Validation: All artifacts exist and are consistent

5. **Human Approval** (`approve-spec`):
   - Input: Consolidated report (spec/verification/test summaries)
   - Output: Approval decision (approved/rejected)
   - State transition: `PRE_IMPLEMENTATION_READY` → `AWAITING_HUMAN_APPROVAL` → `APPROVED_FOR_IMPLEMENTATION`
   - Validation: Explicit human approval required

6. **Implementation** (`implement-specification`):
   - Input: Approved artifacts and explicit approval
   - Output: Implementation (code changes)
   - State transition: `APPROVED_FOR_IMPLEMENTATION` → Implementation begins
   - Validation: All prerequisites satisfied (gate enforced by `manage-development`)

## Assumptions

- The OMP AEF framework currently has an unbounded SDD pipeline without strict pre-implementation gates.
- The recent orchestration failure was caused by the orchestrator trusting completion reports or filenames rather than validating actual artifacts.
- Existing OMP state-management conventions can be leveraged without introducing a new state-management subsystem.
- Milestone/task artifact conventions (M{X}, M{X}S{Y}, etc.) are stable and will not change in this milestone.
- The `generate-tests` skill already has the implementation-code-read requirement removed; this must be preserved.
- Human approval is always required before implementation begins (no automation of this gate).
- Resume/recovery must not restart valid completed stages unnecessarily.
- The state machine must be lightweight and use existing conventions where possible.
