## Objective

Automate post-approval execution of the OMP/AEF development pipeline so that, after explicit human approval, the framework autonomously chains implement-specification → evaluate-implementation → automatic routing (PASS/MINOR/COMPLEX/HUMAN) → repair/review, with bounded repair loops, protected approval gate, and test-driven completion enforced.

### Milestone Complexity & Multi-Spec Plan

This milestone is comprehensive but cohesive—no multi-spec plan needed. One specification covers all aspects of post-approval automation.

## Functional Requirements

**FR-1**: Post-Approval Automation Chain
- Orchestrator MUST automatically chain implement-specification → evaluate-implementation after explicit human approval, without manual invocation between stages.
- Implementation receives approved artifacts (specification, verification protocol, test plan).
- Orchestrator MUST NOT declare success merely because implementation completed without an error.

**FR-2**: Evaluation Routing
- Orchestrator MUST evaluate implementation results and automatically route to appropriate next step:
  - **PASS path**: evaluate → review-implementation → final report to user
  - **MINOR IMPLEMENTATION DEFECT path**: evaluate → hotfix-issue → evaluate again (no approval required), provided:
    - Root cause is sufficiently clear
    - Defect is localized
    - Specification remains valid
    - Verification criteria remain valid
    - Approved scope remains valid
    - Existing tests can validate the fix
  - **COMPLEX OR UNCLEAR ISSUE path**: evaluate → investigate-issue when:
    - Root cause is unclear
    - Issue crosses multiple components
    - Architecture may be wrong
    - Specification may be incomplete
    - Verification criteria may be invalid
    - Scope may need to change
    - Investigation produces concrete report
    - If investigation concludes requirements/architecture/scope must change:
      - Workflow MUST automatically return to: specification → verification → tests → readiness → human approval → implementation
  - **HUMAN ESCALATION path**: Orchestrator MUST ask user for intervention when:
    - Requirements conflict
    - Architectural decisions are required
    - Approved scope must change
    - Autonomous repair is unsafe
    - Autonomous repair cycles are exhausted
    - Investigation cannot establish reliable root cause
    - Tests and specification disagree in a way that requires a decision
    - User MUST receive concise but evidence-based report containing: current state, root cause/uncertainty, attempted actions, failed tests, proposed options, exact decision required

**FR-3**: Autonomous Repair Loop Limit
- Orchestrator MUST enforce MAX_AUTO_REPAIR_CYCLES limit (default 2 or 3) to prevent infinite repair loops.
- Orchestrator MUST track repair attempts for current implementation task.
- If MAX_AUTO_REPAIR_CYCLES limit is reached: Orchestrator MUST STOP, REPORT, and ASK HUMAN.
- Repair counter MUST reset only when workflow enters genuinely new approved implementation cycle.

**FR-4**: Approval Gate Protection During Repair
- Orchestrator MUST ensure autonomous hotfix never becomes approval bypass.
- If repair changes requirements, architecture, approved scope, acceptance criteria, verification criteria, or test expectations:
  - It is NOT a simple hotfix
  - Workflow MUST automatically return to: specification → verification → tests → readiness → human approval
  - Only after human approval may implementation continue

**FR-5**: Test-Driven Completion
- Final success condition MUST be: implementation completed AND tests pass AND verification passes AND evaluation passes AND review passes.
- Orchestrator MUST treat test failures as real implementation failures.
- Orchestrator MUST NOT weaken, remove, skip, or rewrite tests merely to make pipeline green.
- If test is genuinely incorrect: Orchestrator MUST identify as specification/verification/test integrity issue and return through appropriate change path.

**FR-6**: Review Automation
- Orchestrator MUST automatically invoke review-implementation when evaluation passes.
- Final review report MUST include: what was implemented, specification compliance, verification results, test results, review findings, known limitations, any follow-up technical debt.
- Review report MUST be returned to user.
- Orchestrator MUST NOT automatically start another milestone unless existing roadmap conventions explicitly require it.

**FR-7**: manage-development Full Lifecycle Orchestration
- manage-development MUST become full lifecycle orchestrator:
  - **Before approval**: generate-spec → generate-verification → generate-tests → readiness → approval
  - **After approval**: implement → evaluate → repair/investigate/review
- manage-development MUST own: sequencing, state, preconditions, postconditions, routing, retry limits, human gates.
- Individual skills (generate-spec, generate-verification, generate-tests, readiness, approve-spec, implement-specification, evaluate-implementation, review-implementation, hotfix-issue, investigate-issue) MUST own their domain-specific work.
- Orchestrator coordinates, does not rewrite.

**FR-8**: manage-roadmap Strategic Focus
- manage-roadmap MUST NOT expand into post-approval implementation lifecycle.
- manage-roadmap MUST remain responsible for: roadmap state, milestone planning, milestone creation, decomposition, documentation, readiness for development.
- Once execution-ready: manage-roadmap → manage-development handoff occurs.

## Non-Functional Requirements

**NFR-1**: Safety Boundaries
- Approval gate from M4 MUST remain non-negotiable.
- No route from specification → implementation bypasses: verification → tests → readiness → explicit approval.
- All repair paths that change requirements MUST automatically return to approval gate.

**NFR-2**: Maintainability
- Orchestrator logic must be modular and testable.
- Routing decisions must be evidence-based, not guess-based.
- Human gates must be positioned at decision points, not hidden.

**NFR-3**: Performance
- Evaluation routing decisions must be made quickly (< 1 second per evaluation).
- Repair loop limit enforcement must be constant-time O(1).
- No unnecessary file I/O or redundant artifact reading.

**NFR-4**: Reliability
- Orchestrator must handle partial failures gracefully (e.g., implementation starts but evaluation fails).
- State transitions must be robust against tool failures (resume/recovery from M4).
- No data loss during state transitions.

**NFR-5**: Usability
- When human escalation is required, report must be concise but evidence-based.
- Report must include: current state, root cause/uncertainty, attempted actions, failed tests, proposed options, exact decision required.
- User must clearly understand what is happening and why.

**NFR-6**: Testability
- All routing paths must be testable in isolation.
- Repair loop limit must be independently verifiable.
- Approval gate protection must be independently testable.
- Test-driven completion enforcement must be independently testable.

**NFR-7**: Extensibility
- Repair loop limit should be configurable (environment variable or config file).
- Routing thresholds should be configurable if needed in future.
- No hardcoding of specific skills or paths in orchestration logic.

## Data Flow

**Pre-Approval (existing flow):**
```
generate-spec → generate-verification → generate-tests → readiness → approval
```

**Post-Approval (new flow):**
```
approval
    ↓
IMPLEMENT (implements approved specification)
    ↓
EVALUATE (evaluates implementation)
    ↓
┌───────────────────────────────────────┐
│ ROUTING DECISION                      │
├───────────────────────────────────────┤
│ PASS                                  │
│   → REVIEW (automatic)                │
│   → Final Report → USER               │
├───────────────────────────────────────┤
│ MINOR DEFECT                          │
│   → HOTFIX (no approval)               │
│   → EVALUATE (re-run)                 │
│   → ... (loop repeats up to limit)    │
│   → STOP after MAX_AUTO_REPAIR_CYCLES │
├───────────────────────────────────────┤
│ COMPLEX ISSUE                         │
│   → INVESTIGATE                       │
│   → DETECT REQUIREMENT CHANGE?         │
│     YES: spec → verif → tests → readi → approval → implement (NEW CYCLE)
│     NO:  EVALUATE (re-run)             │
├───────────────────────────────────────┤
│ HUMAN ESCALATION                      │
│   → REPORT (evidence-based)           │
│   → WAIT FOR USER DECISION            │
└───────────────────────────────────────┘
```

**State Machine (post-approval):**
```
POST_APPROVAL
    ↓
IMPLEMENTING
    ↓
EVALUATING
    ↓
┌─────────────────────┬───────────────────────┬─────────────────────┬───────────────────────┐
│ PASS                │ MINOR                 │ COMPLEX             │ HUMAN                 │
│                     │ DEFECT                │ ISSUE               │ ESCALATION            │
├─────────────────────┼───────────────────────┼─────────────────────┼───────────────────────┤
│ → REVIEWING         │ → HOTFIXING           │ → INVESTIGATING     │ → REPORTING           │
│    → FINAL REPORT   │    → EVALUATING       │    → DETECT CHANGE? │    → WAITING          │
│    → USER           │    → (loop)            │    YES: spec → ...  │    → DECISION?        │
│                     │    → (stop if limit)  │    NO:  → EVALUATE  │                        │
│                     │    → STOP if limit    │                      │                        │
│                     │    → RETURN if limit  │                      │                        │
└─────────────────────┴───────────────────────┴─────────────────────┴───────────────────────┘
```

**Repair Loop Tracking:**
```
State fields:
- current_implementation_task: (task identifier)
- repair_attempt_counter: integer (starts at 0)
- max_repair_cycles: integer (default 2 or 3)

Operations:
- increment_repair_counter()
- get_repair_cycle_count()
- reset_repair_counter() (called on new approval)
- check_repair_limit(): returns true if counter >= max_repair_cycles
```
