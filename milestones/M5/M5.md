# Milestone M5: Automate the Post-Approval Development and Recovery Loop

**Status**: Planning
**Phase**: Requirements Elicitation
**Date**: 2026-07-26

---

## Goal

Extend the now-stable OMP/AEF development orchestration so that, after explicit human approval, the framework can autonomously execute implementation, evaluation, issue routing, repair, and final review.

The pre-implementation pipeline and approval gate are already established by the preceding orchestration-integrity milestone (M4).

This milestone must NOT weaken, bypass, or redesign that gate.

---

## Motivation

### Why This Matters

The current SDD pipeline requires manual handoffs between almost every stage:
1. Human creates milestone
2. Human runs generate-spec
3. Human runs generate-verification
4. Human runs generate-tests
5. Human runs readiness validation
6. Human runs generate_approval_report
7. Human invokes approve-spec
8. Human invokes implement-specification
9. Human invokes evaluate-implementation
10. Human reviews results
11. Human decides on repairs
12. Human re-runs steps

This friction:
- **Slows down development**: Manual handoffs consume cognitive load and time
- **Increases error risk**: Humans forget steps or misapply context
- **Breaks flow**: Each handoff interrupts momentum
- **Violates pipeline invariants**: Manual execution can skip or misorder steps

### Consequences of Inaction

Without this automation:
- Every implementation requires multiple manual interventions
- Human cognitive load remains high throughout the pipeline
- Development speed remains limited by manual orchestration
- Error recovery remains manual and error-prone
- The powerful pre-implementation integrity is only half-utilized

By automating post-approval execution, we:
- Free human from manual orchestration
- Enable continuous execution without interruption
- Maintain strict safety boundaries (no bypassing approval)
- Achieve true end-to-end automation
- Scale the framework to larger projects

## Scope

### In-Scope

1. **Automate Post-Approval Execution**
   - After approval, automatically chain: implement-specification → evaluate-implementation
   - No manual invocation between these stages
   - Implementation receives approved artifacts
   - Evaluation inspects: implementation correctness, specification compliance, verification criteria, test results, known risks
   - Orchestrator does not declare success merely because implementation completed without an error

2. **Evaluation Routing Based on Results**
   - **PASS**: Automatically invoke review-implementation, return final review report to user
   - **MINOR IMPLEMENTATION DEFECT**: Use hotfix-issue only when:
     - Root cause is sufficiently clear
     - Defect is localized
     - Specification remains valid
     - Verification criteria remain valid
     - Approved scope remains valid
     - Existing tests can validate the fix
     - Workflow: evaluate → hotfix-issue → evaluate again (no human approval required)
   - **COMPLEX OR UNCLEAR ISSUE**: Use investigate-issue when:
     - Root cause is unclear
     - Issue crosses multiple components
     - Architecture may be wrong
     - Specification may be incomplete
     - Verification criteria may be invalid
     - Scope may need to change
     - Investigation produces concrete report
     - If investigation concludes requirements/architecture/scope must change:
       - Return to specification → verification → tests → readiness → human approval → implementation
   - **HUMAN ESCALATION**: Ask user for intervention when:
     - Requirements conflict
     - Architectural decisions are required
     - Approved scope must change
     - Autonomous repair is unsafe
     - Autonomous repair cycles are exhausted
     - Investigation cannot establish reliable root cause
     - Tests and specification disagree in a way that requires a decision
     - User receives concise but evidence-based report containing: current state, root cause/uncertainty, attempted actions, failed tests, proposed options, exact decision required

3. **Autonomous Repair Loop Limit**
   - Prevent infinite repair loops
   - Configurable limit: MAX_AUTO_REPAIR_CYCLES (default: 2 or 3)
   - Track repair attempts for current implementation task
   - If limit reached: STOP, REPORT, ASK HUMAN
   - Reset counter only when workflow enters genuinely new approved implementation cycle

4. **Protect Approval Gate During Repair**
   - Autonomous hotfix must NOT become approval bypass
   - If repair changes requirements, architecture, approved scope, acceptance criteria, verification criteria, or test expectations:
     - It is NOT a simple hotfix
     - Workflow must return to: specification → verification → tests → readiness → human approval
     - Only then may implementation continue

5. **Test-Driven Completion**
   - Final success condition: implementation completed AND tests pass AND verification passes AND evaluation passes AND review passes
   - Orchestrator treats test failures as real implementation failures
   - Do not weaken, remove, skip, or rewrite tests merely to make pipeline green
   - If test is genuinely incorrect: specification/verification/test integrity issue → return through appropriate change path

6. **Review Automation**
   - When evaluation passes, review-implementation runs automatically
   - Final report includes: what was implemented, specification compliance, verification results, test results, review findings, known limitations, any follow-up technical debt
   - Report returned to user
   - Do not automatically start another milestone unless existing roadmap conventions explicitly require it

7. **manage-development Responsibilities**
   - Becomes full lifecycle orchestrator
   - **Before approval**: generate-spec → generate-verification → generate-tests → readiness → approval
   - **After approval**: implement → evaluate → repair/investigate/review
   - Owns: sequencing, state, preconditions, postconditions, routing, retry limits, human gates
   - Individual skills own their domain-specific work

8. **manage-roadmap Responsibilities**
   - Do NOT expand into post-approval implementation lifecycle
   - Remains responsible for: roadmap state, milestone planning, milestone creation, decomposition, documentation, readiness for development
   - Once execution-ready: manage-roadmap → manage-development

### Out of Scope

1. **Approval Gate Removal or Weakening**
   - Must NOT remove, bypass, or redesign the approval gate
   - Pre-implementation integrity from M4 must remain intact
   - No route from specification → implementation that bypasses: verification → tests → readiness → explicit approval

2. **Modifying Individual Skills Internal Logic**
   - Do NOT redesign internal domain logic of individual SDD skills
   - Each skill owns its specific responsibilities
   - Orchestrator only coordinates, does not rewrite

3. **Automatic Approval**
   - Do NOT allow autonomous approval of changed requirements
   - Any requirement change requires human approval
   - Do NOT remove approve-spec skill unless separately approved as architectural change

4. **Milestone Auto-Creation**
   - Do NOT automatically start new milestones
   - Only start new milestones if existing roadmap conventions explicitly require it

5. **Execution without Approval**
   - Do NOT execute implementation without explicit human approval
   - The approval gate from M4 must remain non-negotiable

6. **Hotfixes Changing Requirements**
   - Do NOT let hotfixes change requirements silently
   - If requirements change, workflow returns to approval gate

7. **Infinite Repair Loops**
   - Do NOT continue indefinitely
   - Stop after MAX_AUTO_REPAIR_CYCLES reached
   - Ask human for intervention

## Success Criteria

### Primary Success Criteria

1. **Post-Approval Automation Complete**
   - After approval, framework automatically executes: implement → evaluate → route → repair/review
   - No manual invocation between these stages (except where required for human escalation)
   - Orchestrator maintains full control over sequencing and routing

2. **Evaluation Routing Implemented**
   - PASS path: evaluate → review → final report
   - MINOR defect path: evaluate → hotfix-issue → evaluate (no approval)
   - COMPLEX issue path: evaluate → investigate → (spec change? → approval) → continue
   - HUMAN escalation path: user receives decision report with clear evidence

3. **Repair Loop Bounded**
   - MAX_AUTO_REPAIR_CYCLES limit (default 2-3) prevents infinite loops
   - Counter resets for new implementation cycles
   - Stop after limit reached and report to user

4. **Approval Gate Protected**
   - No repair path can silently modify requirements
   - Any requirement change returns to approval gate
   - Hotfixes limited to localized scope changes

5. **Test-Driven Completion**
   - Tests pass is required for final success
   - Test failures prevent final success
   - No test weakening or rewriting

6. **Review Automation**
   - review-implementation runs automatically when evaluation passes
   - Final report includes all required information
   - Report returned to user

### Secondary Success Criteria

7. **manage-development Full Lifecycle Orchestration**
   - Owns sequencing, state, preconditions, postconditions, routing, retry limits, human gates
   - No duplication of individual skill internal logic

8. **manage-roadmap Strategic Focus**
   - Remains focused on strategic responsibilities
   - Does NOT expand into execution lifecycle

9. **Zero Breaking Changes**
   - Existing functionality preserved
   - All changes are additive or refactoring
   - Backward compatible

10. **Test Coverage**
    - All routing paths tested
    - Loop limit tested
    - Approval protection tested
    - Test-Driven Completion enforced

## Risks

### Risk 1: Approval Gate Weakening

**Description**: Risk that automation requirements may tempt us to weaken or bypass the approval gate to achieve smoother automation.

**Impact**: HIGH - Violates fundamental safety principle established in M4

**Mitigation**:
- Explicit requirement: "NO implementation before explicit human approval"
- All repair paths that change requirements must return to approval gate
- Review M4 approval gate implementation before proceeding
- Do NOT implement any route from specification → implementation that bypasses verification → tests → readiness → explicit approval
- Verify in all tests that approval gate remains intact

### Risk 2: Hotfix Changing Requirements Silently

**Description**: Risk that hotfix-issue may modify requirements or scope without requiring re-approval.

**Impact**: HIGH - Violates specification integrity principle

**Mitigation**:
- Explicit requirement: "No hotfixes changing requirements silently"
- Implement requirements-change detection in hotfix-issue
- If requirements change, automatically route to approval gate
- Document this protection in both skills
- Test that requirement changes require re-approval

### Risk 3: Infinite Repair Loops

**Description**: Risk that repair loops continue indefinitely, wasting time and resources.

**Impact**: MEDIUM - Lowers efficiency, wastes compute resources

**Mitigation**:
- Implement MAX_AUTO_REPAIR_CYCLES limit (default 2-3)
- Track repair attempts per implementation task
- Stop after limit reached and report to user
- Reset counter for new implementation cycles
- Test that limit is enforced

### Risk 4: Test-Driven Completion Erosion

**Description**: Risk that test failures may be silently suppressed or tests weakened to achieve pipeline green state.

**Impact**: HIGH - Violates test integrity principle

**Mitigation**:
- Explicit requirement: "Treat test failures as real implementation failures"
- Do NOT weaken, remove, skip, or rewrite tests
- If test is incorrect: specification/verification/test integrity issue → return through appropriate change path
- Test that test failures prevent final success
- Document test-driven completion in completion criteria

### Risk 5: Architectural Redesign of Individual Skills

**Description**: Risk that implementing orchestration logic may lead to redesigning internal logic of individual SDD skills.

**Impact**: MEDIUM - Violates responsibility separation principle

**Mitigation**:
- Explicit requirement: "Do NOT redesign internal domain logic of individual SDD skills"
- Each skill owns its specific responsibilities
- Orchestrator only coordinates, does not rewrite
- Test that individual skills remain unchanged
- Review each skill's internal logic before implementing orchestration

### Risk 6: manage-roadmap Scope Creep

**Description**: Risk that manage-roadmap expands into post-approval execution lifecycle, duplicating manage-development responsibilities.

**Impact**: MEDIUM - Violates responsibility separation principle

**Mitigation**:
- Explicit requirement: "manage-roadmap focus on strategic responsibilities only"
- manage-roadmap owns: roadmap state, milestone planning, milestone creation, decomposition, documentation, readiness for development
- Once execution-ready: manage-roadmap → manage-development
- Document clear handoff contract
- Test that manage-roadmap does NOT handle execution

## Notes

### Positive Incentives

- **True Automation**: This enables fully autonomous implementation after approval
- **Human Freedom**: Humans freed from manual orchestration, can focus on decision-making
- **Error Reduction**: Automated orchestration reduces human error from missed or misordered steps
- **Efficiency**: Continuous execution without interruption
- **Consistency**: Orchestrator ensures consistent application of rules

### Negative Guardrails (Non-Negotiable)

1. **NO implementation before explicit human approval**
2. **NO hotfixes changing requirements silently**
3. **NO infinite repair loops**
4. **NO skip evaluation**
5. **NO skip tests**
6. **NO declare success solely because implementation finished**
7. **NO rewrite tests to hide implementation failures**
8. **NO automatically approve changed requirements**
9. **NO automatically start new milestones without existing framework support**
10. **NO redesign individual skills unnecessarily**
11. **NO remove approve-spec unless separately approved as architectural change**

### Design Principles

1. **Preserve Safety Boundaries**: Approval gate from M4 remains non-negotiable
2. **Autonomy Within Boundaries**: Framework can automate but must stay within safety rules
3. **Human Control Points**: Only human can override when rules are insufficient
4. **Evidence-Based Decisions**: Routing and escalation based on concrete evidence, not guesses
5. **Test-Driven Completion**: Tests pass is required for final success
6. **Loop Boundedness**: No infinite loops, ever
7. **Responsibility Separation**: Orchestrator owns sequencing, skills own domain logic

### Integration with Existing Work

- **M4 (Pre-implementation Orchestration Integrity)**: Provides approval gate, pipeline sequence enforcement, artifact validation, test readiness validation, resume/recovery
- **M5 (Post-approval Automation)**: Builds on M4 foundation, extends automation after approval
- **approve-spec Skill**: Preserved, unchanged, handles human approval decision
- **manage-development**: Becomes full lifecycle orchestrator (before: pre-implementation; after: full lifecycle)
- **manage-roadmap**: Remains strategic, handoff to manage-development for execution
- **Individual SDD Skills**: Unchanged, own domain-specific logic

### Test Strategy

The milestone MUST be tested through the real orchestrator, not just by reading skill instructions. Required test scenarios:

**A — Successful path**:
```
approval → implementation → evaluation PASS → review → final report
```

**B — Minor defect**:
```
approval → implementation → evaluation FAIL → hotfix → evaluation PASS → review
```

**C — Complex/unclear issue**:
```
evaluation FAIL → investigate → issue resolved without spec change → continue safely
```

**D — Specification change**:
```
evaluation FAIL → investigate → specification must change → verification regenerated → tests regenerated → readiness → human approval → implementation
```

**E — Repair loop limit**:
```
Repeated unsuccessful hotfixes → MAX_AUTO_REPAIR_CYCLES reached → STOP → REPORT → ASK HUMAN
```

**F — Test failure**:
```
Test fails → Prevents final success → Treated as real implementation failure
```

**G — Approval protection**:
```
No post-approval repair path can silently modify requirements and continue without re-approval
```

### Definition of Done

The milestone is complete when the post-approval lifecycle is demonstrably autonomous but remains bounded and safe:

```
APPROVED
    ↓
IMPLEMENT
    ↓
EVALUATE
    ↓
┌───────────────┐
│               │
PASS            FAIL
│               │
▼               ▼
REVIEW       CLASSIFY ISSUE
    │               │
    │         ┌─────┼─────┐
    │         │     │     │
    │       HOTFIX INVEST  HUMAN
    │         │     │
    │         ▼     ▼
    │      EVALUATE  SPEC CHANGE?
    │                │
    │             YES│
    │                ▼
    │          RETURN TO APPROVAL
    │
    ▼
FINAL REPORT
```

The system must:
- Automate routine post-approval execution
- Automatically evaluate results
- Automatically repair safe localized defects
- Automatically investigate complex issues where appropriate
- Stop after bounded repair attempts
- Return to human approval whenever requirements or architecture change
- Produce a final evidence-based review report
