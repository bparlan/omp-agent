## Objective

Fix the OMP AEF milestone namespace collision between meta-framework milestones and project-specific milestones by implementing project-scoped milestone directory structure, preventing state corruption when multiple projects use the same milestone IDs (e.g., AEF-M5 vs BARIA-M5).

### Milestone Complexity & Multi-Spec Plan

This is a followup specification to address a systemic architecture defect discovered after M5S1 implementation. The fix requires:
- **S1**: Update framework directory structure (prefix or subdirectory)
- **S2**: Update all milestone path resolution logic in framework skills
- **S3**: Update session audit and documentation generation

This specification focuses on **S1** (project-scoped structure).

## Functional Requirements

### FR-1: Project-Scoped Milestone Structure

**The framework MUST support multiple projects using the same milestone IDs without collision.**

**Required Structure Options** (framework must support both):

**Option A: Prefix-based Namespace** (recommended for simplicity):
- Format: `{PROJECT_PREFIX}-{MILESTONE_ID}`
- Directory structure: `milestones/{PROJECT_PREFIX}-{MILESTONE_ID}/`
- Examples: `milestones/AEF-M5/`, `milestones/BARIA-M5/`
- Prefixes: `AEF`, `BARIA`, or custom project identifiers from configuration

**Option B: Subdirectory-based Namespace** (recommended for clarity):
- Format: `milestones/{project_slug}/{MILESTONE_ID}`
- Directory structure: `milestones/{project_slug}/{MILESTONE_ID}/`
- Examples: `milestones/aef/M5/`, `milestones/baria/M5/`
- Slug normalization: lowercase, hyphens replaced with underscores
- Required: `milestones/{project_slug}/archive/`, `milestones/{project_slug}/TEMP/`

**Requirement**: Framework must implement one of the two options and detect collisions before creating milestone artifacts.

### FR-2: Project Configuration Integration

**The framework MUST read project-scoped configuration to determine milestone path.**

- Framework skills must read project configuration from `.omp/config.yml` or `.omp/{project_name}.yml`
- Configuration must include project identifier (e.g., `project_id: "AEF"`, `project_slug: "aef"`)
- Milestone path must be dynamically calculated: `get_milestone_path(milestone_id, project_scope)`
- If configuration is missing or invalid, fall back to meta-framework mode (Option A with default prefix)

### FR-3: Unique Milestone Validation

**The framework MUST prevent duplicate milestone IDs within a project scope.**

- Before creating new milestone artifacts, validate uniqueness: `validate_milestone_uniqueness(milestone_id, project_scope)`
- Detect if milestone directory already exists
- Prevent file overwriting: reject creation if `milestones/{scope}/{milestone_id}/` exists
- Return clear error message: "Milestone ID {milestone_id} already exists in project scope {scope}"

### FR-4: Framework Path Updates

**All framework skills that reference milestones must use dynamic path resolution.**

Skills requiring updates:
- `manage-development` (milestone path resolution)
- `session-audit` (namespace usage tracking)
- `generate-spec` (create milestone directory)
- `implement-specification` (locate milestone artifacts)
- `generate-verification` (locate milestone artifacts)
- `generate-tests` (locate milestone artifacts)
- `evaluate-implementation` (locate milestone artifacts)
- `review-implementation` (locate milestone artifacts)
- `generate-specification` (future spec creation)

Replace hardcoded `milestones/M{X}` with: `milestones/{scope}/{milestone_id}` or `milestones/{prefix}-{milestone_id}`

### FR-5: Session Audit Namespace Tracking

**The session-audit skill MUST include namespace usage in generated reports.**

- Audit reports must list all milestones in current project scope
- Detect namespace collisions across projects
- Generate namespace usage summary: "Project usage: AEF=5, BARIA=3, CUSTOM=2"
- Provide recommendations for project-scoping configuration

## Non-Functional Requirements

### NFR-1: Backward Compatibility

**The framework MUST support existing single-project workflows.**

- Existing `milestones/M{X}/` structure must remain functional during migration
- Support two migration strategies:
  - Prefix strategy: Rename `milestones/M5/` → `milestones/AEF-M5/`
  - Subdirectory strategy: Move `milestones/M5/` → `milestones/aef/M5/`
- Existing milestone artifacts must not be lost during migration
- Provide automatic migration script

### NFR-2: Migration Safety

**Migration MUST be reversible or require explicit user approval.**

- Framework must detect project scope before performing any file operations
- Display migration plan before execution:
  - "Migrating AEF-M5 from flat structure to project-scoped structure"
  - "This will move milestones/AEF-M5/ to milestones/aef/M5/"
- Require explicit user confirmation before migration
- Create backup of existing `milestones/` directory before migration

### NFR-3: Query Performance

**Namespace resolution MUST not significantly impact framework performance.**

- Milestone path lookup must be O(1) (hash map lookup)
- Project scope detection must be O(1) (read config file once)
- Unchanged: Milestone directory lookup uses existing file system operations

### NFR-4: Documentation Completeness

**All framework skills must document project-scoped structure.**

- `manage-development` SKILL.md must document path resolution logic
- Session audit reports must include namespace usage section
- Session audit reports must provide migration recommendations
- Code-search index must include project-scoped milestone paths

### NFR-5: Error Messaging

**Error messages MUST be clear about namespace collisions.**

Error message format:
```
ERROR: Milestone ID {milestone_id} already exists in project scope {scope}

Current structure:
  milestones/{scope}/{milestone_id}/

Conflict: Attempting to create duplicate artifacts

Resolution:
  1. Choose a unique milestone ID
  2. Use a different project scope
  3. Delete existing milestone artifacts (use with caution)
```

### Public Interfaces

1. **`get_milestone_path(milestone_id, project_scope)`**
   - Input: `milestone_id` (string, e.g., "M5"), `project_scope` (string, e.g., "aef")
   - Output: `path` (string, e.g., "milestones/aef/M5")
   - Behavior: Returns milestone directory path based on project scope

2. **`validate_milestone_uniqueness(milestone_id, project_scope)`**
   - Input: `milestone_id` (string), `project_scope` (string)
   - Output: `is_unique` (boolean), `error_message` (string or null)
   - Behavior: Returns True if milestone ID is unique in project scope, False with error message if collision detected

3. **`detect_project_scope()`**
   - Input: None
   - Output: `project_scope` (string, e.g., "aef") or `None` (if running in meta-framework mode)
   - Behavior: Reads project configuration and returns project scope, or None if not in a project

## Data Flow

### Milestone Path Resolution Flow

```
User Request → manage-development Skill
  ↓
  1. Read project configuration (.omp/config.yml)
  2. Detect project scope (e.g., "aef" or "BARIA")
  3. Calculate milestone path: get_milestone_path("M5", "aef")
  4. Result: "milestones/aef/M5/"
  ↓
5. Validate uniqueness: validate_milestone_uniqueness("M5", "aef")
  ↓
  6. Check if directory exists
  7. If collision → reject creation with error message
  8. If unique → proceed with milestone creation
```

### Namespace Collision Detection Flow

```
User creates milestone M5
  ↓
manage-development Skill
  ↓
1. Read project configuration (project_id: "BARIA")
  ↓
2. Get milestone path: milestones/BARIA-M5/
  ↓
3. Check if milestones/BARIA-M5/ exists
  ↓
  4. If exists → Collision detected
  5. Return error: "Milestone ID M5 already exists in project BARIA"
  ↓
6. If not exists → Proceed with milestone creation
```

### Session Audit Namespace Tracking Flow

```
Session Audit Skill
  ↓
1. Read session artifact (M{X}SA{Y}.md)
  2. Extract project identifier
  3. Scan milestones directory: find milestones/*/M{X}/*.md
  4. Group by project scope: AEF=5, BARIA=3, CUSTOM=2
  5. Detect collisions: AEF-M5 vs BARIA-M5
  6. Generate namespace usage section
  7. Output: "Project usage: AEF=5, BARIA=3, CUSTOM=2"
```

## Assumptions

1. **Project Configuration Format**: Project configuration is stored in `.omp/config.yml` or `.omp/{project_name}.yml` with `project_id` or `project_slug` field.

2. **Single Active Project**: The framework will be used for one project at a time (not multiple projects in the same workspace simultaneously).

3. **Milestone IDs Remain Constant**: Milestone IDs (M{X}) do not change across projects (e.g., M5 is M5 for both AEF and BARIA).

4. **Migration Timing**: Namespace fix will be applied before creating new milestones for BariaDAO project (not retroactively for existing AEF milestones).

5. **No Existing BariaDAO Milestones**: The BariaDAO project does not have existing milestones that would collide with AEF meta-framework (otherwise collision detection must also warn about retroactive collisions).

6. **Project Configuration is Authoritative**: Project identifier from configuration is the source of truth for namespace scope.

7. **Meta-Framework Mode Exists**: If project configuration is missing or invalid, framework falls back to meta-framework mode (AEF-M5 prefix).
