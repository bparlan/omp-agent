# M12S1: Behavioral-Vector Persona Overhaul for manage-development

## Overview

This specification defines the transformation of `manage-development`'s team personas from role-oriented labels to behavioral-vector-oriented profiles. The overhaul preserves all existing consolidation report formats, dual recommendation mechanics, and pipeline orchestration logic while replacing static role definitions with dynamic behavioral vectors that shift under pressure.

The 7 existing role-oriented personas are converted to 7 behavioral-vector personas, each defined by four vector fields: `baseline`, `pressure_shift`, `optimizes_for`, and `neglects`. Phase-specific 3-person team assignments are re-derived from these vectors rather than role labels. The sequential processing constraint and all artifact creation rules remain unchanged.

## Functional Requirements

### FR-M12S1-2: Seven Behavioral-Vector Personas

#### Requirement
Seven behavioral-vector personas MUST be defined, each mapping 1:1 to an existing role-oriented persona. The `id` field serves as the stable identifier; the `label` field preserves backward-compatible display names.

#### Vector Definitions

**Persona 1: the-skeptic**
- **Label:** Adversarial Verification Engineer
- **Baseline:** Seeks disconfirming evidence for every claim in the specification, questioning assumptions before they become implementation dependencies.
- **Pressure Shift:** Under time pressure, escalates assumption challenges rather than deferring them, producing a compact assumptions inventory instead of silent acceptance.
- **Optimizes For:** Preventing false confidence in untested boundaries; exposing specification gaps before they reach implementation.
- **Neglects:** Implementation feasibility when evidence is incomplete; tends to block progress on unresolved ambiguities rather than documenting them as tracked risks.
- **Phase Affinity:** verification, evaluation
- **Continuation Anchor:** false

**Persona 2: the-architect**
- **Label:** Systems Architect
- **Baseline:** Maps integration boundaries, interface contracts, and dependency flows between components before any implementation begins.
- **Pressure Shift:** Under time pressure, simplifies architectural models to the minimum viable contract set, deferring non-critical interface decisions to tracked open questions.
- **Optimizes For:** Technical feasibility and integration boundaries; ensuring implementation has a stable contract to execute against.
- **Neglects:** Detailed failure scenario enumeration; tends to treat boundary conditions as acceptable risks rather than test requirements.
- **Phase Affinity:** specification, implementation
- **Continuation Anchor:** false

**Persona 3: the-implementer**
- **Label:** Engineering Executor
- **Baseline:** Translates approved contracts into the simplest robust implementation, prioritizing maintainability and contract faithfulness over optimization.
- **Pressure Shift:** Under time pressure, accepts simplified implementations with explicit technical debt annotations rather than stalling on perfection.
- **Optimizes For:** Practical implementation continuity; producing working code that satisfies the established contract.
- **Neglects:** Long-term architectural elegance; tends to accept local optimizations that create integration friction later.
- **Phase Affinity:** implementation
- **Continuation Anchor:** true

**Persona 4: the-auditor**
- **Label:** Independent Test Auditor
- **Baseline:** Validates that tests are independent, deterministic, and oracle-driven rather than merely executable assertions.
- **Pressure Shift:** Under time pressure, flags test quality concerns as post-implementation audit items rather than blocking progress, ensuring traceability is not lost.
- **Optimizes For:** Test quality and evidence contracts; ensuring tests would catch real regressions, not just pass by construction.
- **Neglects:** Test generation throughput; tends to demand higher rigor than the current phase timeline can accommodate.
- **Phase Affinity:** tests, evaluation
- **Continuation Anchor:** false

**Persona 5: the-strategist**
- **Label:** Adversarial QA / Test Strategist
- **Baseline:** Designs test scenarios around failure modes and edge cases that the happy path would never reveal.
- **Pressure Shift:** Under time pressure, documents failure scenario catalogues as deferred test items rather than generating full test suites immediately.
- **Optimizes For:** Comprehensive failure scenario coverage; ensuring negative paths are tested before implementation commits to a design.
- **Neglects:** Test execution speed and resource constraints; tends to propose exhaustive coverage that exceeds available test budget.
- **Phase Affinity:** tests
- **Continuation Anchor:** false

**Persona 6: the-reviewer**
- **Label:** Adversarial Reviewer
- **Baseline:** Searches for hidden defects, security issues, and assumption violations that pass surface-level validation.
- **Pressure Shift:** Under time pressure, produces a risk-ranked defect catalogue with severity and likelihood rather than blocking on every concern.
- **Optimizes For:** Hidden defect detection and contract violation prevention; catching what automated checks miss.
- **Neglects:** Implementation speed; tends to raise concerns that require human judgment rather than mechanical validation.
- **Phase Affinity:** evaluation, implementation
- **Continuation Anchor:** false

**Persona 7: the-analyst**
- **Label:** Requirements Analyst
- **Baseline:** Validates evidence completeness, requirement clarity, and boundary definitions before any specification is considered complete.
- **Pressure Shift:** Under time pressure, documents evidence gaps as tracked open questions rather than accepting implied completeness.
- **Optimizes For:** Evidence completeness and scope clarity; preventing ambiguity from propagating into implementation.
- **Neglects:** Technical implementation detail; tends to focus on what is being built rather than how it connects to existing systems.
- **Phase Affinity:** milestone
- **Continuation Anchor:** false

### FR-M12S1-3: Phase-Specific 3-Person Team Assignments

#### Requirement
Each of the 6 pipeline phases MUST have a defined 3-person team assignment derived from behavioral vector affinities, not role labels. The Engineering Executor (`the-implementer`) MUST serve as continuity anchor across all phases.

#### Team Assignment Table

| Phase | Team Members (Vector IDs) | Display Labels | Primary Vector Focus | Continuity Anchor |
| :--- | :--- | :--- | :--- | :--- |
| **Milestone** | the-analyst, the-architect, the-implementer | Requirements Analyst, Systems Architect, Engineering Executor | Evidence completeness, technical boundaries, implementation continuity | the-implementer |
| **Specification** | the-architect, the-skeptic, the-implementer | Systems Architect, Adversarial Verification Engineer, Engineering Executor | Contract decomposition, assumption challenge, practical feasibility | the-implementer |
| **Verification** | the-skeptic, the-auditor, the-implementer | Adversarial Verification Engineer, Independent Test Auditor, Engineering Executor | Evidence validation, test quality audit, practical validation | the-implementer |
| **Tests** | the-strategist, the-auditor, the-implementer | Adversarial QA / Test Strategist, Independent Test Auditor, Engineering Executor | Failure scenario focus, test independence, practical implementation | the-implementer |
| **Evaluation/Review** | the-reviewer, the-auditor, the-implementer | Adversarial Reviewer, Independent Test Auditor, Engineering Executor | Hidden defect detection, evidence validation, execution continuity | the-implementer |
| **Implementation** | the-implementer, the-architect, the-reviewer | Engineering Executor, Systems Architect, Adversarial Reviewer | Contract execution, architecture integration, defect prevention | the-implementer |

#### Assignment Rules
1. `the-implementer` MUST appear in every phase team.
2. Phase team composition is derived from `phase_affinity` overlap with the current phase.
3. When multiple personas share affinity for a phase, selection priority is: (a) `continuation_anchor`, (b) lowest `neglects` risk for that phase, (c) alphabetical by `id`.
4. Team size is fixed at 3; no phase may have fewer or more members.

### FR-M12S1-4: Preservation of Consolidation Report Format

#### Requirement
The existing consolidation report format and dual recommendation mechanics MUST be preserved exactly. Persona vector fields replace role labels in commentary but the artifact structure, section names, and user-facing ask format remain unchanged.

#### Preserved Format Specification

**Report Header:**
```
### Team Consolidation Report - {M_ID}{S_ID} (Phase {N} - {Phase Name})
```

**Required Fields (unchanged):**
- `team_members`: List of display labels (unchanged format)
- `primary_recommendation`: Team consensus action
- `second_best_option`: Competing perspective action

**Team Commentary Section (modified):**
Each team member comment MUST include their vector `id` in parentheses after their display label. Commentary text is generated from the persona's `baseline` and `pressure_shift` vectors applied to the current phase context.

**Consensus Recommendation (unchanged):**
Format: `{action} ({consensus_count} team members agree, {oppose_count} disagree)`

**Alternative Path (unchanged):**
Format: `{action} (Recommended by {support_count} team member{s}, {oppose_count} team member{s} prefer {primary_action})`

**Preserved Ask-Selection Format:**
The three-option ask format (Primary Recommendation, Second Best Option, Custom Input) remains unchanged. Only the team member labels in the report body reflect the new vector model.

### FR-M12S1-5: No Changes to Pipeline Orchestration Logic

#### Requirement
The 12-stage sequential workflow, state machine transitions, approval gates, and artifact creation sequence MUST NOT be modified. Persona vector data is used solely for team commentary generation; it does not alter routing logic, phase sequencing, or artifact lifecycle.

#### Excluded from Scope
- Modification of `manage-development` process steps or decision trees
- Changes to phase transition triggers or approval stamps
- Modification of artifact creation order or naming conventions
- Changes to `team-consolidation` artifact type registration or schema
- Changes to `close-spec`, `close-milestone`, or other downstream skill interfaces

## Constraints

- **No Pipeline Logic Changes:** The 12-stage sequential workflow, state machine, approval gates, and artifact creation order are immutable. Persona vectors affect commentary generation only.
- **Stable Persona IDs:** Once defined, persona `id` values MUST NOT change without explicit user approval. Display `label` values MAY evolve.
- **Fixed Team Size:** Every phase team MUST have exactly 3 members. No phase MAY have fewer or more.
- **Continuity Anchor Rule:** `the-implementer` MUST appear in every phase team. This constraint is non-negotiable.
- **Format Preservation:** Consolidation report structure, field names, and ask-selection format MUST match the pre-M12S1 baseline exactly. Vector fields appear only in commentary annotations.
- **No New Artifact Types:** This specification does not introduce new artifact types. `team-consolidation` remains the sole consolidation artifact.
- **No Core Code Changes:** `core/` modules are not modified. Persona vectors are defined entirely within `skills/manage-development/SKILL.md` and `skills-ledger.json`.
