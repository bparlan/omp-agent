## Objective

Establish a non-destructive indexing and classification mechanism for the pre-M10 legacy corpus (M1-M9) that maintains reference traceability while protecting historical file states.

### Milestone Complexity & Multi-Spec Plan

M7 is broken into three sequential specifications:

- **M7S1 (SPEC-001)** — Complete. Artifact Identity & Metadata Contract. Established canonical machine identifiers, YAML frontmatter mandate, and `validate_metadata.py`.
- **M7S2 (SPEC-002)** — Complete. Artifact Resolution & Canonical Storage. Defined the directory structure contract and implemented `resolve_artifact.py` with 3-tier priority resolution.
- **M7S3 (SPEC-003)** — Current. Legacy Compatibility & Transition. Implements the legacy indexing mechanism, classification fallback logic, and integration hooks into the resolution engine.

## Functional Requirements

- **FR-11 (Legacy Manifest Baseline)**: The system MUST provide a utility (`bin/legacy_indexer.py`) that maps every pre-M10 file path to its SHA-256 checksum and records the mapping in `milestones/M7/legacy_manifest.txt` before any transition execution runs. Each manifest entry MUST be a single line formatted as `<SHA-256> <relative-path>`.

- **FR-12 (6-Tier Classification Priority)**: The legacy indexer MUST implement a strict 6-tier classification fallback for determining the artifact type of each pre-M10 file:
  1. **Existing frontmatter metadata** — Parse YAML frontmatter `type` or `id` fields.
  2. **Directory structure** — Infer type from the subdirectory name (e.g., `specifications/`, `verifications/`).
  3. **Explicit top-level Markdown headers** — Match `# Specification` or `# Investigation` headings.
  4. **Legacy filename naming conventions** — Match patterns:
     - `M{X}S{Y}.md` → specification
     - `M{X}S{Y}V.md` → verification
     - `M{X}S{Y}T{Z}.md` → test plan
     - `M{X}S{Y}C.md` → completion report
     - `M{X}S{Y}E.md` → evaluation report
     - `M{X}S{Y}R.md` → review report
     - `M{X}S{Y}I{Z}.md` → investigation
  5. **Controlled custom filename pattern mapping** — Apply an external mapping file or configuration for non-standard patterns.
  6. **Human review** — Mark as `AMBIGUOUS_LEGACY_ARTIFACT` for manual resolution.

- **FR-13 (Zero-Touch Invariance)**: The indexing engine is strictly read-only. It is forbidden from renaming, moving, or writing frontmatter to any M1-M9 file. All normalization mappings MUST be recorded solely in an external legacy index or memory cache — never in the physical artifact files themselves.

- **FR-14 (Safe Fallback)**: Any file that cannot be deterministically classified with high confidence through tiers 1-5 MUST resolve specifically to the category `AMBIGUOUS_LEGACY_ARTIFACT` and be flagged for manual human review, rather than guessing a category.

- **FR-15 (Coexistence)**: The artifact resolution utility (`resolve_artifact.py`) MUST integrate queries against the legacy index so that legacy files are discoverable as valid targets by newer skills. When a legacy ID (e.g., `M7S1`) is queried, the resolution engine MUST consult the legacy manifest as a fallback tier equivalent to the existing Tier 3 (filename heuristics).

## Non-Functional Requirements

- **NFR-5 (Immutable Integrity)**: Post-execution verification MUST mechanically prove that the SHA-256 checksums of all real M1-M9 files match the legacy baseline manifest exactly (no silent writes). A verification command or script MUST recompute checksums and diff against `legacy_manifest.txt`, reporting any mismatch.

- **NFR-6 (Resolution Performance)**: Consulting the legacy index MUST NOT add more than 1 second of latency to the artifact resolution engine for a milestone directory with up to 100 indexed legacy files.

## Data Flow

1. **Indexing phase**: A human or CI process invokes `legacy_indexer.py`. The script walks `milestones/` for M1-M9 directories.
2. For each file found, the 6-tier classification fallback determines the artifact type.
3. Each successfully classified file is recorded as `<SHA-256> <relative-path>` in the manifest.
4. Unclassifiable files are written to stderr with category `AMBIGUOUS_LEGACY_ARTIFACT` and may optionally be listed in a separate section at the bottom of the manifest.
5. **Resolution phase**: A user or agent invokes `resolve_artifact.py` with a legacy ID (e.g., `M5S1`).
6. Tiers 1-2 execute as defined in SPEC-002. If unresolved, Tier 3 (legacy filename heuristics) runs.
7. If Tier 3 fails, `resolve_artifact.py` reads `legacy_manifest.txt` and cross-references the queried legacy ID against the indexed entries. A match returns the resolved path.
8. **Integrity verification**: A post-execution step recomputes checksums for all M1-M9 files in the manifest and diffs against `legacy_manifest.txt`. Any mismatch is a critical failure.
