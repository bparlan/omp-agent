Integrate the canonical artifact architecture established by M9 into the existing AEF/OMP development infrastructure, ensuring that artifact-producing and artifact-consuming skills operate consistently with the canonical identity, type, metadata, lineage, storage, and legacy-compatibility rules. This specification also establishes project-level workspace isolation so that AEF can be used for both framework development (AEF itself) and independent application projects without leaking AEF-specific documentation or development artifacts.

### Milestone Complexity & Multi-Spec Plan

This is a comprehensive integration specification (M9S1) rather than a split into multiple sequential specifications. All scope items are tightly coupled: artifact-system adoption, resolution, creation, validation, configuration, mode-aware bootstrapping, agent guidance, and documentation synchronization form an integrated system where changes to one component affect others. Splitting this into separate specs would increase coupling, reduce clarity, and obscure the integration pattern that must be established uniformly across all skills.

The milestone defines a unified artifact-system integration contract that applies to all affected skills simultaneously. Subsequent followup specifications (if any) would address specific enhancement areas (e.g., additional project modes, extended registry capabilities, advanced validation rules), but M9S1 establishes the core integration pattern that serves as the foundation for all future work.

## Functional Requirements

### FR-1 — Canonical Artifact Contract Adoption

All affected artifact-producing and artifact-consuming skills must adopt the M9 canonical artifact model, rejecting independent schemas and decisions about artifact identity, type, metadata, lineage, storage, and legacy handling.

**Acceptance Criteria:**
- No affected skill independently defines a competing canonical artifact schema or metadata contract.
- Artifact type, identity, metadata, lineage, and storage decisions originate exclusively from the canonical artifact system (Artifact Registry, Resolver, Validator).
- Skills consume canonical artifact metadata rather than reconstructing semantics from filenames or paths.
- Skills maintain no skill-specific mandatory-field lists unless explicitly registered in the Artifact Registry.



### FR-2 — Canonical Artifact Resolution

Affected skills must resolve artifacts through the canonical artifact-resolution mechanism defined by M9, not through hardcoded assumptions or path patterns.

**Acceptance Criteria:**
- Skills do not hardcode milestone-specific artifact paths (e.g., `milestones/M9/M9S1.md`) as their primary resolution mechanism.
- Artifact resolution works when canonical artifacts are stored according to the M9 storage model regardless of location.
- Resolver failures are explicit and actionable (return structured error with artifact identity, attempted path, and failure reason).
- Ambiguous resolution does not silently select an arbitrary artifact (must surface ambiguity for human/agent intervention).

**Behavioral Specification:**
```
Skill
  ↓
Request Artifact (identity/type/context)
  ↓
Canonical Resolver (loads Registry + Validator + Storage rules)
  ↓
Return Artifact Identity/Type/Metadata
  ↓
Resolve Physical Path (via canonical storage model)
  ↓
Return Physical Path OR Error
  ↓
Skill reads/writes artifact via resolved path
```

**Ambiguous Resolution Behavior:**
```
Resolver receives ambiguous artifact request (multiple artifacts match criteria)
  ↓
Determine match criteria (identity, type, context, namespace, priority)
  ↓
If exactly one artifact matches:
  ↓
  Return artifact identity and resolved path
Else if multiple artifacts match:
  ↓
  Surface ambiguity with structured error:
    - artifact_id: list of matching artifact IDs
    - match_criteria: details about why each matched
    - user_instruction: guidance for resolving ambiguity (e.g., provide more specific identity, adjust type/context)
  ↓
  Do NOT automatically select or load an arbitrary artifact
  ↓
Skill receives ambiguous resolution error
  ↓
Either:
  - Provide more specific artifact identity/context to resolve
  - Or abort with explicit error message guiding user
```

**Error Response Format:**
```
AmbiguousResolutionError:
  error_type: "ambiguous_resolution"
  matching_artifacts:
    - artifact_id: "<id1>"
      type: "<type1>"
      match_reason: "<reason>"
    - artifact_id: "<id2>"
      type: "<type2>"
      match_reason: "<reason>"
  match_criteria:
    provided_identity: "<provided>"
    provided_type: "<provided>"
    provided_context: "<provided>"
  user_instruction: "Please provide more specific artifact identity or context. Available options: <id1>, <id2>, ... or adjust type/context criteria."
```

### FR-3 — Canonical Artifact Creation

All affected artifact-producing skills must create artifacts conforming to the canonical metadata contract, following a strict 7-step creation protocol.

**7-Step Creation Protocol:**
1. determine the artifact type (from Artifact Registry or explicit declaration).
2. assign or request canonical artifact identity (from Registry or generator).
3. generate required metadata (per Artifact Registry schema).
4. write canonical frontmatter (type, identity, metadata fields).
5. place the artifact in its canonical storage location (per Registry storage rules).
6. validate the resulting artifact (via canonical validator).
7. report the created artifact identity and resolved path (or error if validation fails).

**Acceptance Criteria:**
Every successful artifact creation results in:
- canonical identity present in metadata;
- canonical type present in frontmatter and registry;
- required metadata fields populated and valid;
- valid frontmatter with correct YAML syntax and structure;
- canonical storage location (no fallback to arbitrary paths);
- successful metadata validation (all contract rules satisfied).



### FR-4 — Validation Before Completion

Artifact-producing skills must validate their generated output before reporting successful completion, rejecting partial or invalid artifacts as failures.

**Acceptance Criteria:**
- Invalid artifacts (validation failures) cause the producing skill to fail explicitly with error output.
- Partial artifact creation (e.g., missing frontmatter, invalid YAML) is not reported as successful.
- Validation is performed through the canonical validator (not custom checks per skill).
- Skills do not silently bypass validation (no `--skip-validation` flag unless it disables entire skill, which is considered out-of-scope for this milestone).

**Validation Gate Behavior:**
```
Skill executes artifact creation steps 1-7
  ↓
Before reporting success, validate artifact via canonical validator
  ↓
Validation result: PASS
  ↓
Report success with artifact identity and resolved path
  ↓
Validation result: FAIL
  ↓
Report error (validation details) and stop skill execution
  ↓
Do NOT report successful creation
```



### FR-5 — Project-Scoped Configuration

`bootstrap-project` must create or update project configuration using the canonical `.omp/config.yml` model, treating configuration itself as a canonical artifact where applicable.

**Acceptance Criteria:**
A bootstrapped project has:
- `.omp/config.yml` exists in project root;
- Configuration contains valid project configuration (project_id, project_slug, mode fields as specified in Registry schema);
- Configuration itself is treated according to canonical artifact/configuration rules where applicable (validation, lineage, storage).

**Supported Configuration Fields (per Registry schema, to be defined in M9S1 or extended later):**
- `project_id`: Unique project identifier (string, required).
- `project_slug`: Human-readable project identifier (string, required).
- `mode`: Development mode (framework | application, required).
- Optional fields as defined by Registry schema extensions.



### FR-6 — Mode-Aware Bootstrap

`bootstrap-project` must distinguish between framework mode and application mode, adjusting generated artifacts and documentation accordingly.

**Framework Mode Acceptance Criteria:**
- Preserves framework-oriented initialization behavior where appropriate (e.g., generating AEF framework documentation where explicitly required by specification).
- May generate AEF-specific architectural documents (FRAMEWORK.md, PLAYBOOK.md, DATA.md) only when explicitly required by the specification or project configuration.

**Application Mode Acceptance Criteria:**
- Does NOT generate irrelevant AEF-internal documentation by default (e.g., FRAMEWORK.md, PLAYBOOK.md, DATA.md unless explicitly required).
- Creates project-appropriate agent guidance (see FR-7).
- Preserves project-specific architecture and documentation conventions (no overwriting project conventions with AEF defaults).
- Establishes the canonical artifact infrastructure required by AEF (Artifact Registry, Resolver, Validator integration) without requiring project to adopt AEF-specific development workflows by default.

**Mode Selection Behavior:**
```
bootstrap-project receives project configuration
  ↓
If mode == 'framework':
  ↓
  Generate framework-specific artifacts and documentation where explicitly required
  ↓
  Install AEF agent guidance for framework development
  ↓
Else if mode == 'application':
  ↓
  Generate project-appropriate agent guidance only
  ↓
  Do NOT generate AEF-internal framework documentation by default
  ↓
  Preserve project architecture and conventions
  ↓
  Establish minimal AEF infrastructure (config + canonical components)
```



### FR-7 — Application-Specific Agent Guidance

For application-mode projects, `bootstrap-project` must generate or install project-local agent guidance appropriate to the detected or declared technology stack, using a parameterized approach rather than hardcoded technology stacks.

**Acceptance Criteria:**
- Bootstrap generates or installs project-local agent guidance appropriate to detected/declared technology stack (e.g., Tailwind/DaisyUI guardrails for web apps).
- Technology-specific rules are parameterized (not hardcoded in universal bootstrap process).
- The bootstrap architecture supports: Project Mode + Project Technology/Stack → Appropriate Agent Guidance.
- The system does NOT assume all application projects use a single technology stack (e.g., Tailwind/DaisyUI).

**Parameterized Guidance Model:**
```
bootstrap-project detects/declares technology stack (e.g., 'tailwind-daisyui')
  ↓
Determine appropriate agent guidance for stack (from parameter library or project configuration)
  ↓
Generate or install project-local guidance file (e.g., .agent/guidance/tailwind-daisyui.md)
  ↓
Guidance file contains stack-specific guardrails and conventions
  ↓
Subsequent AEF skills use this guidance file as constraint
```

**Example Guidance (parameterized, not hardcoded):**
```
Do not modify, reorder, or remove layout or utility classes unless the active specification explicitly requires a visual or structural change.
```

This example is part of a parameter library, not embedded in universal bootstrap logic.



### FR-8 — Documentation Synchronisation

`sync-documentation` must operate within the active project's workspace boundary, resolving documentation artifacts through the canonical artifact system rather than assuming universal project structures.

**Acceptance Criteria:**
- `sync-documentation` resolves documentation artifacts through canonical resolution (not hardcoded paths).
- Skill distinguishes between AEF framework documentation (if in AEF project) and project documentation (if in application project).
- Skill does not inject AEF-specific documents into an application project merely because the skill itself was developed inside AEF.
- Documentation synchronization respects the project's configured mode (framework vs application) and canonical artifact architecture.

**Workspace Boundary Behavior:**
```
sync-documentation invoked
  ↓
Determine active project (from .omp/config.yml or context)
  ↓
Resolve project boundary (workspace root, allowed artifacts)
  ↓
Resolve documentation artifacts via canonical resolution
  ↓
If project is AEF framework:
  ↓
  Affect AEF framework documentation (FRAMEWORK.md, PLAYBOOK.md, DATA.md, SKILLS.md, AGENTS.md)
  ↓
Else if project is application:
  ↓
  Affect only project documentation (not AEF-specific docs)
  ↓
  Respect project conventions and architecture
```



### FR-9 — Milestone Artifact Integration

Milestone creation must produce canonical milestone artifacts using the M9 artifact contract, rejecting legacy filename-only documents.

**Acceptance Criteria:**
- Newly created milestones have valid canonical frontmatter (type, identity, metadata).
- Newly created milestones have canonical identity (not filename-derived).
- Newly created milestones have `type: milestone` in frontmatter.
- Newly created milestones are stored according to canonical storage rules (Registry + Resolver).
- Newly created milestones pass metadata validation before creation is reported successful.

**Creation Protocol (Milestone-Specific):**
```
milestone skill invoked
  ↓
Prompt user for milestone details (title, description, goals, success criteria)
  ↓
Generate canonical identity (Registry assignment or user-provided)
  ↓
Create milestone document with canonical frontmatter (type: milestone)
  ↓
Generate required metadata (goals, success criteria, status, derived_from, etc.)
  ↓
Write to canonical storage location (Registry-specified path)
  ↓
Validate milestone artifact via canonical validator
  ↓
If validation fails:
  ↓
  Report error with validation details
  ↓
  Do NOT report successful creation
Else if validation passes:
  ↓
  Report successful creation with artifact identity and resolved path
```



### FR-10 — Pipeline Traceability

The specification → verification → test → implementation pipeline must use explicit canonical artifact relationships, not filename-based inference.

**Acceptance Criteria:**
- The system can establish relationships: `specification` → `verification` → `test` → `implementation` without relying exclusively on filename conventions.
- Relationships (`derived_from`, `verifies`, `tests`, `implements`, `evaluates`, `reviews`) use the canonical relationship model defined by M9 (relationship edges stored in metadata, not inferred from directory structure).
- Each pipeline stage consumes the canonical artifact identity and metadata of the previous stage (identity passed explicitly, not inferred from filename patterns).

**Relationship Model (Canonical):**
```
Specification
  metadata:
    derived_from: ['M9']
    artifact_type: specification

Verification Protocol
  metadata:
    verifies: '<SPECIFICATION_ID>'
    artifact_type: verification

Test Plan
  metadata:
    tests: '<VERIFICATION_PROTOCOL_ID>'
    artifact_type: test_plan

Implementation
  metadata:
    implements: '<SPECIFICATION_ID>'
    artifact_type: implementation

Evaluation
  metadata:
    evaluates: '<IMPLEMENTATION_ID>'
    artifact_type: evaluation

Review
  metadata:
    reviews: '<EVALUATION_ID>'
    artifact_type: review
```



### FR-11 — Legacy Compatibility

Existing legacy artifacts (M1-M9) must remain readable according to M9's legacy compatibility rules without mass-migration.

**Acceptance Criteria:**
- Existing M1-M9 legacy artifacts are not mass-migrated automatically (no silent rewriting or reformatting).
- Existing artifacts remain discoverable through the canonical resolution process where supported (e.g., Resolver can locate legacy artifacts by pattern matching or metadata heuristics).
- New artifacts use canonical rules (not a mix of canonical and legacy).
- Legacy artifacts and canonical artifacts can coexist safely (no naming conflicts, no metadata collisions).

**Legacy Compatibility Strategy:**
- Resolver supports legacy artifact detection via pattern matching (e.g., `milestones/M{X}/{artifact}.md`) with warning logs that legacy artifacts are being used.
- Validator marks legacy artifacts as `legacy: true` in metadata and flags them for future migration but does not block usage.
- No automated mass-migration task in M9S1 (explicitly out of scope; future milestone may add migration tooling).



### FR-12 — Generated Test Reliability

The verification/test generation pipeline must generate tests grounded in the current canonical specification and verification artifacts, not hallucinated or guessed requirements.

**Acceptance Criteria:**
Generated tests:
- Reference the correct source specification (via canonical identity in metadata, not filename patterns).
- Reference the correct verification protocol (via canonical identity, not filename patterns).
- Test stated requirements from the specification, not invented or extrapolated requirements.
- Establish a valid initial failure path where applicable (fail-fast on missing dependencies, invalid inputs, or unresolved prerequisites).
- Do NOT validate documentation claims that are absent from the canonical specification.
- Do NOT become specification validators accidentally (tests verify implementation behavior, not specification text correctness).
- Are executable in an isolated fixture environment (no external dependencies, clean workspace).
- Are persisted as canonical test artifacts (valid frontmatter, type: test_plan or test_script).

**Generator Guardrails:**
- Generator reads specification and verification protocol via canonical resolver (not filesystem patterns).
- Generator extracts functional requirements from specification metadata (not by parsing text).
- Generator generates tests that reference requirements by canonical ID (not by descriptive text).
- Generator validates test assertions against specification requirements (exists, not inventing new requirements).



### FR-13 — Artifact-Type Consistency

All pipeline stages must use canonical artifact types, ensuring machine-readable type identification is explicit in metadata, not inferred from filenames.

**Acceptance Criteria:**
- The system does not produce ambiguous artifacts where semantic meaning depends only on filename conventions (e.g., `M9S4.md` could be anything).
- The filename may remain human-readable for human interaction.
- The artifact's machine-readable type and identity must be explicit in canonical metadata (frontmatter fields, Registry entries).
- All pipeline stages (milestone creation, specification generation, verification protocol, test design, implementation, evaluation, review) produce artifacts with valid canonical type declarations.

**Type Declaration Model:**
```
Artifact frontmatter:
  type: specification  # explicit, not inferred
  artifact_id: SPEC-M9S1  # explicit identity
  version: 1.0
  milestone_id: M9

Registry entry:
  type: specification
  artifact_id: SPEC-M9S1
  version: 1.0
  storage_location: milestones/M9/M9S1.md
```

Filename conventions are supported for human convenience (e.g., `M9S1.md`) but are not the source of truth.



## Non-Functional Requirements

### NFR-1 — Skill Compatibility

All 16+ affected skills must maintain backward compatibility with existing workflows where possible, introducing canonical integration as an enhancement, not a breaking change.

### NFR-2 — Error Clarity

All canonical integration failures must surface actionable error messages that include:
- Artifact identity (if resolution or creation failed)
- Expected vs actual state (if validation failed)
- Recommended next steps (if guidance needed)

### NFR-3 — Performance

Canonical resolution and validation must not introduce noticeable performance degradation for normal workflow operations (target: < 100ms for artifact resolution in typical cases).

### NFR-4 — Extensibility

The canonical artifact model must support future extensions (additional artifact types, modes, validation rules) without requiring rewrites of existing skills or migration of all existing artifacts.

### NFR-5 — Observability

Skills must log canonical integration activities (resolution attempts, validation results, mode selections) for debugging and auditing, but must not generate excessive logging in production use.

## Data Flow

### Artifact Creation Flow
```
Skill determines artifact type (from Registry or declaration)
  ↓
Skill assigns canonical identity (Registry or explicit)
  ↓
Skill generates required metadata (per Registry schema)
  ↓
Skill writes canonical frontmatter (type, identity, metadata)
  ↓
Skill places artifact in canonical storage location (Registry-specified)
  ↓
Skill validates artifact via canonical Validator
  ↓
If validation fails: Skill fails, reports error, does NOT report success
Else if validation passes: Skill reports success with artifact identity and resolved path
```

### Artifact Resolution Flow
```
Skill requests artifact (type, identity, context)
  ↓
Skill invokes canonical Resolver
  ↓
Resolver loads Registry and Validator
  ↓
Resolver loads type definition and storage rules
  ↓
Resolver resolves physical path (per storage rules, legacy fallback)
  ↓
Resolver loads artifact metadata
  ↓
Resolver validates artifact via Validator
  ↓
If resolution fails: Resolver returns error with details (identity, attempted path, reason)
Else if resolution succeeds: Resolver returns artifact identity, type, metadata, physical path
  ↓
Skill reads/writes artifact via resolved path
```

### Mode-Aware Bootstrap Flow
```
bootstrap-project receives project mode (framework/application)
  ↓
Create .omp/config.yml with canonical fields (project_id, project_slug, mode)
  ↓
If mode == 'framework':
  ↓
  Generate framework-specific artifacts and documentation where explicitly required
  ↓
  Install AEF agent guidance for framework development
Else if mode == 'application':
  ↓
  Detect or declare technology stack (from config or CLI args)
  ↓
  Generate project-appropriate agent guidance (parameterized, not hardcoded)
  ↓
  Do NOT generate AEF-internal framework documentation by default
  ↓
  Preserve project architecture and conventions
  ↓
  Establish minimal AEF infrastructure (config + canonical components)
```

## Assumptions

1. **Artifact System Exists**: The canonical artifact system (Registry, Resolver, Validator) either exists from prior work or is implemented in this specification. If the components do not yet exist, this specification defines the interface contracts they must provide.

2. **Project Configuration is Start**: Each project has or will have a `.omp/config.yml` file that defines project identity, slug, and mode. If the file does not exist, `bootstrap-project` creates it with minimal required fields.

3. **Skill Inventory is Known**: The milestone lists 16+ affected skills. If additional skills are identified during implementation that create or consume canonical artifacts, they must be updated to maintain consistency.

4. **Technology Stack is Declared or Detectable**: Application-mode projects must declare or allow detection of their technology stack (e.g., `--stack tailwind-daisyui`, or auto-detection via config). If stack is unknown, bootstrap uses generic project guidance.

5. **Legacy Artifacts Are Discoverable**: Legacy artifacts (M1-M9) are located in standard milestone directories and can be discovered by the Resolver via pattern matching or manual lookups. If legacy artifacts are in non-standard locations, Resolver falls back to pattern matching with warnings.

6. **Validator is Strict but Graceful**: Validator enforces all contract rules but does not block usage of legacy artifacts (flags them as `legacy: true`). Validator does not allow mixed canonical/legacy artifacts in same workspace (ensures clear boundaries).

7. **Mode Selection is Explicit**: Project mode (framework vs application) is explicitly declared during project creation or via configuration. Bootstrap does not auto-detect mode based on project content (to avoid ambiguity and maintain clarity).

8. **Agent Guidance is External**: Project-specific agent guidance is stored in external files (e.g., `.agent/guidance/` directory or inline in config) rather than embedded in bootstrap code. This supports parameterization and future extensibility.

9. **Documentation Scope is Configurable**: Documentation synchronization respects project configuration and mode. Framework projects get AEF framework documentation; application projects get project documentation only.

10. **Pipeline Relationships are Metadata-Driven**: Artifact relationships (derived_from, verifies, tests, implements, evaluates, reviews) are stored in metadata, not inferred from directory structure or filename patterns. This ensures traceability and consistency.
