## Goal

Establish a minimal, stable AEF artifact architecture and integrate a unified, single-mode health tracking and gatekeeper system (`healthcenter`) that manages skills, maintains a skill health ledger via canonical artifact creation, and provides safe auto-remediation.

---

## Motivation

The prior AEF infrastructure had two separate, half-implemented health systems (`healthcheck` and `health-monitoring`), duplicate logic, and no unified relationship tracking within the AEF artifact system. Additionally, the original M9 proposal was burdened with a complex dual-mode bootstrapping architecture (Framework vs. Application) that added unnecessary maintenance overhead.

By pivoting to a single-mode architecture and replacing legacy health scripts with a streamlined `healthcenter` skill, we establish a robust, minimal, and predictable development environment. The `healthcenter` acts as a gate and ledger, validating skills, storing canonical check outcomes, linking them via the artifact registry, and automatically repairing trivial formatting or version suffix issues without human intervention.

## Scope

### 1. Core Artifact Infrastructure (M9S1)
- **Artifact Registry**: Implement a centralized system for registering, retrieving, and validating canonical artifact types and storing relationships.
- **Artifact Resolver**: Provide a unified, deterministic mechanism to locate artifacts across milestones and specs, replacing hardcoded path logic in AEF skills.
- **Artifact Metadata Validator**: Establish a single authority for frontmatter parsing, metadata validation, and format enforcement.
- **Canonical Type Schema**: Support essential artifact type schemas (such as `milestone`, `specification`, `verification`, `test`, `completion`, `evaluation`, `review`, `closure`, and `health-check`).

### 2. Standard Project Configuration (M9S2)
- **Minimal `.omp/config.yml`**: Define and validate a simple YAML project configuration containing only three required fields: `project_id`, `project_slug`, and `version`.
- **Validation Rules**: `core/validation.py` must validate this file during bootstrap/init stages. No mode-specific or stack-specific fields are required.

### 3. Healthcenter Skill Integration (M9S3)
- **Unified Skill**: Replace `healthcheck` and `health-monitoring` with a single Python-based skill named `healthcenter` inside `skills/healthcenter/`.
- **Skill Discovery**: Automatically scan the `skills/` directory to discover and parse active skills.
- **Comprehensive Validation**: Verify every discovered skill's `SKILL.md` for:
  - Correct YAML frontmatter delimiters (`---`).
  - Required fields: `name`, `version`, `description`, `tools`, `user-invocable`.
  - Version stability via the required `-stable` suffix (e.g., `1.0.0-stable`).
  - Integrity requirements: Unix LF line endings, no NUL bytes, valid YAML parsing.
  - AEF Integration rules: ensure standard tool lists (e.g., `read`, `write`, `edit`) are specified.
- **Canonical Health-Check Artifacts**:
  - Every validation run generates a canonical `health-check` artifact (e.g., `milestones/M9/M9-health-check-<skill_name>.md`).
  - The artifact MUST contain a valid YAML frontmatter conforming to the registered `health-check` schema.
  - It must document health status (`healthy`, `needs_review`, `error`), score, timestamp, and a list of identified issues.
- **Skill Health Ledger**:
  - The `healthcenter` skill registers health check outcomes as relationships (`evaluates`, `derived_from`) in the AEF Artifact Registry.
  - This establishes an immutable record of skill health tied directly to the skill's artifact identity.
- **Safe Auto-Fix System**:
  - Enable automatic remediation for trivial compliance errors when requested:
    - Adding `-stable` suffix to version fields.
    - Converting CRLF to Unix LF line endings.
    - Fixing standard frontmatter delimiters.
    - Normalizing standard field names.
- **Actionable Insights & Recommendations**:
  - For complex or syntactic issues that cannot be safely auto-fixed, generate detailed, structured, non-destructive recommendations.
- **CLI Commands / Triggers**:
  - Manual trigger execution only:
    - Validate single skill: `healthcenter --skill <skill_name>`
    - Validate all discovered skills: `healthcenter --all`
    - Apply auto-fixes: include `--fix` flag.

## Out of Scope

- **No Watch Mode or Daemons**: The system must not run in the background, monitor file changes automatically, or introduce continuous-watching loops.
- **No Trend or Historical Reporting**: `healthcenter` only tracks the immediate/current status of skill health via the artifact ledger. Historical trajectory/trend logging is excluded.
- **No Complex Skill Rewriting**: Automatic modification of a skill's behavioral instructions, structural code files, or prompts (such as those in `docs/solutions/Broader_System_Awareness.md`) is excluded. Repairs are strictly limited to formatting and metadata.
- **No Dual-Mode Bootstrap Routing**: The system does not support "Application Mode" vs. "Framework Mode". AEF is a single-mode standard.
- **No Non-Local External Network Dependencies**: Health checks are completely localized to the project workspace.

## Success Criteria

- [ ] Discovered skills in `skills/` directory are successfully parsed by `healthcenter` and recorded.
- [ ] Running `skills/healthcenter/healthcenter.py --skill <skill_name>` produces a valid `health-check` artifact under the milestone/specification directory structure.
- [ ] The generated `health-check` artifact contains a YAML frontmatter parsed successfully by `core/artifacts/metadata.py`.
- [ ] Running `skills/healthcenter/healthcenter.py --all` processes all discovered skills in batch, creating a corresponding `health-check` artifact for each.
- [ ] Relationship queries on the artifact registry via `get_relationships()` successfully return the link between a skill and its corresponding `health-check` artifact.
- [ ] Providing the `--fix` flag to `healthcenter` successfully appends `-stable` to non-compliant versions and rewrites CRLF to LF in `SKILL.md` files.
- [ ] Running `healthcenter` without the `--fix` flag when errors exist leaves files unchanged but outputs detailed recommendations in the `health-check` artifact's body.
- [ ] Legacy skills directories `skills/healthcheck/` and `skills/health-monitoring/` are completely removed from the filesystem after `healthcenter` implementation.
- [ ] Project configuration `.omp/config.yml` exists, conforms to the minimal schema, and is successfully validated by `core/validation.py`.

## Risks

- **Accidental Skill File Corruption**: Running `--fix` could corrupt a `SKILL.md` if the frontmatter parser has bugs.
  - *Mitigation*: Ensure the parser uses extremely conservative regexes or safe-YAML loaders, and only performs string edits when exact compliance matchers fail.
- **Circular Verification dependency**: Verification requires registering artifact types, but registry initialization might fail.
  - *Mitigation*: Unit test the registry and type definitions with local mocks before performing full integration checks.
- **Namespace Collisions**: Old `healthcheck` or `health-monitoring` files might cause Python import clashes.
  - *Mitigation*: Perform complete removal of the old directories in the cleanup phase of specification implementation.
