# M9S3 — Skill Integration & Healthcenter: Canonical Artifact Adoption and Healthcenter Skill

## Objective

Define the specification for integrating AEF skills with the M9 canonical artifact system and replacing legacy health systems with `healthcenter`—a unified skill acting as a gate and ledger for AEF skill health via canonical artifact creation, validation, relationship tracking, and safe auto-remediation.

## Functional Requirements

### FR-HEALTHCENTER-ARTIFACT_CREATION

**Type**: Filesystem State Contract
**Interface Contract**: `healthcenter` skill creates canonical health-check artifacts via `core/artifacts/creation.py.create_artifact()`

**Expected Behavior**: For each validated skill, create a canonical artifact with:
- Skill identity and metadata
- Health validation results
- Timestamp and version information
- Actionable insights and recommendations

**Observable Boundary**: File system creation of health-check artifacts in canonical storage location

**Acceptance Criteria**:
- Health-check artifact created for each validated skill
- Contains canonical frontmatter with required fields (id, type, milestone_id, metadata, etc.)
- Includes skill health status and validation score
- Contains timestamp for health check execution
- Provides actionable insights when health issues detected
- Follows canonical storage location pattern: `M9/M9-health-check-<skill_name>.md`

### FR-HEALTHCENTER-LEDGER_INTEGRATION

**Type**: Filesystem State Contract
**Interface Contract**: `healthcenter` skill uses `core/artifacts/registry.py.ArtifactRegistry.store_relationship()`

**Expected Behavior**: Create relationships between skill artifacts and their health check artifacts using `derived_from` and `evaluates` relationship types

**Observable Boundary**: Canonical artifact registry contains relationships between skills and their health check artifacts

**Acceptance Criteria**:
- Skill artifacts linked to their corresponding health check artifacts
- Relationship type `derived_from` from health check to skill
- Relationship type `evaluates` from health check to skill
- Ledger accurately reflects skill health status over time
- Historical health data preserved through artifact relationships

### FR-HEALTHCENTER-BATCH_PROCESSING

**Type**: CLI Executable Contract
**Interface Contract**: `healthcenter --all` command

**Expected Behavior**: Process multiple skills in batches, creating health artifacts and ledger relationships for each

**Observable Boundary**: Batch processing produces canonical health artifacts for all skills in batch

**Acceptance Criteria**:
- Batch processing creates health artifacts for all skills
- Each skill gets individual health check artifact
- All batch artifacts properly linked to skills in ledger
- Batch size configurable without breaking artifact creation
- Failed skills in batch don't prevent processing of others

### FR-HEALTHCENTER-SINGLE_SKILL

**Type**: CLI Executable Contract
**Interface Contract**: `healthcenter --skill <skill_name>` command

**Expected Behavior**: Single skill health check produces canonical artifact with fix recommendations when health issues detected

**Observable Boundary**: Single skill processing creates health artifact with validation results and recommendations

**Acceptance Criteria**:
- Single skill processing completes successfully
- Health artifact created with accurate validation results
- Fix recommendations provided when health score < threshold
- Artifact follows canonical creation protocol
- Relationship established between skill and health artifact

### FR-HEALTHCENTER-VALIDATION_INTEGRATION

**Type**: Function/API Contract
**Interface Contract**: `core/validation.py.validate_artifact()` function

**Expected Behavior**: Health check artifacts validated against canonical metadata contract before being accepted as valid

**Observable Boundary**: `validate_artifact()` returns structured validation results for health-check artifacts

**Acceptance Criteria**:
- Health artifacts validated using canonical validator
- Invalid health artifacts rejected with structured errors
- Valid health artifacts pass all schema and type constraints
- Validation occurs before artifact is considered complete
- Error messages clearly indicate validation failures

### FR-HEALTHCENTER-STORAGE_COMPLIANCE

**Type**: Filesystem State Contract
**Interface Contract**: `core/artifacts/registry.py.get_type("health-check")` to retrieve storage rules

**Expected Behavior**: Health check artifacts stored in standardized locations based on AEF storage model

**Observable Boundary**: Health check artifacts stored in `{milestone_id}/health-checks/{skill_name}-HC-{N}.md` pattern

**Acceptance Criteria**:
- Health artifacts stored in canonical storage location
- Storage location follows `{M_ID}/health-checks/{skill_id}-HC-{N}.md` pattern
- Storage rule retrievable from artifact registry
- Artifacts resolvable through canonical resolver
- Storage location consistent across all health check artifacts

### FR-HEALTHCENTER-HISTORY_TRACKING

**Type**: Filesystem State Contract
**Interface Contract**: `core/artifacts/registry.py.get_relationships()` function

**Expected Behavior**: Health status evolution tracked through chronological health check artifacts

**Observable Boundary**: Series of health check artifacts for each skill showing health trajectory

**Acceptance Criteria**:
- Multiple health check artifacts per skill show health trends
- Artifact relationships form chronological health history
- Health status changes detectable through artifact analysis
- Historical health data preserved and accessible
- Current health status determinable from latest artifact

### FR-HEALTHCENTER-INSIGHTS_GENERATION

**Type**: Structured Schema Contract
**Interface Contract**: Health check artifact metadata includes `insights` and `recommendations` fields

**Expected Behavior**: When health issues detected, artifact contains specific guidance for remediation

**Observable Boundary**: Health check artifact metadata includes `insights` and `recommendations` fields

**Acceptance Criteria**:
- Health artifacts contain actionable insights when issues detected
- Insights are specific to validation failures found
- Recommendations provide clear remediation steps
- Insights and recommendations structured for consumption
- No insights provided when health status is optimal

## Non-Functional Requirements

### NFR-HEALTHCENTER-COMPLIANCE

**Constraint**: Full compliance with M9 canonical artifact system requirements.

**Verification**: All health check operations must follow M9 artifact creation, validation, and storage protocols.

**Acceptance Criteria**:
- Health check artifacts created via 7-step canonical protocol
- Validation performed through canonical validator
- Storage follows canonical storage rules
- Resolution works through canonical resolver
- Relationships tracked through canonical registry

### NFR-HEALTHCENTER-BACKWARD_COMPATIBILITY

**Constraint**: Maintain compatibility with existing healthcheck functionality where possible.

**Verification**: Existing CLI interface and basic validation logic preserved.

**Acceptance Criteria**:
- `healthcheck.py --all` still works for batch processing
- `healthcheck.py <skill_name>` still works for single skill
- Basic SKILL.md validation still performed
- Existing report generation maintained as optional feature
- CLI argument parsing unchanged for existing options

### NFR-HEALTHCENTER-PERFORMANCE

**Constraint**: Efficient processing for both single skills and large batches.

**Verification**: Processing time scales linearly with number of skills.

**Acceptance Criteria**:
- Single skill health check completes in reasonable time
- Batch processing scales predictably with skill count
- Memory usage remains constant per skill processed
- No exponential performance degradation with batch size
- Concurrent processing options available for large skill sets

### NFR-HEALTHCENTER-ERROR_HANDLING

**Constraint**: Graceful handling of errors without breaking health check workflow.

**Verification**: Individual skill failures don't break batch processing.

**Acceptance Criteria**:
- Failed skills logged but don't stop batch processing
- Error information preserved in health check artifacts
- System continues processing remaining skills
- Clear error reporting for failed skills
- Recovery possible from partial batch failures
