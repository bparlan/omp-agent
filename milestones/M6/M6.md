# Milestone M6: Redesign AEF Artifact Identity and Type Detection

## Goal

Redesign the OMP Agentic Engineering Framework's artifact identity, type detection, lineage, and storage model so that agentic skills never infer document semantics from ambiguous milestone-style filenames.

The immediate failure motivating this work is that an investigation artifact such as `M5S1I1.md` was interpreted by `generate-tests` as an `Implementation Report` because the artifact did not match the expected specification naming convention.

A second failure is that `investigate-issue` currently proposes follow-up specifications using identifiers such as:

- `M5S1I1-CORRECTED`
- `M5S1I2-NAMESPACE`
- `M5S1I3-GUARDRAILS`

This incorrectly encodes investigation lineage, correction status, and semantic meaning into the specification identifier.

The underlying problem is not simply a bad naming convention. The underlying architectural problem is that AEF currently relies too heavily on filenames to determine artifact type, lifecycle meaning, and relationships.

This milestone must correct that model.

## Motivation

### Current Failure Mode

1. **Ambiguous Artifact Identity**: Current framework uses complex filename patterns to infer artifact semantics
2. **Type Detection Relies on Filenames**: Skills like `generate-tests` misclassify artifacts based on naming conventions rather than explicit metadata
3. **Encodes Semantics in IDs**: Investigation IDs, correction status, and lineage are embedded in specification identifiers
4. **Unclear Lineage Tracking**: Relationships between artifacts are not represented through explicit metadata

### Problem Consequences

- Skills make incorrect assumptions about artifact type
- Generation workflows fail when artifacts don't match expected patterns
- Lineage information is lost or implicit
- Migration and refactoring become fragile

## Scope

### In Scope

1. **Canonical Artifact Types**: Define stable machine-oriented IDs for all artifact types
   - Milestone: `M{N}`
   - Specification: `SPEC-{N}`
   - Verification: `VER-{N}`
   - Test Set: `TEST-{N}`
   - Investigation: `INV-{N}`
   - Evaluation: `EVAL-{N}`
   - Review: `REVIEW-{N}`
   - Audit: `AUDIT-{N}`

2. **Canonical Storage Model**: Redesign directory structure to separate concerns
   ```
   <project-scope>/
     milestones/
       M{N}/
         milestone.md
         specs/
           SPEC-{N}.md
         verifications/
           VER-{N}.md
         tests/
           TEST-{N}.md
         investigations/
           INV-{N}.md
         evaluations/
           EVAL-{N}.md
         reviews/
           REVIEW-{N}.md
         audits/
           AUDIT-{N}.md
   ```

3. **Artifact Metadata Schema**: Define minimal metadata for all artifacts
   - Required: `id`, `type`, `title`, `milestone_id`, `status`
   - Optional: `derived_from`, `supersedes`, `superseded_by`, `related_artifacts`, `created_at`, `updated_at`, `template_version`

4. **Deterministic Type Resolution**: Implement priority-based type resolution
   - Priority 1: Explicit metadata `type` field
   - Priority 2: Canonical artifact directory
   - Priority 3: Filename (legacy compatibility only)

5. **Lineage Model**: Explicitly represent artifact relationships through metadata
   - Investigations → Specifications
   - Specifications → Evaluations → Reviews
   - Corrections through `supersedes` and `derived_from`

6. **Legacy Compatibility**: Support existing artifacts during migration
   - Classify using multiple sources (metadata, directory, headers, Document Type field)
   - Controlled migration with planning
   - No automatic bulk migration

7. **Skill Integration Updates**: Update skills to use new model
   - `investigate-issue`: Generate investigation artifacts, not specification identifiers
   - `generate-spec`: Allocate canonical IDs, add lineage metadata
   - `generate-verification`: Create verification artifacts for specifications
   - `generate-tests`: Resolve artifact types before generating tests

8. **Documentation**: Create canonical artifact architecture document
   - Types, IDs, directory structure, metadata schema
   - Lineage relationships, correction semantics
   - Legacy compatibility, type resolution rules
   - Skill creation/consumption matrix

### Out of Scope

1. **Replacing Markdown**: Markdown remains canonical human-readable format
2. **Automatic Migration**: No automatic bulk renaming of historical artifacts
3. **New Namespace Mechanism**: Do not introduce competing namespace systems
4. **Versioning**: Specification versioning (if needed, defer to follow-up milestone)
5. **Multi-Project Support**: Focus on single project-scoped milestone architecture

## Architecture Impact

### Affected Skills

1. **investigate-issue**
   - Produces investigation artifacts (INV-{N})
   - Does not prescribe specification IDs
   - References investigations in findings

2. **generate-spec**
   - Creates specifications with canonical IDs (SPEC-{N})
   - Adds lineage metadata from investigations
   - Associates with milestone and sets status

3. **generate-verification**
   - Creates verification artifacts for specifications (VER-{N})
   - Uses specification ID and type

4. **generate-tests**
   - Resolves artifact type before use
   - Verifies source is specification
   - Refuses to proceed on type ambiguity

5. **implement-specification**
   - Uses specification metadata and type
   - Considers lineage in implementation planning

6. **evaluate-implementation**
   - Uses verification and test artifacts
   - Generates evaluation reports

7. **review-implementation**
   - Reviews specifications, verifications, tests, evaluations
   - Creates review reports

8. **session-audit** / **evolve-skills**
   - May reference canonical artifact model
   - Audit trail uses consistent metadata

### Affected Files

1. **Template Files**: Update frontmatter templates
2. **Skill Implementations**: Update artifact creation/consumption logic
3. **Milestone Structure**: Update directory organization
4. **Documentation**: Add artifact architecture guide

### Data Model Changes

1. **Metadata Schema**: Add explicit `type` field to all artifacts
2. **Lineage Fields**: Add `derived_from`, `supersedes`, `superseded_by` to relevant artifacts
3. **Status Fields**: Standardize status field across artifact types
4. **ID Schema**: Canonical IDs replace legacy naming patterns

## Success Criteria

1. **Deterministic Type Resolution**: Artifact type resolution completes in < 100ms and uses explicit metadata first
2. **Canonical IDs**: All artifacts use canonical IDs (M{N}, SPEC-{N}, VER-{N}, TEST-{N}, INV-{N}, EVAL-{N}, REVIEW-{N}, AUDIT-{N})
3. **Explicit Lineage**: Lineage relationships represented through metadata, not IDs
4. **Type Detection Accuracy**: `generate-tests` correctly identifies artifact types, never misclassifies investigations as specifications
5. **Legacy Compatibility**: Existing artifacts remain discoverable and correctly classified during migration
6. **Skill Integration**: All skills updated to use new model
7. **Documentation**: Canonical artifact architecture document complete
8. **Test Coverage**: 80%+ test coverage for type resolution, lineage, and integration points
9. **Fail-Closed Behavior**: Type conflicts between metadata and directory context fail closed
10. **Migration Plan**: Controlled migration strategy with testing and rollback plan

## Risks

### Risk 1: Breaking Existing Workflows

**Description**: Changes to skill behavior may break existing workflows and dependencies.

**Mitigation**:
- Maintain legacy compatibility during migration
- Update skills incrementally with deprecation paths
- Test thoroughly before full rollout

### Risk 2: Migration Complexity

**Description**: Existing artifacts with legacy identifiers complicate migration.

**Mitigation**:
- Develop controlled migration plan
- Support multiple classification sources during transition
- Archive legacy artifacts after migration complete

### Risk 3: Implementation Delays

**Description**: Required skill updates may be time-consuming.

**Mitigation**:
- Prioritize critical skills (investigate-issue, generate-spec, generate-tests)
- Use incremental approach
- Focus on in-scope changes

### Risk 4: Integration Complexity

**Description**: New metadata schema must integrate with existing AEF metadata conventions.

**Mitigation**:
- Inspect existing conventions before designing new schema
- Reuse where possible, extend minimally
- Ensure backward compatibility
