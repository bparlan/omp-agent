# M6S1: Implementation Specification - Canonical Artifact Model

## Functional Requirements

### FR-1: Define Canonical Artifact Types

**Requirement**: Define stable machine-oriented identifiers for all lifecycle artifact types.

**Specification**:

Artifact types and their canonical IDs:

1. **Milestone**: `M{N}`
   - Format: `M` followed by milestone number (1+, no leading zeros)
   - Example: `M6`, `M7`

2. **Specification**: `SPEC-{N}`
   - Format: `SPEC-` followed by specification number (1+, no leading zeros)
   - Example: `SPEC-001`, `SPEC-002`

3. **Verification**: `VER-{N}`
   - Format: `VER-` followed by verification number (1+, no leading zeros)
   - Example: `VER-001`, `VER-002`

4. **Test Set**: `TEST-{N}`
   - Format: `TEST-` followed by test set number (1+, no leading zeros)
   - Example: `TEST-001`, `TEST-002`

5. **Investigation**: `INV-{N}`
   - Format: `INV-` followed by investigation number (1+, no leading zeros)
   - Example: `INV-001`, `INV-002`

6. **Evaluation**: `EVAL-{N}`
   - Format: `EVAL-` followed by evaluation number (1+, no leading zeros)
   - Example: `EVAL-001`, `EVAL-002`

7. **Review**: `REVIEW-{N}`
   - Format: `REVIEW-` followed by review number (1+, no leading zeros)
   - Example: `REVIEW-001`, `REVIEW-002`

8. **Audit**: `AUDIT-{N}`
   - Format: `AUDIT-` followed by audit number (1+, no leading zeros)
   - Example: `AUDIT-001`, `AUDIT-002`

**ID Constraints**:
- IDs must be machine-readable and stable across versions
- IDs must not encode:
  - "corrected" status
  - "follow-up" semantic meaning
  - Issue numbers
  - Parent artifact IDs
  - Implementation status
  - Project namespace

**Implementation**:
- Define constant dictionaries in Python skills:
  ```python
  CANONICAL_TYPES = {
      "milestone": "M{N}",
      "specification": "SPEC-{N}",
      "verification": "VER-{N}",
      "test_set": "TEST-{N}",
      "investigation": "INV-{N}",
      "evaluation": "EVAL-{N}",
      "review": "REVIEW-{N}",
      "audit": "AUDIT-{N}"
  }
  ```
- Implement ID generation functions for each type
- Add validation functions for canonical ID format

**Success Criteria**:
- All artifact types have unique, stable IDs
- ID generation follows canonical patterns
- Validation functions correctly identify valid and invalid IDs

### FR-3: Define Minimal Metadata Schema

**Requirement**: Define minimal metadata schema for all lifecycle artifacts.

**Specification**:

#### Required Fields (All Artifacts)

1. **id**: Unique machine-readable identifier
   - Format: canonical ID pattern
   - Example: `SPEC-002`, `INV-001`
   - Must be present and valid

2. **type**: Artifact type
   - Valid values: `milestone`, `specification`, `verification`, `test_set`, `investigation`, `evaluation`, `review`, `audit`
   - Must be present
   - Must be lowercase

3. **title**: Human-readable title
   - Type: string
   - Must be present
   - No length restrictions (but reasonable limit, e.g., 200 chars)

4. **milestone_id**: Parent milestone identifier
   - Format: `M{N}`
   - Must be present
   - Must reference existing milestone

5. **status**: Current lifecycle status
   - Valid values: `proposed`, `active`, `complete`, `deprecated`, `archived`
   - Default: `proposed`
   - Must be present

#### Optional Fields (Type-Specific)

1. **derived_from**: Lineage from investigations
   - Type: list of artifact IDs
   - Example:
     ```yaml
     derived_from:
       - INV-001
     ```
   - Required for: specification, verification, evaluation, review
   - May appear multiple times

2. **supersedes**: Previous version (corrections)
   - Type: list of artifact IDs
   - Example:
     ```yaml
     supersedes:
       - SPEC-001
     ```
   - Required for: specification, verification, evaluation, review
   - May appear multiple times

3. **superseded_by**: Successor version
   - Type: list of artifact IDs
   - Example:
     ```yaml
     superseded_by:
       - SPEC-002
     ```
   - Required for: specification, verification, evaluation, review
   - May appear multiple times

4. **related_artifacts**: Related artifacts
   - Type: list of artifact IDs
   - Example:
     ```yaml
     related_artifacts:
       - SPEC-001
       - VER-001
     ```
   - Optional for all artifacts

5. **created_at**: Creation timestamp
   - Format: ISO 8601 (`YYYY-MM-DDTHH:MM:SSZ`)
   - Default: current timestamp
   - Set by: `investigate-issue`, `generate-spec`, etc.

6. **updated_at**: Last modification timestamp
   - Format: ISO 8601
   - Default: current timestamp
   - Updated by: any artifact modification

7. **template_version**: Template version used
   - Format: semver (major.minor.patch)
   - Default: `2.0.0`
   - Set by: template file

**Implementation**:
- Create metadata validation function:
  ```python
  def validate_metadata(metadata: dict) -> dict:
      result = {"valid": True, "errors": [], "warnings": []}

      # Check required fields
      for field in REQUIRED_FIELDS:
          if field not in metadata:
              result["valid"] = False
              result["errors"].append(f"Missing required field: {field}")

      # Check type field
      if "type" in metadata:
          if metadata["type"].lower() not in VALID_TYPES:
              result["valid"] = False
              result["errors"].append(
                  f"Invalid type: {metadata['type']}. Valid types: {VALID_TYPES}"
              )

      # Check id format
      if "id" in metadata:
          if not is_valid_canonical_id(metadata["id"]):
              result["valid"] = False
              result["errors"].append(
                  f"Invalid ID format: {metadata['id']}. "
                  f"Expected canonical ID pattern."
              )

      # Check lineage fields
      lineage_fields = ["derived_from", "supersedes", "superseded_by"]
      for field in lineage_fields:
          if field in metadata and not isinstance(metadata[field], list):
              result["valid"] = False
              result["errors"].append(
                  f"Field '{field}' must be a list"
              )

      return result
  ```

**Success Criteria**:
- All artifacts have required fields
- Type field validates against allowed values
- ID field follows canonical pattern
- Lineage fields are correctly typed
- Validation fails on invalid metadata

### FR-4: Implement Deterministic Type Resolution

**Requirement**: Implement deterministic artifact type resolution with priority order.

**Specification**:

Type resolution algorithm:

```
function resolve_artifact_type(path: Path, metadata: dict) -> ArtifactType:
    # Priority 1: Explicit metadata
    if "type" in metadata and metadata["type"].lower() in VALID_TYPES:
        return metadata["type"].lower()

    # Priority 2: Canonical directory
    directory = path.parent.name
    type_from_directory = CANONICAL_DIRECTORIES.get(directory)
    if type_from_directory:
        return type_from_directory

    # Priority 3: Legacy filename patterns
    filename = path.stem
    return resolve_from_filename(filename)
```

**Directory-to-Type Mapping**:

```python
CANONICAL_DIRECTORIES = {
    "specs": "specification",
    "verifications": "verification",
    "tests": "test_set",
    "investigations": "investigation",
    "evaluations": "evaluation",
    "reviews": "review",
    "audits": "audit",
    "milestone": "milestone"
}
```

**Filename Pattern Matching (Legacy)**:

```python
LEGACY_PATTERNS = {
    r"M\d+S\d+T\d+": "test_set",  # M6S1T1
    r"M\d+S\d+V": "verification",  # M6S1V
    r"M\d+S\d+I\d+": "investigation",  # M6S1I1
    r"M\d+S\d+S\d+": "specification",  # M6S1S1 (compound spec)
    r"M\d+S\d+": "specification",  # M6S1 (single spec)
    r"M\d+": "milestone"  # M6
}
```

**Fail-Closed Behavior**:

If metadata type conflicts with directory type:

```
ERROR: Artifact type conflict
  Path: milestones/M6/specs/SPEC-002.md
  Metadata type: investigation
  Directory: specs
  Resolution: Fix metadata type or move artifact
```

**Implementation**:

```python
def resolve_artifact_type(path: Path, metadata: dict) -> dict:
    """
    Resolve artifact type from path and metadata.

    Returns:
        dict with "type" and "source" (metadata, directory, or filename)
    """
    # Priority 1: Explicit metadata
    if "type" in metadata:
        metadata_type = metadata["type"].lower()
        if metadata_type in VALID_TYPES:
            return {
                "type": metadata_type,
                "source": "metadata"
            }

    # Priority 2: Canonical directory
    directory = path.parent.name
    type_from_directory = CANONICAL_DIRECTORIES.get(directory)
    if type_from_directory:
        return {
            "type": type_from_directory,
            "source": "directory"
        }

    # Priority 3: Legacy filename
    filename = path.stem
    type_from_filename = None
    for pattern, type_name in LEGACY_PATTERNS.items():
        if re.match(pattern, filename):
            type_from_filename = type_name
            break

    if type_from_filename:
        return {
            "type": type_from_filename,
            "source": "filename"
        }

    # Unrecognized artifact
    return {
        "type": "unknown",
        "source": None
    }
```

**Performance Requirement**: Resolution must complete in < 100ms

**Success Criteria**:
- Type resolution uses correct priority order
- Fail-closed behavior on conflicts
- Performance requirement met
- All artifact types resolved correctly

### FR-5: Define Lineage Model

**Requirement**: Explicitly represent artifact relationships through metadata.

**Specification**:

#### Investigation → Specification

An investigation leads to zero or more specifications:

```yaml
investigations/INV-001.md
  └── (derived_from: INV-001) SPEC-002.md
  └── (derived_from: INV-001) SPEC-003.md
  └── (derived_from: INV-001) SPEC-004.md
```

Each specification must have `derived_from` pointing to the investigation.

#### Specification → Verification → Evaluation → Review

A specification leads to verifications, which lead to evaluations and reviews:

```yaml
SPEC-002.md
  └── (derived_from: SPEC-002) VER-001.md
  └── (derived_from: SPEC-002) VER-002.md
```

```yaml
VER-001.md
  └── (derived_from: VER-001) EVAL-001.md
  └── (derived_from: VER-001) EVAL-002.md
```

```yaml
EVAL-001.md
  └── (supersedes: EVAL-001) REVIEW-001.md
```

#### Corrections

Corrections represented through `supersedes` and `derived_from`:

```yaml
SPEC-001.md
  └── (derived_from: INV-001) SPEC-002.md
      └── (supersedes: SPEC-001) (derived_from: INV-001)
```

**Implementation**:

Update `generate-spec` to add `derived_from` from investigations:

```python
def generate_spec(investigation_id: str, findings: List[str]) -> Path:
    # ... generate specification ...

    # Add lineage metadata
    metadata["derived_from"] = [investigation_id]

    return path
```

**Success Criteria**:
- Lineage relationships explicitly represented
- Investigation IDs not encoded in specification IDs
- `derived_from` field populated correctly
- `supersedes` field populated for corrections

### FR-11: Update generate-tests Skill

**Requirement**: Update `generate-tests` to resolve artifact type before use.

**Specification**:

**Before Generating Tests**:

1. Identify target specification (from command line or interactive prompt)
2. Resolve its artifact type
3. Verify that it is actually a specification
4. Verify that it belongs to the current milestone
5. Resolve its associated verification artifact
6. Refuse to proceed if artifact identity or type is ambiguous

**Error Message**:
```
ERROR: Cannot resolve source artifact type.
Expected: specification.
Found: investigation.
Resolution: select or generate a valid specification.
```

**Implementation**:

```python
def generate_tests(specification_path: Path) -> Path:
    # Resolve artifact type
    metadata = parse_yaml_frontmatter(specification_path)
    resolution = resolve_artifact_type(specification_path, metadata)

    # Verify type
    if resolution["type"] != "specification":
        raise ValueError(
            f"Cannot resolve source artifact type.\n"
            f"Expected: specification.\n"
            f"Found: {resolution['type']}.\n"
            f"Resolution: select or generate a valid specification."
        )

    # Verify milestone
    if resolution["milestone_id"] != current_milestone():
        raise ValueError(
            f"Specification {resolution['id']} does not belong to "
            f"current milestone {current_milestone()}."
        )

    # Generate tests
    test_id = generate_canonical_id("test_set", resolution["milestone_id"])
    metadata["type"] = "test_set"
    metadata["derived_from"] = [resolution["id"]]

    return create_artifact(
        metadata=metadata,
        content="# Test Set\n\n",
        directory="tests"
    )
```

**Success Criteria**:
- Artifact type resolved before use
- Type validation rejects non-specification artifacts
- Milestone validation enforced
- Clear error messages for type ambiguity
- `generate-tests` cannot misclassify investigations as specifications

### FR-12: Implement Fail-Closed Behavior

**Requirement**: If explicit metadata conflicts with directory context, fail closed.

**Specification**:

**Conflict Detection**:

```python
def check_type_conflict(path: Path, metadata: dict) -> bool:
    resolution = resolve_artifact_type(path, metadata)
    if resolution["source"] == "metadata" and resolution["source"] == "directory":
        # Metadata and directory disagree
        return True

    # Metadata and directory are consistent
    return False
```

**Error Handling**:

```python
if check_type_conflict(path, metadata):
    print(
        "ERROR: Artifact type conflict\n"
        f"  Path: {path}\n"
        f"  Metadata type: {metadata.get('type')}\n"
        f"  Directory: {path.parent.name}\n"
        f"  Resolution: Fix metadata type or move artifact"
    )
    sys.exit(1)
```

**Success Criteria**:
- Conflicts detected between metadata and directory
- Clear error messages displayed
- Process exits on conflict (no silent reclassification)
- No silent reinterpretation of documents

## Edge Cases

### EC-1: Investigation with No Findings

**Scenario**: Investigation artifact created with no actionable findings.

**Resolution**: Allow empty findings list. Investigation still represents analysis work even if no specifications generated.

### EC-2: Specification with Multiple Investigations

**Scenario**: One specification derived from multiple investigations.

**Resolution**: `derived_from` field can contain multiple investigation IDs.

### EC-3: Verification from Multiple Specifications

**Scenario**: Verification protocol covers multiple specifications.

**Resolution**: `derived_from` field can contain multiple specification IDs.

### EC-4: Missing metadata during migration

**Scenario**: Legacy artifact has no `type` field.

**Resolution**: Use directory or filename classification (Priority 2 or 3).

### EC-5: Artifact moved between directories

**Scenario**: User moves artifact from `specs/` to `investigations/` after creation.

**Resolution**: Check type conflict on next access. If metadata type doesn't match new directory, fail closed.

### EC-6: Empty title

**Scenario**: Artifact created without `title` field.

**Resolution**: Default to "Untitled" or generate from ID (e.g., `SPEC-001` → "Specification 001").

### EC-7: Invalid status value

**Scenario**: Artifact has invalid `status` value (e.g., "invalid").

**Resolution**: Validate status against allowed values during metadata validation. Fail closed.

### EC-8: Circular lineage

**Scenario**: `derived_from` creates circular reference (A → B → A).

**Resolution**: Detect cycles during lineage validation. Fail closed.

### EC-9: Non-existent referenced artifact

**Scenario**: `derived_from` references artifact that doesn't exist.

**Resolution**: Validate referenced artifacts exist. Fail closed or log warning.

### EC-10: Multiple specifications in same directory

**Scenario**: Two specifications created in `specs/` without explicit ordering.

**Resolution**: Use canonical ID number for ordering (SPEC-001, SPEC-002, ...).

## Failure Scenarios

### FS-1: Type resolution returns unknown

**Scenario**: Artifact not recognized by any classification method.

**Resolution**: Log warning. Treat as unknown type. Generate test fails with clear error message.

### FS-2: Metadata conflicts with directory but no type field

**Scenario**: Artifact not in canonical directory but has `type: specification` field.

**Resolution**: Consider type from metadata. Ignore directory. Log warning about non-canonical location.

### FS-3: Skill cannot determine milestone_id

**Scenario**: Artifact created without explicit `milestone_id`.

**Resolution**: Infer from directory path. If not possible, fail closed.

### FS-4: ID generation collision

**Scenario**: Two artifacts attempt to create same canonical ID.

**Resolution**: Increment ID until unique. Log warning about collision.

### FS-5: Template not found

**Scenario**: Skill tries to use template that doesn't exist.

**Resolution**: Generate artifact without template. Log warning.

### FS-6: File system permissions

**Scenario**: Artifact creation fails due to permissions.

**Resolution**: Raise clear error with file path. Do not silently fail.

## Architecture Constraints

### C-1: Do Not Introduce Competing Namespace

**Constraint**: Do not create a new namespace mechanism alongside the existing project-scope milestone architecture.

**Impact**: Must reuse existing directory structure and milestone organization.

**Mitigation**: All changes must integrate with existing AEF project-scoped milestone architecture.

### C-2: Markdown Remains Canonical Format

**Constraint**: Markdown remains the canonical human-readable format. Do not replace with JSON or other formats for narrative content.

**Impact**: YAML frontmatter only for metadata, not content.

**Mitigation**: Only use JSON/TOML where machine processing is specifically required (e.g., configuration files).

### C-3: Fail Closed on Conflicts

**Constraint**: If metadata and directory disagree, fail closed and report conflict.

**Impact**: No silent reclassification. Clear error messages required.

**Mitigation**: Implement conflict detection in type resolution function.

### C-4: No Automatic Bulk Migration

**Constraint**: Do not rename or migrate all historical artifacts automatically.

**Impact**: Manual migration required for legacy artifacts. Migration must be controlled and planned.

**Mitigation**: Provide controlled migration plan with phased rollout.
