# Specification M8S1: Valid Evidence — Formalise Test Validity as a Lifecycle Concept

## Objective

Introduce a mandatory **validity check** stage between test execution and evidence interpretation in the SDD lifecycle. Test exit codes alone are insufficient — the pipeline must first establish that a test failure is attributable to the intended subject before advancing to the next phase.

### Milestone Complexity & Multi-Spec Plan

This milestone is cohesive: all 10 scope items center on a single concept ("Valid Evidence"), targeting 3 independent skill files plus framework documentation and 3 templates. A single specification (M8S1) suffices — the implementation tasks are grouped into 4 sequential phases but all within one spec.

### Prior Work Completed

M7 restored test-first integrity: `generate-tests` now produces executable tests that initially fail, enforces hard boundary guardrails against production code, and generates machine-readable output. The M7 lifecycle postmortem identified 10 architectural findings, one of which directly motivates M8: "Test failure is not equivalent to missing implementation."

### Remaining Gaps

The M7 fix guarantees that tests fail before implementation, but provides no mechanism to determine **why** a test failed. The pipeline cannot distinguish:
- A valid test failure attributable to missing implementation
- An invalid test failure caused by self-scanning, wrong interpreter, wrong path, dirty working tree, platform incompatibility, malformed assertions, or broken test harness

This gap is what M8S1 closes.

## Functional Requirements

### FR-1: Define "Valid Evidence" as a Lifecycle Concept

**FR-1.1** — Define formal vocabulary for test evidence:
- `VALID_TEST`: A test whose exercised the intended subject and whose failure/success is attributable to that subject
- `INVALID_TEST`: A test whose result is not attributable to the intended subject — the pipeline must stop
- `VALIDITY CHECK`: The mandatory evaluation-time pre-processing step that classifies each test before interpreting its exit code

**FR-1.2** — Codify the six validity criteria for a test to be considered valid evidence:
1. The test exercised the intended subject — it loaded, imported, or invoked the correct code path
2. The failure is attributable to the subject — not to infrastructure, config, or environment
3. The test environment is deterministic — same inputs produce same results
4. The working tree is clean — no uncommitted changes that could affect behavior
5. The test does not scan itself — the test script is not testing its own contents
6. The failure message is diagnostic — it identifies WHAT failed and WHY, not just an exit code

**FR-1.3** — Codify the core principle in canonical AEF documentation:
> Never advance the lifecycle based solely on test exit codes. First establish that the test itself is valid and that its failure is attributable to the intended subject.

### FR-2: Validity Gate in `evaluate-implementation`

**FR-2.1** — Insert a mandatory validity check BEFORE test interpretation in the `evaluate-implementation` process. The evaluator must answer for each test: "Is this test failure attributable to the intended subject?"

**FR-2.2** — The validity gate produces one of three verdicts per test:
- `VALID_TEST`: Proceed to pass/fail interpretation
- `INVALID_TEST`: Stop — produce invalidation report, do not advance pipeline
- `UNCERTAIN`: Flag for human review — do not treat as evidence

**FR-2.3** — Invalid tests produce an invalidation report describing:
- Why the test is invalid (which validity criterion was violated)
- What the failure actually indicates (wrong path? wrong interpreter? self-scanning? dirty tree?)
- What must be repaired (fix the test, fix the environment, or clean the working tree)

**FR-2.4** — The validity check MUST run BEFORE the pass/fail interpretation. Order is:
```
TEST EXECUTION
  ↓
VALIDITY CHECK
  ↓
VALID TEST?
  ├── NO → INVALID_TEST
  │         stop — produce invalidation report
  │
  └── YES
       ↓
       PASS / FAIL   ← now interpretable as evidence
```

### FR-3: Self-Validity Assertions in Generated Tests

**FR-3.1** — Every generated test MUST include a self-validity assertion: a mechanical check that proves the test actually exercised its subject before reporting pass/fail.

**FR-3.2** — Self-validity assertions must be simple, mechanical checks:
- File existence check: `test -f "$TARGET_FILE"` (bash) or `os.path.exists(path)` (Python)
- Module import check: `python -c "import $MODULE"` or JavaScript `require()`
- Function existence check: `type $FUNCTION &>/dev/null` (bash) or `hasattr(module, name)` (Python)
- Output inspection check: the script actually called the subject and captured its output

**FR-3.3** — Self-validity assertions MUST NOT contain complex logic. A broken assertion is itself detectable.

**FR-3.4** — If the self-validity assertion fails, the test MUST emit:
```
VALIDITY FAILURE: test did not exercise intended subject
Subject: <path or module name>
Reason: <specific validation failure>
```
and exit with code 2 (distinct from exit 0 = pass, exit 1 = fail).

**FR-3.5** -- Self-validity assertions are a secondary signal. The primary validity gate is at evaluation-time (FR-2). Both execute and both must pass for a test to be considered valid evidence.

### FR-4: INVALID_TEST Classification

**FR-4.1** — `INVALID_TEST` is a formal test result state, distinct from PASS and FAIL.

**FR-4.2** — When a test is classified INVALID, the pipeline MUST STOP. Do not advance to the next phase.

**FR-4.3** — No silent discard or automatic retry of invalid tests. Every invalidation requires human attention.

**FR-4.4** — The invalidation report metadata includes:
- Test file path
- Which validity criterion was violated
- Raw evidence (exit code, stdout, stderr)
- Recommended repair action

### FR-5: Validity Metadata in Test Artifacts

**FR-5.1** — Test plans (`M{X}S{Y}T{Z}.md`) MUST carry a `Validity Metadata` section including:
- Subject under test (exact file path, module name, function name)
- Acceptance criteria for validity (how is "exercised the subject" determined?)
- Expected failure conditions (what would a valid failure look like?)
- Environment prerequisites (tools, files, state required for validity)

**FR-5.2** — Executable test files MUST carry validity metadata in comments at the top of the file:
```
# VALIDITY: subject=tests/M8/test_subject.py
# VALIDITY: check=file_exists
# VALIDITY: env_required=python3,bash
```

### FR-6: Validity Analysis in `review-implementation`

**FR-6.1** — The review report MUST include a "Test Validity" section that answers "Were the tests themselves valid?"

**FR-6.2** — The review must distinguish "test is wrong" from "implementation is wrong" in its findings.

**FR-6.3** — The compliance matrix must include a "Test Valid?" column alongside "Requirement" and "Status".

**FR-6.4** — If any tests were classified INVALID, the review must recommend test repair before re-evaluation.

### FR-7: Framework Documentation

**FR-7.1** — The core principle MUST appear verbatim in AGENTS.md (or FRAMEWORK.md if more appropriate):

> Never advance the lifecycle based solely on test exit codes. First establish that the test itself is valid and that its failure is attributable to the intended subject.

**FR-7.2** — Documentation must be grep-able. The principle must appear as a literal string, not reformatted or paraphrased.

**FR-7.3** — The "Valid Evidence" concept must be documented with definition, six criteria, and the VALID_TEST / INVALID_TEST / UNCERTAIN classification.

## Non-Functional Requirements

### NFR-1: Determinism

The validity gate must be deterministic — same test output + same environment = same validity verdict.

### NFR-2: Minimal Overhead

The validity check must not add significant execution time. It operates on already-available data: exit code, stdout, stderr, file path, and working tree state. No external service calls.

### NFR-3: Compatibility with M7

M8's validity gate must coexist with M7's test-first guarantees. M7 ensures tests fail before implementation; M8 ensures we know *why* they failed. Both execute during evaluation. No regression in M7's deterministic output (TESTS_RUN, TESTS_PASSED, TESTS_FAILED, EXIT_CODE).

### NFR-4: Human Override

The pipeline MUST support human certification of an INVALID test as valid (override path). The override must be logged and explicit.

### NFR-5: No Test Framework Changes

Validity operates on AEF's interpretation of test results, not on test framework internals. Exit code, stdout, stderr, file path, and subject under test are the only data sources.

## Data Flow

### Validity Gate Data Flow (evaluate-implementation)

```
Test Execution Result
  │
  ├─ exit_code (int)
  ├─ stdout (string)
  ├─ stderr (string)
  ├─ test_file_path (string)
  └─ subject_under_test (string, from test metadata)
       │
       ▼
VALIDITY CHECK
  │
  ├─ 1. Did the test exercise the subject?    ← checks subject import/call succeeded
  ├─ 2. Is failure attributable to subject?   ← checks that failure msg relates to subject
  ├─ 3. Is environment deterministic?         ← checks same test ran before
  ├─ 4. Is working tree clean?                ← git status --porcelain
  ├─ 5. Does test avoid self-scan?            ← checks test doesn't read its own source
  └─ 6. Is failure message diagnostic?        ← checks stderr contains subject-identifying text
       │
       ▼
    VERDICT
       │
       ├── VALID_TEST    → Pass/Fail Interpretation
       ├── INVALID_TEST  → Invalidation Report → STOP
       └── UNCERTAIN     → Flag for Human Review
```

### Self-Validity Assertion Data Flow (generate-tests → test execution)

```
Generated Test
  │
  ├─ Self-validity assertion (top of script)
  │    │
  │    ├─ PASS → Continue to actual test logic
  │    └─ FAIL → Exit code 2, emit VALIDITY FAILURE message
  │
  └─ Actual test logic
       │
       ├─ PASS → exit 0
       └─ FAIL → exit 1
```

## Constraints

1. **No retroactive validation** — Do not re-validate past test results from M1-M7. Existing artifacts are immutable.
2. **No automated validation infrastructure** — No dedicated daemon, service, or CI pipeline. The validity check is a procedural gate.
3. **No test framework redesign** — Validity operates on AEF's interpretation of test results, not on test framework internals.
4. **No pipeline topology changes** — The validity gate inserts into existing phases, not restructures them.
5. **No non-test artifact validation** — This spec is about test validity only. Specification validity, verification validity, and review validity are separate concerns.
6. **Self-validity assertions must be simple** — No complex logic. File exists, module imports, function exists, output captured.
7. **M7 compatibility** — M7's deterministic output (TESTS_RUN, TESTS_PASSED, TESTS_FAILED, EXIT_CODE) must be preserved. M8 extends, not replaces.

## Assumptions

1. The primary validity gate at evaluation-time is the authoritative check; self-validity assertions in tests are a complementary secondary signal.
2. Human override path exists — a human can certify an INVALID test as valid, with explicit logging.
3. The six validity criteria are sufficient to classify the common failure modes observed in M7 and before.
4. Exit code 2 is unused by existing test infrastructure and can safely represent "validity failure" without conflicting with M7's semantics (exit 0 = pass, non-zero = fail).
5. AGENTS.md and FRAMEWORK.md are the appropriate targets for concept documentation. The spec defers exact placement to implementation analysis.
6. The validity check implementation requires no external dependencies — all data sources (exit code, stdout, stderr, file path, git status) are available in the execution environment.
