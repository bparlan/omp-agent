# Milestone M8 - HealthCheck Skill Modular Refactoring

## Milestone Contract

This document is the authoritative contract for milestone M8. Downstream stages SHALL derive their requirements from this document. Downstream stages MUST NOT introduce behavior, scope, or interfaces not declared or implied by this document. Contract violations SHALL emit #NEEDS-CLARIFICATION.

This milestone defines the strict requirements for transforming the monolithic healthcheck.py into a modular, maintainable architecture while preserving complete backward compatibility and existing functionality.

## Goal

Refactor the monolithic healthcheck.py script (237 lines) into a modular architecture with separate components for validation, discovery, reporting, CLI, and main entry point while maintaining backward compatibility and existing functionality. The refactoring will enable independent testing of each component, improve maintainability, and support future extensibility without breaking existing user workflows.

## Spec Decomposition Plan

This milestone decomposes into exactly 5 specifications:

- **M8S1** — Core validation module with Validator base classes
- **M8S2** — Discovery module with skill location mechanisms
- **M8S3** — Reporting module for badge and JSON generation
- **M8S4** — CLI module with argument parsing and orchestration
- **M8S5** — Main entry point with minimal glue logic

Each specification SHALL address exactly the scope in its one-line description. generate-spec MUST NOT create specifications beyond this plan.

## Scope

- Refactor healthcheck.py monolithic architecture into 5 focused modules:
  - core/validation.py - Pure validation logic with Validator base classes
  - discovery.py - Skill discovery mechanisms with project root detection
  - reporting.py - All reporting functionality (badges, JSON reports, processed skills)
  - cli.py - CLI parsing and orchestration with argument handling
  - main.py - Clean entry point that imports and runs modules
- Maintain backward compatibility with existing CLI interface (--all, single-skill modes)
- Preserve all existing functionality and output formats
- Enable independent testing of each module
- Reduce cognitive complexity from 237 lines in single file to ~40-50 lines per module
- Support easy addition of new validation rules and discovery strategies
- Enable incremental validation cycles over time
- Create comprehensive test coverage for each component

## Out of Scope

- Changing the core validation business logic or acceptance criteria
- Modifying the existing output formats (badge, JSON, processed skills)
- Adding new validation requirements beyond what's currently implemented
- Changing the overall tool behavior from user perspective
- Refactoring other skills in the AEF ecosystem
- Adding new features not specified in requirements
- Performance optimization beyond code organization improvements
- Changing the batch processing structure (3 batches)
