## Goal

Introduce a mandatory **validity check** stage between test execution and evidence interpretation in the SDD lifecycle, so the pipeline never advances based solely on exit codes — it first establishes that the test failure is attributable to the intended subject.

---

## Motivation

### Current Failure Mode

The AEF lifecycle currently treats test exit codes as direct evidence:

```
TEST
  ↓
PASS / FAIL
```

This is insufficient. An LLM can easily produce a test that "fails" and interpret the failure as evidence of missing implementation, but the failure could actually be caused by:

- Wrong file path
- Wrong fixture
- Wrong interpreter
- Test scanning itself (circular self-test)
- Dirty working tree (uncommitted changes polluting results)
- Platform-specific command that doesn't run on this OS
- Incorrect assumption about the codebase structure
- Malformed assertion (syntax error, invalid comparison)
- Test infrastructure not set up (missing dependencies, uninstalled tools)
- Broken test harness (the test framework itself has a bug)

The M7 experience demonstrated this failure mode directly — generated tests failed for the wrong reasons (contamination, wrong interpreter, pseudo-code leakage), and the framework had no vocabulary or gate to distinguish _valid_ test failure from _invalid_ test failure.

### What's Missing

The lifecycle needs a formal validity gate:

```
TEST EXECUTION
  ↓
VALIDITY CHECK
  ↓
VALID TEST?
  ├── NO → INVALID_TEST
  │         stop — test is not evidence
  │
  └── YES
       ↓
       PASS / FAIL   ← now interpretable as evidence
```

A test failure is **valid evidence** only when:

1. The test exercised the intended subject — it loaded, imported, or invoked the correct code path
2. The failure is attributable to the subject — not to infrastructure, config, or environment
3. The test environment is deterministic — same inputs produce same results
4. The working tree is clean — no uncommitted changes that could affect behavior
5. The test does not scan itself — the test script is not testing its own contents
6. The failure message is diagnostic — it identifies WHAT failed and WHY, not just an exit code

### Consequences of Inaction

Without this concept:

- **False negatives** (`test failed` → `implementation missing` when the test itself is broken) silently corrupt the pipeline
- **False positives** (`test passed` → `implementation correct` when the test doesn't actually exercise the subject) silently pass broken code
- The review-implementation phase cannot distinguish "test is wrong" from "implementation is wrong" — both produce the same raw signal
- Every evaluation cycle becomes a guessing game: "Did it really fail, or was the test broken?"
- The AEF cannot learn from failures because failure attribution is lost

## Scope

### In Scope

1. **Define "Valid Evidence" as a Lifecycle Concept** — Formal vocabulary, definition, and criteria for what constitutes valid test evidence. Codify in canonical framework documentation.

2. **Validity Gate in the Evaluation Phase** — Add a mandatory validity check to `evaluate-implementation` before interpreting test results. The evaluator must answer: "Is this test failure attributable to the intended subject?"

3. **Validity Assertions in Generated Tests** — Every generated test MUST include a self-validity assertion: a check that proves the test actually exercised its subject (e.g., "the file exists", "the module imported", "the function was called") before reporting pass/fail.

4. **Invalidation Protocol** — Define what happens when a test is deemed INVALID: stop the pipeline, produce an invalidation report, do not advance to the next phase. No silent discard or automatic retry.

5. **Validity Metadata in Test Artifacts** — Test plans and executable test files must carry explicit validity metadata: subject under test, acceptance criteria for validity, expected failure conditions, environment prerequisites.

6. **Review Phase Validity Analysis** — `review-implementation` must analyze not just whether tests passed, but whether the tests themselves were valid. Distinguish "test is wrong" from "implementation is wrong" in review reports.

7. **Update `evaluate-implementation` Skill** — Modify the skill's instructions to include the validity check as a mandatory pre-processing step before test interpretation.

8. **Update `review-implementation` Skill** — Modify the skill's instructions to include validity analysis in its compliance matrix.

9. **Update `generate-tests` Skill** — Modify the skill's instructions to include self-validity assertions in all generated tests.

10. **Framework Documentation** — Codify the principle in the canonical AEF documentation (AGENTS.md, FRAMEWORK.md, or equivalent):

    > **Never advance the lifecycle based solely on test exit codes. First establish that the test itself is valid and that its failure is attributable to the intended subject.**

### Out of Scope

1. **Retroactive Validation** — Do not re-validate past test results from M1–M7. Existing artifacts are immutable.

2. **Automated Validation Infrastructure** — No dedicated validity-check daemon, service, or CI pipeline. The validity check is a procedural gate within existing skills.

3. **Test Framework Redesign** — No changes to how tests are discovered, run, or reported by external test frameworks (pytest, Jest, etc.). The validity gate operates on the AEF's own interpretation of test results.

4. **Arbitrary Architecture Changes** — No redesign of the SDD pipeline topology. The validity gate inserts into existing phases rather than restructuring them.

5. **Validation of Non-Test Artifacts** — This milestone is about test validity only. Specification validity, verification validity, and review validity are separate concerns.

## Success Criteria

### Primary Success Criteria

1. **Valid Evidence concept is codified** in canonical AEF documentation — definition, criteria, and the core principle are documented in a grep-able, testable form.

2. **`evaluate-implementation` performs a validity check** before interpreting test exit codes. It must answer "Is this test failure attributable to the intended subject?" and produce a structured response.

3. **INVALID_TEST classification exists** as a formal test result state, distinct from PASS and FAIL. The pipeline stops on INVALID_TEST.

4. **Self-validity assertions in generated tests** — Every test generated by `generate-tests` includes a check that it actually exercised its subject before reporting pass/fail (e.g., file existence, module import, function invocation, output inspection).

5. **Invalidation report produced** when a test is classified INVALID. Report describes why the test is invalid, what the failure actually indicates, and what must be fixed.

6. **Review-implementation distinguishes validity from correctness** — The review report includes a "Test Validity" section that answers "Were the tests themselves valid?"

7. **All three affected skills updated** — `evaluate-implementation`, `review-implementation`, and `generate-tests` contain the new validity instructions.

### Secondary Success Criteria

8. **Pipeline integration** — M8's changes coexist with M7's determinism guarantees. No conflict or regression.

9. **Edge cases documented** — The validity criteria include guidance for:
   - Tests that pass before implementation (false positives)
   - Tests that fail for infrastructure reasons
   - Tests that cannot self-validate (interpreted languages without module systems)
   - Tests involving external systems (network, database, file system)

10. **Test for test validity** — At least one meta-test that validates the validity gate itself (similar to M7's Tests A–G).

## Risks

### Risk 1: Validity Gate Introduces False Negatives

**Description**: An overly strict validity check may classify valid tests as INVALID, stalling the pipeline on false negatives.

**Impact**: HIGH

**Mitigation**:
- Validity criteria must be conservative but not paranoid — a test loading the correct module is valid even if it doesn't test every edge case
- Provide an override path: human can manually certify a test as valid
- Log invalidation metadata so patterns of false invalidation can be detected
- Invalid tests produce a diagnostic report, not a silent halt

### Risk 2: Self-Validation Adds Fragility to Test Scripts

**Description**: Self-validity assertions in generated tests may themselves be wrong — the assertion could pass when the subject wasn't exercised, or fail when it was.

**Impact**: MEDIUM

**Mitigation**:
- Self-validity assertions must be simple, mechanical checks (file exists, module imports, function exists)
- No complex logic in validity assertions — a broken assertion is itself detectable
- Validity check at evaluation-time is the primary gate; self-validity in tests is a secondary signal
- Human override for edge cases

### Risk 3: Scope Creep into Test Framework Territory

**Description**: The validity concept could expand into redesigning how test frameworks report results, which is explicitly out of scope.

**Impact**: MEDIUM

**Mitigation**:
- Validity operates on AEF's interpretation of test results, not on test framework internals
- A test result is: exit code, stdout, stderr, file path, subject under test
- Validity check answers: "Given these outputs, can we trust this test?" — not "Is this test framework correct?"
- Hard boundary in the specification

### Risk 4: Conflicts with M7's Test-First Guarantees

**Description**: M7 requires that generated tests initially fail. If a test fails because it's invalid, the failure is correct but misleading — the pipeline sees a non-zero exit code and advances, not knowing the failure was for the wrong reason.

**Impact**: MEDIUM

**Mitigation**:
- M7's test-first guarantee holds: tests still fail before implementation
- M8 adds a new dimension: "Why did the test fail?"
- M7 and M8 are complementary — M7 guarantees the *fact* of failure, M8 guarantees the *attribution* of failure
- Both checks execute during evaluation
- M8's validity check runs BEFORE the pass/fail interpretation

## Notes

### Relationship to M7

M8 is a direct architectural followup to M7's finding #10 (or equivalent): "Test failure is not equivalent to missing implementation." M7 restored the guarantee that tests fail before implementation. M8 adds the guarantee that the failure is *meaningful* — attributable to the intended subject.

### Implementation Order

1. **Define the concept** — Document "Valid Evidence" in framework docs (AGENTS.md, FRAMEWORK.md)
2. **Update `evaluate-implementation`** — Add validity check before test interpretation
3. **Update `generate-tests`** — Add self-validity assertions to generated tests
4. **Update `review-implementation`** — Add validity analysis to review reports
5. **Test the validity gate** — Meta-test for validity
6. **Integration check** — Verify M7 and M8 coexist
7. **Final documentation** — Codify the principle

### Key Principle

> **Never advance the lifecycle based solely on test exit codes. First establish that the test itself is valid and that its failure is attributable to the intended subject.**

This principle MUST appear literally in framework documentation.
