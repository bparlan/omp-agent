CLI Contract

The `bin/omp-verify-precondition` utility must expose a well-defined CLI contract that is verifiable through automated testing. This contract includes:

- **Executable Path:** The primary entry point for the tool is located at `bin/omp-verify-precondition`.
- **Argument Parsing:** The tool must correctly parse and validate all required arguments (`--ledger`, `--test-dir`).
- **Exit Code Contract:** The tool must adhere to the specified exit code semantics (0 for PASS, 1 for FAIL, 2 for VALIDITY_FAILURE) as detailed in FR-2.
- **Output Format:** Standard output and standard error should be used for reporting test status and errors, respectively.

'Exit Semantics'

# Objective

Automate pre-implementation test-validity and precondition verification for Milestone M10, ensuring that implementation phases only proceed when tests are correctly configured to fail before code introduction and do not exhibit self-scanning or environmental contamination.

# Functional Requirements

## FR-1: CLI Executable Contract

The system MUST provide a command-line interface (CLI) executable at `bin/omp-verify-precondition` that performs pre-implementation verification.

- **Command:** `bin/omp-verify-precondition`
- **Arguments:**
  - `--ledger <test_ledger_path>`: Path to a file defining the test ledger.
  - `--test-dir <test_directory>`: Path to the directory containing test scripts and fixtures.

## FR-2: Exit Semantics

The `bin/omp-verify-precondition` CLI MUST adhere to the following exit codes:

- **Exit Code 0 (PASS):**
  - All checks defined in the test ledger return PASS (exit code 0).
  - All executable implementation check scripts return a VALID_INITIAL_FAILURE (exit code 127 or 1).
- **Exit Code 1 (FAIL):**
  - Any precondition is violated. This includes, but is not limited to:
    - A test script passes prematurely (i.e., not a VALID_INITIAL_FAILURE).
    - A required file (e.g., ledger, script) is missing.
    - A script fails with exit code 2 (INVALID_TEST).

## FR-3: Test Validity Rules

The verification process MUST reject any test execution that produces a syntax error, self-scanning behavior, or environment contamination. Such cases MUST be classified as a VALIDITY_FAILURE, which blocks progression to the implementation phase.

## FR-4: Testability and Isolation

Downstream integration tests MUST execute the REAL `bin/omp-verify-precondition` binary against static, isolated project fixtures.

- **Fixture: `tests/fixtures/synthetic_precondition_valid/`**
  - Contains a ledger and scripts that are designed to fail naturally with exit codes 127 or 1 (representing a VALID_INITIAL_FAILURE).
- **Fixture: `tests/fixtures/synthetic_precondition_invalid/`**
  - Contains a ledger where tests pass prematurely or fail with syntax/compilation errors (representing a VALIDITY_FAILURE).
- **Constraint:** Test scripts MUST NOT mock the CLI tool's internal execution loop. They must execute the actual binary and assert exit codes programmatically. Regex-parsing of stderr is strictly banned.

# Data Flow

1.  The `bin/omp-verify-precondition` CLI tool accepts a path to a test ledger file and a test directory.
2.  It parses the ledger to identify tests and their expected outcomes.
3.  It executes the specified test scripts within the provided directory.
4.  It checks the exit codes of the executed scripts against the ledger's expectations and the VALID_INITIAL_FAILURE criteria.
5.  Based on the outcomes, it exits with code 0 (PASS) or 1 (FAIL).

# Constraints

- Downstream tests must use static, isolated fixtures.
- Test scripts must call the actual `bin/omp-verify-precondition` binary.
- Regex parsing of stderr is forbidden for verification.
- Implementation details of the verification loop should not be mocked by tests.

# Out of Scope

- Modifying any existing skills or production code beyond the implementation of `bin/omp-verify-precondition`.
- Automating the creation or maintenance of test fixtures.
- Defining test logic within the specification; this is handled by the ledger and scripts.
