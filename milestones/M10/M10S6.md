## Objective

Tailor the test framework and execution logic to the type of project under test without imposing a universal testing technology.

### Milestone Complexity & Multi-Spec Plan

The milestone M10 is explicitly decomposed into 10 sequential specifications, as detailed in `M10.md`. This specification (M10S6) addresses a specific part of that decomposition. No further breakdown is required for this sequence.

---

## Functional Requirements

### FR-1: Markdown Project Test Execution
The test execution framework MUST support Markdown projects by utilizing structural metadata and frontmatter parsing to drive test selection and execution.

### FR-2: Static HTML/CSS Project Test Execution
The test execution framework MUST support Static HTML/CSS projects by employing DOM and class assertions to drive test selection and execution.

### FR-3: Python Project Test Execution
The test execution framework MUST support Python projects by integrating with `pytest` and utilizing standard pytest assertions for test selection and execution.

### FR-4: Framework/AEF Task Project Test Execution
The test execution framework MUST support Framework/AEF tasks by leveraging isolated, synthetic fixtures and shell execution scripts for test selection and execution.

## Data Flow

1.  The project type is identified (e.g., through `bin/omp-discover` or explicit configuration).
2.  Based on the detected project type, the appropriate test execution strategy is selected and invoked by `bin/aef-test-runner`.
3.  Tests are executed using the chosen strategy (e.g., `pytest` for Python, shell scripts for AEF tasks, DOM assertions for web projects).
4.  Test results are collected and reported.

## Constraints

- Test execution must dynamically adapt to diverse project types without imposing a single universal technology.
- Must integrate with or be callable by upstream components like `bin/omp-verify-precondition`.

## Assumptions

- A reliable mechanism exists for detecting project types (e.g., via `bin/omp-discover` or other explicit project metadata).
- Necessary testing environments and tools (`pytest`, shell interpreters, browser automation libraries for DOM assertions) are available and configured in the execution environment.

## Acceptance Criteria

- [ ] The `bin/aef-test-runner` (or equivalent) correctly identifies project types for Markdown, Static HTML/CSS, Python, and Framework/AEF tasks.
- [ ] The selected test execution strategy is appropriate for the identified project type.
- [ ] Tests are executed successfully using the selected strategy.
- [ ] Test results are reported correctly.
- [ ] The test execution framework is designed to be extensible for future project types.
