#### Objective
Establish a robust, project-agnostic failure classification and diagnostics contract inside the OMP test execution runner (`bin/omp-test` / `bin/aef-test-runner`) [163]. This contract prevents cascading downstream test crashes from obscuring root-level parsing and validation errors, ensuring all failures are categorized cleanly into machine-readable buckets [163].

##### Milestone Complexity & Multi-Spec Plan
This specification, M10S8, defines the eighth of the ten sequential contracts specified in the Milestone M10 roadmap [214]. This sequence addresses the failure containment, single-line reporting, and traceback logging isolation boundaries. Subsequent phases will address implementation, evaluation, and review.

#### Functional Requirements

##### FR-1: Core Dependency Validation and Assertion Suppression
Before executing any project-specific test strategy, `bin/omp-test` MUST run a mandatory validation gate on all target specification files (`M10S*.md`, `M10S*V.md`) in the workspace [163].
*   **Validation check:** The runner must execute `python3 bin/validate_metadata.py` against the files.
*   **Suppression:** If any of these validations return a non-zero exit code (1 or 2), the test runner MUST immediately suppress and skip all subsequent Project Execution Strategies (Markdown, Static, Python, AEF) [163]. It is strictly prohibited from running functional assertions against a broken/unvalidated specification layout.

##### FR-2: Standardized Single-Line Diagnostics Summary
When a root-level or validation-level dependency fails, `bin/omp-test` MUST capture the error state and write a single, standardized, high-fidelity diagnostic block to `stderr` [163]:
*   **Format:** The line written to `stderr` must occupy its own clean line and strictly match: `VALIDITY_FAILURE: <specific_reason_or_path_error>`.
*   **Noise Control:** The tool is strictly prohibited from displaying raw Python tracebacks, nested subprocess stdout outputs, or multiline exception messages directly on the standard stream console [163].

##### FR-3: Traceback and Verbose Log Isolation
The tool MUST persist and isolate the full, unsuppressed, verbose stack trace and raw stdout/stderr dumps generated by the failing dependency [163].
*   **Target Log Path:** It must write these details to the dedicated log file `/workspace/scratch/diagnostic_run.log` [163].
*   **Enforcement:** This ensures that the developer has complete, detailed debugging evidence while keeping the automated integration pipeline entirely clean of console noise [163].

--------------------------------------------------------------------------------

#### Non-Functional Requirements
*   **NFR-1 (Bounded Log Growth):** The log file `/workspace/scratch/diagnostic_run.log` must append runs up to 10MB, after which it should overwrite or rotate to prevent workspace disk exhaustion.

#### Data Flow
1. **Input:** Execution command targeted at a test directory.
2. **Pre-flight Validation:** Test runner executes `validate_metadata.py` against workspace files.
3. **Branch Decision:**
    * **If Validation Fails:** Downstream strategies are suppressed. The runner extracts the specific error, writes the single-line summary to `stderr`, appends the traceback to `/workspace/scratch/diagnostic_run.log`, and exits with code 2.
    * **If Validation Passes:** Downstream project-specific tests are executed normally.
4. **Summary Output:** Standardized execution metrics printed to stdout.

--------------------------------------------------------------------------------

#### Implementation Tasks
1. Integrate pre-flight metadata checks inside `bin/omp-test` using `subprocess.run`.
2. Implement functional test suppression on validation check failures.
3. Construct the clean single-line `VALIDITY_FAILURE` string parsing and write to `stderr`.
4. Implement the file redirector for saving unsuppressed traceback outputs to `/workspace/scratch/diagnostic_run.log`.

--------------------------------------------------------------------------------

#### Constraints
*  The tool must use Python standard library modules only (`subprocess`, `sys`, `os`) to maintain environment portability.
*  The log directory `/workspace/scratch/` must be safely created using `os.makedirs` if missing.

--------------------------------------------------------------------------------

#### Assumptions
*  `bin/validate_metadata.py` is present and functional in the path.

#### Acceptance Criteria
*  [ ] Running `bin/omp-test` on a project with malformed YAML specification files immediately aborts test execution.
*  [ ] No project execution strategy runs when metadata checks fail.
*  [ ] The console `stderr` displays exactly one line: `VALIDITY_FAILURE: <reason>`.
*  [ ] No multiline Python traceback is visible on `stdout` or `stderr` upon dependency failure.
*  [ ] Full traceback text is safely stored in `/workspace/scratch/diagnostic_run.log`.
*  [ ] The test runner exits with code 2 on validity failure.
