## Objective

Ensure every canonical artifact (specification, verification, test set, completion, evaluation, review, milestone) has an unambiguous, machine-validatable identity independent of filename. Establish a YAML frontmatter schema and a CLI verification tool that enforces identity correctness, type classification, and lineage traceability across all lifecycle artifacts.

## Functional Requirements

- **FR-1**: The system shall provide a CLI tool for validating canonical YAML frontmatter metadata across lifecycle artifacts.
    - **FR-1.1**: Implement a CLI tool named `bin/omp-verify-metadata`.
    - **FR-1.2**: `bin/omp-verify-metadata` shall accept one or more file paths as positional arguments: `bin/omp-verify-metadata <file1> [file2 ...]`.
    - **FR-1.3**: `bin/omp-verify-metadata` shall exit with status code `0` if all analyzed files contain valid, schema-compliant YAML frontmatter.
    - **FR-1.4**: `bin/omp-verify-metadata` shall exit with status code `1` if any file fails schema validation, is missing required fields, or contains invalid field types.
    - **FR-1.5**: `bin/omp-verify-metadata` shall exit with status code `1` if a provided file path does not exist.
    - **FR-1.6**: `bin/omp-verify-metadata` shall produce human-readable error messages on stderr indicating which file failed and why. (These messages are for diagnostic purposes only; the test oracle MUST assert exit codes, not prose.)

- **FR-2**: The YAML frontmatter schema governing all canonical artifacts shall enforce the following fields:
    - **FR-2.1**: `id` — type: string, required. Must be non-empty. **Must reject** any value containing a semantic qualifier suffix such as `-CORRECTED`, `-FINAL`, `-V2`, `-V3`, `-FIXED`, `-REVISED`, or any hyphenated suffix composed entirely of uppercase letters or version numbers.
    - **FR-2.2**: `type` — type: string, required. Must be one of the following enum values: `specification`, `verification`, `test_set`, `completion`, `evaluation`, `review`, `milestone`.
    - **FR-2.3**: `milestone_id` — type: string, required. Must be non-empty (e.g., `M10`).
    - **FR-2.4**: `derived_from` — type: array of strings, optional. When present, each element must be a non-empty string.
    - **FR-2.5**: `supersedes` — type: array of strings, optional. When present, each element must be a non-empty string.

- **FR-3**: Test isolation and expected failure semantics shall validate the tool against static fixtures:
    - **FR-3.1**: Tests shall execute `bin/omp-verify-metadata` against the static isolated fixture directory `tests/fixtures/synthetic_metadata_valid/`, which contains markdown files with valid, schema-compliant YAML frontmatter.
    - **FR-3.2**: Tests shall execute `bin/omp-verify-metadata` against the static isolated fixture directory `tests/fixtures/synthetic_metadata_invalid/`, which contains files with missing fields, invalid types, or IDs containing prohibited qualifiers (e.g., `-V2`).
    - **FR-3.3**: Test oracles for `bin/omp-verify-metadata` shall assert exit codes programmatically. The test oracle MUST NOT attempt to regex-parse or assert against the prose content of error messages.

## Data Flow

1. User invokes `bin/omp-verify-metadata <path1> [path2 ...]`.
2. For each file path provided:
   a. Verify the file exists on disk. If not, report error, final exit code = 1.
   b. Read the file and extract YAML frontmatter (between leading `---` delimiters). If no frontmatter, report error, final exit code = 1.
   c. Parse YAML into a structured object.
   d. Validate each required field (`id`, `type`, `milestone_id`) for presence and type correctness.
   e. Validate `type` against the allowed enum.
   f. Validate `id` contains no prohibited semantic qualifier suffixes.
   g. Validate optional fields (`derived_from`, `supersedes`) for type correctness if present.
3. After all files are processed, exit with code 0 if every file passed; exit with code 1 otherwise.
4. Human-readable error details are written to stderr for diagnostic purposes.

## Implementation Tasks

1. Create `bin/omp-verify-metadata` as a Python (or Bash) script.
2. Implement argument parsing for one or more positional file path arguments.
3. Implement YAML frontmatter extraction (parse content between leading `---` markers).
4. Implement field-level validation: `id` (non-empty string, no qualifier suffixes), `type` (enum check), `milestone_id` (non-empty string), `derived_from` (array of strings, optional), `supersedes` (array of strings, optional).
5. Implement exit code semantics: 0 for all valid, 1 for any invalid or missing file.
6. Implement stderr error reporting per-file.
7. Create test fixture directories with valid and invalid frontmatter files.
8. Ensure the tool handles files without YAML frontmatter gracefully (exit 1, clear stderr message).

## Constraints

- The tool MUST NOT modify any files it validates.
- The tool MUST support both Python 3 and Bash implementations; Python is preferred for robust YAML parsing.
- Semantic qualifier detection in `id` MUST reject any hyphenated trailing suffix composed exclusively of uppercase ASCII letters, digits, or hyphen separators (e.g., `-CORRECTED`, `-FINAL`, `-V2`, `-REVISED`, `-FIXED`). Plain IDs like `SPEC-M10S1` or `M10S1` are valid.
- Test fixtures must be static and isolated from the active workspace.

---

## Assumptions

- Target environment has Python 3 or a POSIX-compatible shell with `yq`/Python available for the tool implementation.
- YAML frontmatter in markdown files follows the standard `---` ... `---` delimiter convention.
- No canonical artifact will have a YAML frontmatter section of such size that file I/O becomes a bottleneck.
