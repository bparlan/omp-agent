#### Objective
Ensure that all newly generated test scripts and test plans are actively tracked within the repository's Git index before advancing the lifecycle [163]. This prevents the "false progress trap" where transient, unsaved, or uncommitted files are executed during evaluation sweeps but lost in subsequent agent sessions [153, 163].

##### Milestone Complexity & Multi-Spec Plan
This specification, M10S9, defines the ninth of the ten sequential contracts specified in the Milestone M10 roadmap [213]. This contract establishes the CLI signature, git-parsing mechanics, and precondition hooks required for tracking file persistence.

#### Functional Requirements

##### FR-1: Git Integrity CLI Contract
The system MUST provide a CLI utility at `bin/omp-verify-git-integrity` that parses the active test plan ledger and audits version-control tracking [163].
*   **Command:** `bin/omp-verify-git-integrity`
*   **Arguments:**
    *   `--ledger <test_ledger_path>`: (Required) Path to the active Markdown test plan ledger (e.g., `milestones/M10/M10S9T1.md`) [250].
*   **Exit Codes:**
    *   **0 (PASS):** All test files listed in the ledger are actively tracked by Git (either clean, modified, or staged) [163].
    *   **1 (BLOCKED):** One or more test files listed in the ledger are untracked (`??` status) or ignored by Git [163].
    *   **2 (VALIDITY_FAILURE):** The command is executed outside a Git repository, the specified ledger is missing/malformed, or required arguments are absent.

##### FR-2: Short-Status Programmatic Parser
`bin/omp-verify-git-integrity` MUST parse tracking states programmatically using raw, low-overhead version control checks.
*   **Mechanics:** The tool shall execute `git status --short -- <file_path>` for each test file parsed from the ledger.
*   **Parsing Logic:**
    *   If the command stdout is empty, the file is tracked and unchanged.
    *   If the stdout starts with `A ` or `M ` (staged) or ` M` (unstaged modifications), the file is tracked.
    *   If the stdout starts with `??`, the file is untracked [163].
    *   If the command exits with a non-zero status (e.g., not a git repository), the tool must output a diagnostic block to stderr and exit with code 2.

##### FR-3: Pre-Implementation Gate Integration
`bin/omp-verify-precondition` MUST invoke `bin/omp-verify-git-integrity` as an immutable pre-flight check before executing baseline tests [160, 163].
*   **Enforcement:** If `bin/omp-verify-git-integrity` exits with code 1 or 2, the precondition gate MUST fail-closed, write a diagnostic message to stderr, and exit with code 1, blocking all downstream implementation.

--------------------------------------------------------------------------------

#### Non-Functional Requirements
*   **NFR-1 (Read-Only Safety):** The git verifier is strictly read-only relative to the workspace. It MUST NOT execute `git add`, `git commit`, `git reset`, or `git clean` [590].
*   **NFR-2 (No Prose Parsing):** The verifier must inspect explicit two-character status codes returned by `git status --short` and must never regex-match human-readable natural language output from standard `git status`.

#### Data Flow
1. **Input:** Path to the active test plan ledger.
2. **Parsing:** Extract all "Test File" paths from the Markdown table.
3. **Audit Loop:** Execute `git status --short` against each file.
4. **Validation:** Check if any file is prefixed with `??` or is missing from the index.
5. **Output:** Return exit status 0 (PASS), 1 (BLOCKED), or 2 (VALIDITY_FAILURE).
