# M10 — Project-Agnostic Artifact Lifecycle & Safe-to-Proceed Development Pipeline (Contract-Grounded)

## Goal

Establish a project-agnostic, metadata-driven, specification-to-implementation workflow for AEF/OMP that can safely operate across radically different project types without assuming the project technology, structure, or artifact layout.

The new system must make all lifecycle failure classes explicit and machine-detectable:

1. Specifications being renamed or consolidated outside the assumptions of downstream skills.
2. Verification artifacts lacking reliable canonical metadata.
3. `generate-tests` producing tests that are not traceable to the actual canonical specification.
4. Tests checking assumptions that are absent from, or semantically different from, the active specification.
5. Test scripts being generated with malformed, text-only, or corrupted content.
6. Tests being executed against the wrong artifact or wrong specification version.
7. Tests being incorrectly interpreted as proving implementation readiness.
8. Implementation being blocked by failures caused by specification/test mismatch rather than missing implementation.
9. Distinguishing invalid tests, incomplete specifications, missing implementation, environment failures, fixture failures, and infrastructure failures.
10. Large test output obscuring the actual first failure and making diagnosis unnecessarily difficult.

---

## Architectural Principles & Core Guardrails

### 1. The "Example Exclusion Fence" (Anti-Few-Shot Contamination)

To prevent LLM-based agents from suffering from completion bias and copying mock templates, a strict architectural ban is enforced on few-shot examples inside skills:

- **No Generator Few-Shots:** Core generator skills (such as `generate-spec`, `generate-verification`, and `generate-tests`) are STRICTLY PROHIBITED from containing specific domain few-shot examples (like "User Profile Service" or "bin/omp-profile") in their prompt instructions.
- **Pure Schema Constraints:** Skills must be instructed using pure-prose structural rules, schema constraints, and meta-level definitions. They must derive concrete CLI names, API routes, and data schemas exclusively by translating the active milestone definition (`M10.md`) into a logical design.
- **The Example Fence:** If formatting examples are necessary, they must use highly abstract placeholders (e.g., `M{X}S{Y}`, `bin/omp-command`, `param1`) to ensure they are mathematically impossible to copy-paste as literal code targets.

### 2. The Interface Contract Mandate

Specifications must never be written in passive prose. Every functional requirement (FR) must define a machine-observable interface contract:

- **CLI Executable Contract:** Exposes a command line interface with explicit arguments, exit codes, and stdout/stderr expectations.
- **Structured Output Contract:** Declares a deterministic JSON or YAML output schema with non-negotiable keys.
- **Oracle-Isolated Fixtures:** Requires tests to run against static, unchanging directory fixtures rather than the moving target of the active workspace.

## SPECIFICATION SET: THE 10-SPEC CONTRACTS

This milestone is decomposed into exactly 10 sequential specifications. To prevent downstream speculation, each specification is bounded by a concrete interface contract:

### M10S1 — Project Context & Artifact Discovery Contract

- **Objective:** Define how AEF/OMP understands the project in which it is operating without assuming the project technology, structure, or domain.
- **Interface Contract (CLI):** `bin/omp-discover`
  - Command: `bin/omp-discover --path <target_directory>`
  - Exit Semantics: Exits with 0 on successful profiling, 1 on invalid path.
- **Output Schema (JSON):**
  ```json
  {
    "project_slug": "my-app",
    "project_kind": "application | framework | hybrid",
    "capabilities": ["python", "static_site", "documentation", "mixed"],
    "artifact_root": "./milestones",
    "active_skills_path": "./agent/skills"
  }
  ```
- **Test Fixtures:** Must execute against static, isolated fixtures: [174]
  - `tests/fixtures/synthetic_python/`
  - `tests/fixtures/synthetic_static/`
  - `tests/fixtures/synthetic_docs/`
- **Test Oracle:** Must assert keys and structures programmatically using `jq` or JSON parsing (never regexing English text).

### M10S2 — Canonical Artifact Identity & Lineage Contract

- **Objective:** Ensure every canonical artifact has an unambiguous identity independent of filename. [154]
- **Schema Contract (YAML Frontmatter):** Every specification, verification, test set, and completion report must contain:
  - `id`: Unique canonical identifier (e.g., `SPEC-M10S1`).
  - `type`: Semantic classification (`specification`, `verification`, `test_set`, `completion`).
  - `milestone_id`: Parent milestone identifier (`M10`).
  - `derived_from`: Lineage trace tracking parent/source artifact IDs.
  - `supersedes`: (Optional) Lists previous specification ID if scope has changed.
- **Interface Contract:** A Python/Bash metadata extraction utility `bin/omp-verify-metadata` that parses and validates this schema across all active files.

### M10S3 — Specification → Verification Contract

- **Objective:** Prevent verification documents from inventing requirements that do not exist in the specification.
- **Traceability Rule:** Every verification criterion in `M10S1V.md` must map back to an explicit requirement ID (e.g., `FR-1` through `FR-7`). Any verification item lacking a source ID must fail validation.
- **Active Verification Mandate:** Active system features must be verified using `SCRIPT_EXECUTION` or `UNIT_TEST` targeting the executable code. `DOCUMENT_CHECK` is strictly reserved for verifying static documents or frontmatter structures.

### M10S4 — Verification → Test Generation Contract

- **Objective:** Prevent `generate-tests` from generating tests based on assumptions not represented in the verification protocol.
- **Test Ledger:** `generate-tests` must output a test plan (`M10S1T1.md`) containing a deterministic mapping of Test File Paths to Verification IDs and Requirement IDs.
- **Traceability comments:** Every generated test script must begin with:
  - `# {Verification IDs: V-FR-1}`
  - `# {Requirement IDs: FR-1}`

### M10S5 — Test Validity & Precondition Gate

- **Objective:** Distinguish implementation failures from environment, specification, or test failures before implementation starts.
- **Pre-Implementation Gate:** Run all generated tests against the blank codebase.
- **Expected State (VALID_INITIAL_FAILURE):**
  - Environment, Specification, and Fixture checks must return `PASS`.
  - Executable implementation tests must fail naturally with exit code `127` (Command Not Found) or `1` (Assertion Failed). This natural failure is the green light to proceed.
  - Any syntax errors, self-scanning, or environment contamination must trigger an `INVALID_TEST` (exit code 2) and block the implementation pipeline immediately.

### M10S6 — Project-Agnostic Test Execution Contract

- **Objective:** Tailor the test framework and execution logic to the type of project under test without imposing a universal testing technology.
- **Execution Strategy:**
  - Markdown projects use structural metadata and frontmatter parsing.
  - Static HTML/CSS projects use DOM and class assertions.
  - Python projects use `pytest` and pytest assertions.
  - Framework/AEF tasks use isolated, synthetic fixtures and shell execution scripts.

### M10S7 — Safe-to-Proceed Implementation Gate

- **Objective:** Prevent the implementation skill from starting work or guessing test states if upstream gates are red.
- **Gate Constraint:** The `implement-specification` skill must check the state of the Precondition Gate and the YAML frontmatter user approval stamp (`#### User Approval`) before touching a single line of production code.

### M10S8 — Failure Classification & Diagnostic Contract

- **Objective:** Prevent cascading errors from obscuring the root cause of a failure. [164]
- **Diagnostic Rule:** If a root-level dependency (like YAML parsing) fails, the test runner must suppress downstream assertion errors and output a single, high-fidelity root cause diagnostic report first. Bounded terminal outputs must be enforced, and full debug logs must be written to a dedicated file in `/workspace/scratch/`.

### M10S9 — Artifact Persistence & Git Integrity Contract

- **Objective:** Guarantee that generated test files and specifications are actively tracked in Git to eliminate the false-progress trap.
- **Persistence Gate:** After test generation, the system must check `git status --short`. All newly generated files must be actively tracked in the index before proceeding.

### M10S10 — Multi-Project Compatibility & Migration Contract

- **Objective:** Support legacy AEF projects without forcing immediate migration or silently mutating historical files.
- **Migration Rule:** The metadata validator must gracefully handle legacy documents lacking YAML frontmatter by treating them under a "legacy compatibility layer," separating them from newly generated canonical artifacts.

## REQUIRED NEGATIVE GUARDRAILS (IMMUTABLE PROCESS LIMITS)

The system MUST NOT:

1. Include specific domain few-shot examples inside skill prompts (e.g., no "User Profile Service" few-shots).
2. Allow specifications to be written in passive, non-verifiable prose.
3. Permit implementation to begin if tests are missing, syntax-broken, or untested against a blank codebase.
4. Weaken, alter, skip, or rewrite test assertions to make a failing pipeline pass.
5. Trust self-asserted completion reports as proof of success without executing raw shell validation commands.
6. Use a single, universal test technology (like Bash) for projects that contain no shell scripts.
7. Merge development skills from the read-write workspace (`agent/skills/`) to production (`skills/`) without executing `scripts/release.sh`.

## FINAL SUCCESS CRITERIA

This milestone is complete only when:

1. `bin/omp-discover` successfully profiles Python, static site, and documentation repositories.
2. The entire SDD pipeline executes autonomously and deterministically from `generate-spec` to `review-implementation` using the updated skills.
3. The generator skills function flawlessly without copying templates or overfitting.
4. All test outputs are captured and logged to the `#### Raw Evidence` sections.
