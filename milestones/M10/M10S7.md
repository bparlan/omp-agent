#### Objective

Prevent the implementation agent (implement-specification) from starting code modifications or guessing baseline test states if upstream gates are incomplete, red, or missing human approval. S7 introduces a mechanical pre-flight verification step that blocks the agent from touching a single line of code until approval is explicitly verified and baseline tests are in a verified TDD state.

##### Milestone Complexity & Multi-Spec Plan

The milestone M10 is explicitly decomposed into 10 sequential specifications, as detailed in M10.md. This specification (M10S7) addresses a specific part of that decomposition. No further breakdown is required for this sequence.

#### Functional Requirements

##### FR-1: Readiness Verification Pre-flight Check

The implement-specification skill MUST initiate a pre-flight check using the bin/omp-verify-readiness CLI tool before executing any implementation code. This check ensures that all necessary upstream gates (user approval and valid test states) are met.

- **Contract:** `bin/omp-verify-readiness --spec milestones/M10/M10S7.md --test-dir tests/M10/`
- **Expected Exit Codes:**
  - 0 (PASS): Specification has valid user approval and tests are in VALID_INITIAL_FAILURE or SPECIFICATION_CHECK pass state.
  - 1 (BLOCKED): Missing user approval stamp or tests are in an invalid state (uncompiled, syntax-broken).
  - 2 (VALIDITY_FAILURE): Missing specification file, test plan ledger, or incorrect path arguments.

##### FR-2: Specification Approval Stamp Verification

The bin/omp-verify-readiness tool MUST verify the presence of an explicit user approval stamp within the target specification file. This stamp is defined as:
#### User Approval
* [x] Approved for implementation by user
If this stamp is absent, the tool MUST write `BLOCKED: Specification lacks human approval` to stderr and exit with code 1.

##### FR-3: Test Readiness State Verification

The bin/omp-verify-readiness tool MUST verify that the testing environment for the specified test directory (--test-dir) is in a valid state. A valid state is defined as tests passing or being in a VALID_INITIAL_FAILURE state (as defined by M10S5). If tests are in an invalid state (e.g., syntax errors, corrupted fixtures), the tool MUST exit with code 1.

#### Data Flow

1. The implement-specification skill initiates its execution.
2. It first calls `bin/omp-verify-readiness`, passing the path to the current specification (milestones/M10/M10S7.md) and the test directory (tests/M10/).
3. `omp-verify-readiness` checks the specification for the approval stamp and the test directory for readiness state.
4. Based on the exit code of `omp-verify-readiness`:
   - If 0 (PASS), implement-specification proceeds.
   - If 1 (BLOCKED) or 2 (VALIDITY_FAILURE), implement-specification halts and reports the error.

---

#### Constraints

- The readiness check must be performed before any code modification or test execution by the implement-specification skill.
- The tool bin/omp-verify-readiness must be written in Python.
- Exit codes must strictly adhere to the defined PASS, BLOCKED, and VALIDITY_FAILURE semantics.

---

#### Assumptions

- The bin/omp-verify-readiness tool will be placed in the bin/ directory.
- The implement-specification skill is capable of invoking CLI tools and interpreting their exit codes.
- The user approval stamp format is precise and must be matched exactly.
