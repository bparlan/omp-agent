## Edge Cases

### EC-1: No verification protocol provided
- **Scenario**: `generate-tests` is invoked without a valid `M{X}S{Y}V.md` file
- **Expected**: Clear error message, no files written, exit code != 0
- **Verification**: Test by running against a non-existent path

### EC-2: Empty verification protocol
- **Scenario**: Verification protocol has no test requirements defined
- **Expected**: `generate-tests` produces a warning about empty verification, no test files written
- **Verification**: Manual test with stripped-down verification

### EC-3: Target test directory already populated
- **Scenario**: `tests/M{X}/` already contains files from a previous run
- **Expected**: New files are added without removing existing files; no overwrite without confirmation
- **Verification**: Check behavior when directory exists

### EC-4: Language-ambiguous test definition
- **Scenario**: Verification protocol does not specify whether tests should be `.sh` or `.py`
- **Expected**: `generate-tests` defaults to `.sh` (shell) with clear note in output
- **Verification**: Manual review of SKILL.md for default behavior documentation

### EC-5: Production path collision
- **Scenario**: A test fixture path inadvertently matches a production directory pattern
- **Expected**: Guardrail classification catches it. If classified as TEST_FIXTURE, allowed. If ambiguous, prompt classification. If misclassified as PRODUCTION_IMPLEMENTATION, halt.
- **Verification**: Test with a path like `src/test_helper.sh` in the proposed test directory

### EC-6: Test that accidentally passes pre-implementation
- **Scenario**: Generated test passes before implementation (feature already exists or test is too weak)
- **Expected**: `WARNING: PRE-IMPLEMENTATION TEST PASSES` emitted. Investigation note generated. Pipeline does NOT halt.
- **Verification**: Manual — inject a test for an already-implemented feature

### EC-7: All generated tests pass (pre-implementation)
- **Scenario**: Every test in the suite passes before implementation
- **Expected**: Warning for each test. Machine-readable summary shows PASSED=N, FAILED=0, EXIT_CODE=0. Investigation recommended.
- **Verification**: Test scenario where `generate-tests` targets an implemented spec

## Failure Scenarios

### FS-1: Guardrail fails to block production write
- **Scenario**: `generate-tests` attempts to write a file in `src/` or `lib/`
- **Expected**: Guardrail detects PRODUCTION_IMPLEMENTATION, halts with error, no file written
- **Failure state**: File written to production path — this is a critical framework bug
- **Verification**: Test G verifies this behavior; run after every `generate-tests` change

- **NFR-2 Determinism**: Test that running `generate-tests` twice against the same inputs produces identical output structure. Use `diff` on output file listing, not timestamps.
