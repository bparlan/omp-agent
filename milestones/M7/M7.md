## Goal

Restore test-first integrity to the OMP AEF SDD pipeline by making `generate-tests` deterministic — it MUST produce executable tests that initially fail, and it MUST NEVER create or modify production implementation code.

---

## Motivation

### Current Failure Mode

The AEF has a critical failure in the `generate-tests` phase. The framework is beginning to generate implementation-oriented code when it is supposed to generate tests only.

The most likely cause is contamination from existing test-plan templates, examples, pseudo-code, or implementation snippets embedded in lifecycle artifacts. Previous investigation identified that test-plan templates included Python implementation-like code inside `.sh` test artifacts, causing generated test files to contain invalid or misplaced implementation code.

This violates the intended separation of concerns:

```
generate-spec
    → defines what must be built

generate-verification
    → defines how correctness will be verified

generate-tests
    → creates executable tests that initially fail against the current implementation

approve-spec
    → human approval gate

implement-specification
    → writes production implementation code
```

### Critical Invariant

`generate-tests` MUST NOT implement the requested feature. It MUST NOT:

- Write production source code
- Modify application/framework implementation files
- Create helper implementations that make the target tests pass
- Copy pseudo-code from specifications into production source files
- Convert specification examples into production code
- Silently "fix" failing tests
- Modify existing implementation files to satisfy generated tests
- Run an implementation loop
- Invoke `implement-specification`
- Behave as an implementation agent

The only implementation-related output allowed is test infrastructure required to execute the test itself, and even that must be clearly separated from production implementation.

If a generated test requires production code that does not yet exist, the test must remain **failing**.

### Consequences of Inaction

Without this remediation:

- `generate-tests` will continue producing or leaking implementation code
- The boundary between testing and implementation erodes permanently
- Generated tests may accidentally pass without the actual feature being implemented
- Pipeline integrity is lost — `implement-specification` becomes redundant
- Test artifacts cannot be trusted as evidence of missing behavior
- The SDD lifecycle degrades to a speculative generation loop

## Scope

### In Scope

1. **Investigation** — Before modifying any files, inspect the current AEF implementation and identify the exact contamination path. Produce an investigation report answering:
   - Why does `generate-tests` see implementation-like content?
   - Which exact files or templates contain the contamination?
   - Which instructions cause the model to cross the test/implementation boundary?
   - Why are executable test files not reliably being created?
   - Why do generated test artifacts sometimes contain pseudo-code instead of executable tests?
   - Which existing M6/M6S1/M6S1V artifacts were affected or deleted by recent changes?
   - What is the smallest safe fix?

2. **Define the Test Contract** — Before generating any new test files, define a strict contract for `generate-tests`. A generated test artifact must contain:
   - Test purpose
   - Source specification ID
   - Source verification ID
   - Executable test file path(s)
   - Test setup
   - Test execution command
   - Expected initial result (failure)
   - Expected post-implementation result (pass)
   - Pass/fail semantics
   - Exit-code semantics
   - Clear distinction between TEST DESIGN DOCUMENTATION and EXECUTABLE TEST FILE

3. **Test-First Requirement** — Every generated implementation test must initially fail before implementation. The intended lifecycle:
   ```
   generate-spec → generate-verification → generate-tests → RUN TESTS → EXPECT FAILURE → HUMAN APPROVAL → implement-specification → RUN TESTS → EXPECT PASS
   ```
   If a generated test passes before implementation, classify as `WARNING: PRE-IMPLEMENTATION TEST PASSES` and investigate.

4. **Executable Test Requirements** — Generated tests must be real executable files:
   - `.sh` files: valid Bash/POSIX shell syntax, valid shebang, executable, exit code 0 on success, non-zero on failure, no Python/TypeScript/JavaScript/pseudo-code syntax
   - `.py` files: valid Python, use project's test runner, no shell syntax embedded as Python
   - Never generate `test.sh` containing Python classes/functions
   - File extension and execution mechanism must match the actual language

5. **Hard Boundary Against Implementation** — Add explicit guardrails to `generate-tests`. Before writing any file, classify it as one of:
   - TEST_ARTIFACT
   - TEST_FIXTURE
   - TEST_HELPER
   - PRODUCTION_IMPLEMENTATION
   - DOCUMENTATION
   
   `generate-tests` may create or modify only TEST_ARTIFACT, TEST_FIXTURE, TEST_HELPER (if strictly required). Must NEVER create or modify application source, framework source, production configuration, production templates, production source files, or implementation modules.

6. **Tests for the Test Generator** — Create tests that verify the behavior of `generate-tests` itself:
   - **Test A**: Generates executable test files (correct extension, interpreter, valid syntax)
   - **Test B**: Generated test initially fails (exit code non-zero, failure from missing implementation)
   - **Test C**: No production files modified (repository state before/after)
   - **Test D**: No pseudo-code leakage (`.sh` must not contain Python syntax)
   - **Test E**: No implementation snippets (no copied production implementation patterns)
   - **Test F**: Existing artifacts preserved (M6/M6S1/M6S1V unchanged)
   - **Test G**: Test failure does not trigger implementation

7. **Mandatory Test Generation Output** — When `generate-tests` completes, it must produce:
   - A test design document
   - One or more actual executable test files
   - A test execution command
   - A pre-implementation execution result
   - A machine-readable summary: TESTS_RUN, TESTS_PASSED, TESTS_FAILED, EXIT_CODE

### Out of Scope

1. **Artifact Migration** — Do not rename, move, delete, rewrite, or reorganize existing milestone artifacts. Protect all existing M3, M4, M5, M6 and historical milestones. Treat existing artifacts as immutable by default.

2. **Bulk Convention Changes** — No migration or bulk renaming to match new conventions. Legacy support means existing artifacts remain accessible, not migrated.

3. **Architecture Redesign** — Do not redesign internal domain logic of individual SDD skills beyond `generate-tests`. Each skill owns its specific responsibilities.

4. **Implementing Production Code** — This milestone does not write or test production implementation. Implementation work belongs to a later lifecycle stage after specification, verification, tests, and human approval.

5. **Artifact Identity System** — Do not introduce a new canonical artifact identity or type detection system. That work (if needed) belongs to a separate milestone.

## Success Criteria

### Primary Success Criteria

1. **`generate-tests` no longer creates production implementation code.** Modified or generated files during test generation are exclusively test artifacts.
2. **Generated tests are actual executable files.** Valid shebang, correct interpreter, runnable from a clean shell, syntactically valid for the target language.
3. **Generated tests initially fail for the expected reason.** Exit code is non-zero. Failure is attributable to missing implementation.
4. **Test failure does not trigger implementation.** `generate-tests` stops at test failure. It does not invoke `implement-specification` or write production code.
5. **Test artifacts contain no misleading pseudo-code.** No Python in `.sh` files. No implementation snippets from specification examples.
6. **Hard boundary guardrails are mechanically enforced in `generate-tests`.** File classification before write. Stop and report on attempted production implementation writes.
7. **The exact original failure scenario is reproduced as a regression test.** Proven by executing the test and observing the expected failure.
8. **Generated test suite can be consumed by `implement-specification` later.** Test files are discoverable, runnable, and map to specification/verification IDs.

### Secondary Success Criteria

9. **Investigation report produced** identifying root cause, contaminated files/templates, affected skills, and affected artifacts.
10. **Test Contract documented** as a canonical reference for `generate-tests` behavior.
11. **Tests for the test generator** (Tests A–G) exist and pass against the fixed framework.
12. **Machine-readable test summary** (TESTS_RUN, TESTS_PASSED, TESTS_FAILED, EXIT_CODE) produced at test-generation completion.
13. **Existing M6/M6S1/M6S1V and other historical artifacts remain untouched.** No deletion, renaming, or reorganization.
14. **No production files modified during test generation.** Verified by repository state comparison.

## Risks

### Risk 1: Breaking Existing Test Workflows

**Description**: Changes to `generate-tests` behavior may break existing test generation workflows for in-progress milestones (M5, M6).

**Impact**: MEDIUM

**Mitigation**:
- Maintain backward compatibility for existing milestone structures
- Add guardrails without removing existing capabilities
- Test against existing milestone artifacts to verify no regression
- Document any behavioral changes clearly

### Risk 2: Guardrails Are Too Restrictive

**Description**: Overly strict guardrails may prevent legitimate test infrastructure creation (test fixtures, helper scripts, mock data generators).

**Impact**: MEDIUM

**Mitigation**:
- Allow TEST_FIXTURE and TEST_HELPER classifications for necessary infrastructure
- Define clear criteria for what constitutes a TEST_HELPER vs PRODUCTION_IMPLEMENTATION
- Provide override path with explicit justification
- Review classification during evaluation phase

### Risk 3: Test-First Enforcement Causes Pipeline Blockage

**Description**: Strict test-first requirements may block the pipeline if existing implementation already satisfies a new test (accidental pre-implementation pass).

**Impact**: LOW

**Mitigation**:
- Pre-implementation pass triggers WARNING and investigation, not pipeline halt
- Clear documentation of what to do when a test passes before implementation
- Investigation determines whether feature already exists or test is too weak

### Risk 4: Investigation Reveals Deeper Problems

**Description**: The required investigation may reveal contamination paths that extend beyond `generate-tests` into shared templates, skill instructions, or the model's own behavior.

**Impact**: Medium — may expand scope

**Mitigation**:
- Investigation is read-only; document all findings
- If depth exceeds this milestone's scope, produce a separate follow-up milestone
- Focus on the smallest safe fix for `generate-tests` as the primary deliverable
