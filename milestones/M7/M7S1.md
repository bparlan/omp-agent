## Objective

Make `generate-tests` deterministic by: (a) investigating the exact contamination path causing it to generate implementation code, (b) adding hard guardrails to prevent crossing the test/implementation boundary, (c) enforcing test-first semantics where generated tests must initially fail, (d) requiring executable test files with language-correct syntax, and (e) creating a test suite (Tests A–G) that verifies the fixed behavior of `generate-tests` itself.

### Multi-Spec Plan

This milestone is suitable for a **single specification (M7S1)**. All parts are deeply interdependent:

- Investigation must precede any modification
- The fix is driven directly by investigation findings
- Tests for the test generator require the fixed `generate-tests` to exist
- All work targets one skill (`generate-tests`) and its consumed template (`test_template.md`)

## Functional Requirements

### FR-1: Investigation Phase (Read-Only)

The system MUST produce an investigation report (`milestones/M7/M7INVESTIGATION.md`) that documents:

- **FR-1.1**: Root cause — Why does `generate-tests` see implementation-like content?
- **FR-1.2**: Exact file/template list — Which specific files or templates contain contamination (pseudo-code, implementation snippets, mock implementations, instruction leakage)?
- **FR-1.3**: Instruction analysis — Which instructions in `skills/generate-tests/SKILL.md` or consumed templates cause the model to cross the test/implementation boundary?
- **FR-1.4**: Executable test gap — Why are executable test files not reliably created?
- **FR-1.5**: Pseudo-code analysis — Why do generated test artifacts sometimes contain pseudo-code instead of executable tests?
- **FR-1.6**: Artifact status — Which existing M6/M6S1/M6S1V artifacts were affected or deleted by recent changes?
- **FR-1.7**: Smallest safe fix — What is the minimal change set to restore determinism?

During investigation, NO files may be modified. All findings are documented in the report.

### FR-2: Test Contract

The system MUST define a strict contract for test artifact generation, embedded in `skills/generate-tests/SKILL.md`:

- **FR-2.1**: Every generated test artifact MUST contain all of: test purpose, source specification ID, source verification ID, executable test file path(s), test setup, test execution command
- **FR-2.2**: Every generated test artifact MUST document expected initial result (failure) and expected post-implementation result (pass)
- **FR-2.3**: Test artifacts MUST distinguish clearly between TEST DESIGN DOCUMENTATION (`.md` plan files) and EXECUTABLE TEST FILE (`.sh`/`.py` runnable scripts)
- **FR-2.4**: Exit-code semantics MUST be documented: exit 0 = PASS, non-zero = FAIL
- **FR-2.5**: No pseudo-code or production implementation examples may appear in test artifacts

### FR-3: Test-First Enforcement

The system MUST enforce test-first semantics:

- **FR-3.1**: Every generated executable test MUST initially fail against the current (pre-implementation) codebase
- **FR-3.2**: `generate-tests` MUST NOT attempt to make tests pass by writing production code
- **FR-3.3**: If a generated test passes before implementation, `generate-tests` MUST classify this as `WARNING: PRE-IMPLEMENTATION TEST PASSES` and include an investigation note
- **FR-3.4**: `generate-tests` MUST run the generated tests and capture their exit codes before reporting completion
- **FR-3.5**: The initial failure MUST be attributable to missing implementation (not test infrastructure bugs)
- **FR-3.6**: Machine-readable test results MUST be reported: TESTS_RUN, TESTS_PASSED, TESTS_FAILED, EXIT_CODE

### FR-4: Executable Test File Requirements

The system MUST generate real, runnable executable test files:

- **FR-4.1**: `.sh` files MUST contain valid Bash/POSIX shell syntax, have a valid shebang (`#!/bin/bash` or `#!/usr/bin/env bash`), be executable (`chmod +x`), return exit code 0 on success, and return non-zero on failure
- **FR-4.2**: `.py` files MUST contain valid Python, use the project's test runner (pytest), and not embed shell syntax as Python
- **FR-4.3**: `.sh` files MUST NOT contain Python, TypeScript, JavaScript, or pseudo-code syntax
- **FR-4.4**: File extension MUST match the language of syntax — `.sh` = bash only, `.py` = Python only
- **FR-4.5**: `generate-tests` MUST run syntax validation (`bash -n` for `.sh`, `python -m py_compile` for `.py`) and refuse to report completion until all scripts pass syntax validation
- **FR-4.6**: Never generate a `.sh` file containing Python classes, functions, or method definitions

### FR-5: Hard Boundary Guardrails

The system MUST add explicit guardrails to `skills/generate-tests/SKILL.md`:

- **FR-5.1**: Before writing any file, `generate-tests` MUST classify the write target as one of: `TEST_ARTIFACT`, `TEST_FIXTURE`, `TEST_HELPER`, `PRODUCTION_IMPLEMENTATION`, `DOCUMENTATION`
- **FR-5.2**: `generate-tests` MAY create or modify only: `TEST_ARTIFACT`, `TEST_FIXTURE`, `TEST_HELPER` (if strictly required for test execution)
- **FR-5.3**: `generate-tests` MUST NEVER create or modify: application source, framework source, production configuration, production templates, production source files (`.ts`, `.js`, `.py` in `src/` etc.), or implementation modules
- **FR-5.4**: If `generate-tests` detects that a proposed write targets a production implementation path, it MUST halt with a clear error: `STOP: generate-tests attempted to write production implementation. This is prohibited. Required action: defer implementation to implement-specification.`
- **FR-5.5**: The guardrails MUST be a mechanically enforced step in the `generate-tests` process, not a soft suggestion

### FR-6: Mandatory Test Generation Output

When `generate-tests` completes, it MUST produce:

- **FR-6.1**: A test design document at `milestones/M{X}/M{X}S{Y}T{Z}.md`
- **FR-6.2**: One or more executable test files at `tests/M{X}/`
- **FR-6.3**: A documented test execution command
- **FR-6.4**: A pre-implementation execution result (captured from actually running the tests)
- **FR-6.5**: A machine-readable summary at the end of output: `TESTS_RUN=N`, `TESTS_PASSED=N`, `TESTS_FAILED=N`, `EXIT_CODE=N`

### FR-7: Tests for the Test Generator (Tests A–G)

The system MUST create a test suite that verifies `generate-tests` behavior:

- **FR-7.1 (Test A)**: Verify that `generate-tests` generates executable test files with correct extension, correct interpreter, and valid syntax
- **FR-7.2 (Test B)**: Verify that generated tests initially fail (exit code non-zero) and failure is attributable to missing implementation
- **FR-7.3 (Test C)**: Verify that no production files are modified during test generation — capture repo state before/after and assert only approved test artifacts changed
- **FR-7.4 (Test D)**: Verify no pseudo-code leakage — scan generated `.sh` files for Python syntax, assert zero matches
- **FR-7.5 (Test E)**: Verify no implementation snippets — scan generated test files for known production implementation patterns or copied blocks from specification examples
- **FR-7.6 (Test F)**: Verify that existing milestone artifacts (M6/M6S1/M6S1V) remain unchanged after test generation
- **FR-7.7 (Test G)**: Verify that when generated tests fail, `generate-tests` does NOT trigger implementation — it must stop and report, not write production code

The tests for the test generator MUST be saved to `tests/M7/` directory.

## Non-Functional Requirements

- **NFR-1 Security**: `generate-tests` MUST NOT write outside designated test directories (`tests/M{X}/`, `milestones/M{X}/`)
- **NFR-2 Determinism**: Given the same specification and verification inputs, `generate-tests` MUST produce the same test structure every time (same file paths, same test IDs, same exit code results)
- **NFR-3 Isolation**: Test generation MUST NOT depend on the presence of production implementation — it must work against a bare milestone/spec/verification trio
- **NFR-4 Observability**: All guardrail breaches MUST be reported in the output, not silently corrected
- **NFR-5 Backward Compatibility**: Existing milestone structures (M5, M6) and their artifacts MUST remain readable and usable after changes
- **NFR-6 Zero Side Effects**: Running `generate-tests` MUST NOT modify any file outside `tests/M{X}/` and `milestones/M{X}/M{X}S{Y}T*.md`

## Constraints

1. **No Production Implementation**: This specification MUST NOT write, modify, or generate any production source code. All output is test infrastructure only.
2. **Legacy Immutability**: Existing milestone artifacts (M3, M4, M5, M6 and all sub-artifacts) are immutable. No deletion, renaming, or reorganization.
3. **No Bulk Migration**: Do not rename files, change directory structures, or migrate legacy artifacts to new conventions.
4. **Investigation First**: FR-1 (investigation) must complete before any modifications begin. The investigation report must inform the implementation.
5. **No Changes to Other Skills**: Only `skills/generate-tests/SKILL.md` and `templates/test_template.md` may be modified. All other skills are out of scope.

## Assumptions

1. The contamination originates from instructions and examples within `skills/generate-tests/SKILL.md` and `templates/test_template.md`, not from external dependencies.
2. The smallest safe fix is to modify instruction language, add guardrails, and enforce process steps — not to rewrite the skill's fundamental approach.
3. Backward compatibility means legacy milestone structures continue to work without modification — not that test output format is identical.
4. Existing M5/M6 test artifacts that may contain contamination are documentational of the problem, not production code, and should be examined during investigation but left in place.
