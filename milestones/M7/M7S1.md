# M7S1: Artifact Identity & Metadata Contract

**Objective**: Implement the first phase of the Canonical Artifact Identity and Storage Architecture, focusing on defining canonical machine identifiers and mandating YAML frontmatter for all artifacts. This spec will establish the core metadata contract and include a validation script.

## **Functional Requirements**:

- **FR-1**: Define canonical machine identifiers for all artifact types (SPEC, VER, TEST, INV). Examples: `SPEC-001`, `VER-001`, `TEST-001`, `INV-001`.
- **FR-2**: Mandate YAML frontmatter for all artifacts.
- **FR-3**: The YAML frontmatter must include the following fields: `id` (canonical machine identifier), `type` (artifact type), `title` (human-readable title), `milestone_id` (ID of the parent milestone), `status` (e.g., draft, active, completed, superseded), and `derived_from` (list of artifact IDs from which this artifact is derived).
- **FR-4**: Prohibit semantic qualifiers in artifact IDs (e.g., `-CORRECTED`, `-FINAL`). IDs must be purely sequential numerical identifiers (e.g., `SPEC-001`).
- **FR-5**: Write a validation script (`validate_metadata.py`) to parse and enforce the YAML frontmatter schema defined in FR-3 and the ID format in FR-4.

## **Non-Functional Requirements**:

- **NFR-1**: The metadata schema must be extensible to accommodate future artifact types without requiring schema redefinition.

## **Architecture Impact** :

- Introduction of a new metadata layer (YAML frontmatter) for all AEF artifacts.

## **Data Flow**:

- Artifact creation processes will now prepend YAML frontmatter. The `id`, `type`, `milestone_id`, and `derived_from` fields will be generated or determined programmatically.
- `validate_metadata.py` will parse this frontmatter during artifact generation or validation.

## **Constraints**:

- **NO PLACEHOLDER TESTS:** Strictly forbidden from generating "Placeholder Test Scripts", outlines, or pseudo-code.
- **BASH INTEGRATION ONLY:** All generated tests must be `.sh` Bash scripts that use `grep`, `jq`, or Python execution against temporary fixture files. Do NOT generate `.py` `pytest` files for markdown/metadata validation.
- **NO SELF-REFERENTIAL TESTS:** Tests must scan isolated fixture directories, not their own source code.
- **NO DESTRUCTIVE MIGRATION:** Do not write any code that automatically deletes or renames M1-M9 legacy artifacts.
- **Requirements based on observable script executions, YAML schemas, or file existence only.**

## **Assumptions**:

- Existing artifact generation processes can be modified to include YAML frontmatter.
- The Python environment has necessary libraries for YAML parsing (e.g., `PyYAML`) and basic file operations.

## **Acceptance Criteria**:

- **AC-1**: `validate_metadata.py` correctly parses YAML frontmatter conforming to the specified schema (FR-3).
- **AC-2**: `validate_metadata.py` rejects YAML frontmatter that is missing required fields (`id`, `type`, `milestone_id`, `status`, `derived_from`).
- **AC-3**: `validate_metadata.py` rejects artifact IDs containing semantic qualifiers like `-CORRECTED` (FR-4).
- **AC-4**: New canonical machine identifiers (`SPEC-001`, `VER-001`, `TEST-001`, `INV-001`) are defined and can be programmatically generated or assigned.
- **AC-5**: All artifacts generated under this specification will include the defined YAML frontmatter.
