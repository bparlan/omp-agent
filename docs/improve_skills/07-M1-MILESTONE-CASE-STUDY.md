# M1 Milestone Case Study

## Purpose

This case study records the empirical result that motivated the current effort to improve AEF generation skills.

It is reference material for future skill improvement, not a template that downstream skills should copy.

## Three M1 Variants

The experiment compared:

1. `M1_solo_aef.md`
   - original `/milestone M1`;
2. `M1_supportive.md`
   - milestone generated with additional supportive context supplied during experimentation;
3. improved `M1.md`
   - milestone generated by the improved solo skill after targeted user clarification.

## Why the Comparison Matters

The original solo version demonstrated that the milestone skill could produce a usable document but left material information implicit or unresolved.

The supportive version demonstrated the quality possible when missing context was manually supplied.

The improved solo version demonstrated that the milestone process itself could discover material forks, investigate available evidence, ask targeted questions, incorporate the answers, and seal the resulting contract.

The architectural lesson is not that every stage should imitate the milestone interaction.

The lesson is:

> Material ambiguity should be resolved at the earliest appropriate responsibility boundary, and downstream stages must not silently reconstruct upstream intent.

## Improved M1 Behavior

During generation, three material forks were resolved:

| Fork | Resolution | Evidence basis |
|---|---|---|
| Runtime language | Pure JavaScript (ESM) | project documentation + user confirmation |
| ETH position | Native ETH | project configuration + user confirmation |
| Token scope | ETH + USDC only | roadmap + user confirmation |

The significance is the behavior:

```text
project evidence
      ↓
material fork detected
      ↓
targeted user clarification
      ↓
answer incorporated
      ↓
contract re-evaluated
      ↓
sealed milestone
```

## Resulting Contract Strength

The improved M1 contained:

- two explicit specification units;
- responsibility/boundary/outcome/dependency/constraint fields;
- concrete integration bindings;
- observable success criteria;
- security constraints;
- verification intent;
- contradiction reporting;
- deferred-scope boundaries;
- legacy roadmap boundaries;
- explicit statement that no material downstream requirements question remained.

## Contradictions Surfaced

The improved milestone identified and documented contradictions including:

- `PRIVATE_KEY` versus `WALLET_PRIVATE_KEY`;
- `targetAllocationBps` not summing to the expected total;
- a MORPHO address appearing to belong to another network;
- schema differences between project documents.

The important behavior was not simply finding contradictions.

The milestone avoided contaminating M1 with unrelated fixes while preserving the findings as documented drift or future concerns.

## What the Case Proves

The experiment supports the following conclusions:

### 1. Richer milestones are possible without external supportive context

The improved skill can acquire missing material information through its designated interaction phase.

### 2. Targeted questions are more valuable than generic questioning

The useful questions resolved forks that could materially change the contract.

### 3. Evidence-first questioning is preferable to immediate asking

Project documentation and configuration were inspected before user clarification was required.

### 4. A milestone should be specification-ready, not implementation-complete

The improved artifact contained enough technical constraints and boundaries for downstream specification while leaving legitimate implementation design downstream.

### 5. Explicit convergence is valuable

The statement that no material downstream requirements question remains creates a useful contract boundary.

## What This Case Does NOT Prove

It does not prove that:

- every generation stage should ask questions;
- every stage should use the same persona;
- every project needs the same sections;
- every implementation detail belongs in a milestone;
- the exact M1 artifact structure should be copied into specifications or tests.

## Transferable Principles

Use this case to test whether downstream skills can inherit:

- evidence-first reasoning;
- anti-fabrication;
- contradiction detection;
- explicit boundaries;
- observable outcomes;
- traceability;
- convergence;
- explicit failure instead of hallucination.

Do not transfer the milestone's user-interaction behavior wholesale.

## Regression Use

When future changes to generation skills are evaluated, ask:

> Would this skill make the same kind of material distinction that improved M1 made, but within its own responsibility boundary?

That is a more useful regression question than:

> Does this skill look like the milestone skill?
